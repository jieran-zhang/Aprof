# AscendC Kernel Direct Invoke

Use this skill to convert an existing AscendC kernel into a direct-invoke project that can be compiled and run. The primary output is a standard scaffold; simulator profiling is an optional validation path.

## Core Rules

- Treat the provided kernel as the algorithm source of truth. Do not rewrite `CopyIn` / `Compute` / `CopyOut`, tiling math, API order, or kernel class logic while scaffolding.
- Only add direct-launch glue: local project layout, CMake, host runner, data generation, optional tiling binary, and simulator config.
- Keep host/device launch ABI consistent. If the kernel takes `GM_ADDR` / `__gm__ uint8_t*`, host device pointers must be passed through as `GM_ADDR`-compatible launch arguments.
- Do not claim a scaffold is runnable unless shape, dtype, input/output/workspace sizes, blockDim, kernel name, and tiling data are known.
- Prefer a user-provided `io-spec-json` over guessing. Auto-inference is only for common AProf vector kernels with obvious `inputGM/outputGM/tilingGM` style signatures.

## Standard Workflow

1. Inspect the kernel entry and dependencies.
   - Find `extern "C" __global__ ... void <kernel>(...)`.
   - Record parameter order and classify each parameter as `input`, `output`, `workspace`, or `tiling`.
   - Check for relative includes. If the kernel depends on local headers, copy them into `op_kernel/` without changing algorithm logic.

2. Scaffold the project with the bundled tool.

   ```bash
   python skills/aprof/benchmark/ascendc-kernel-direct-invoke/tools/scaffold_direct_invoke.py \
     --kernel-file <path/to/op_kernel.asc> \
     --out-dir <output/project> \
     --op-name <op_name> \
     --kernel-name <kernel_entry> \
     --io-spec-json <io_spec.json> \
    --soc dav-2201
   ```

   The tool writes:

   ```text
   <project>/
     CMakeLists.txt
     run.sh
     scaffold_report.json
     op_kernel/<op_name>_kernel.asc
     op_host/main.cpp
     op_host/data_utils.h
     scripts/gen_data.py
     scripts/verify_result.py
     build_sim/op_config.json      # generated by scripts/gen_data.py
   ```

3. If `scaffold_report.json.status` is `needs_io_spec`, fill in the missing fields and rerun with `--io-spec-json`.

4. Build and run on a CANN host.

   ```bash
   cd <project>
   bash run.sh build
   bash run.sh gen
   bash run.sh run
   bash run.sh verify
   ```

5. Prefer ordinary hardware profiling when an NPU is available. It is faster and gives real runtime counters.

   ```bash
   bash run.sh profile
   ```

   By default, `profile` writes large profiler results under `tmp/aprof/...` at the repository root. Override with `APROF_TMP_ROOT` or `APROF_MSPROF_OUTPUT`.

6. Optionally build device-side simulator object and run `msprof op simulator`.

   ```bash
   bash run.sh sim-build
   bash run.sh sim
   ```

## IO Spec

Use this shape when auto-inference is not enough:

```json
{
  "blockdim": 1,
  "dtype": "float32",
  "params": [
    {"name": "inputGM", "kind": "input", "dtype": "float32", "shape": [2048], "file": "input.bin"},
    {"name": "outputGM", "kind": "output", "dtype": "float32", "shape": [2048], "file": "output.bin"},
    {"name": "tilingGM", "kind": "tiling", "size": 40, "file": "tiling.bin"}
  ],
  "tiling_values_u32": [2048, 2048, 2048, 2048, 2048, 256, 256, 8, 0, 0],
  "verification": {"mode": "exists"}
}
```

Supported `kind` values are `input`, `output`, `workspace`, and `tiling`. `verification.mode=exists` only checks that the kernel produced output bytes; use `golden_file` in each output param when mathematical verification is available.

## Simulator Notes

The generated `run.sh sim-build` path uses the same low-level device object flow as the old simulator SOP:

- compile with `bisheng -fPIC --aicore-only --asc-aicore-lang`
- link with `ld.lld -m aicorelinux -Ttext=0`
- run `msprof op simulator --config=./op_config.json`

Use `ASC_ARCH` to match the target hardware or simulator. The scaffold default is `dav-2201`; set `ASC_ARCH=dav-3510` for Ascend950-style environments.

Reference helper scripts and config templates remain under `references/` for manual debugging:

- `references/build_kernel_o.sh`
- `references/gen_input_tiling.py`
- `references/op_config.template.json`

## Validation Checklist

- `scaffold_report.json.status == "runnable"` before build/run claims.
- `python tools/scaffold_direct_invoke.py --help` works.
- `bash run.sh build` produces `build/<op_name>`.
- `bash run.sh gen` produces `data/*.bin` and `build_sim/op_config.json`.
- `bash run.sh run` exits 0 on a host with NPU or supported simulator runtime.
- `bash run.sh profile` produces `tmp/aprof/**/PROF_*` on a host with NPU and ordinary `msprof` support.
- `bash run.sh sim-build` produces `build_sim/<op_name>_kernel.o`.
- `bash run.sh sim` produces `tmp/aprof/**/msprof_sim_output/OPPROF_*` with `trace.json` or `*_instr_exe_*.csv`.
