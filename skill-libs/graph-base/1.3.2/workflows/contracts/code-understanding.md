# code-understanding：算法、实现与硬件行为理解

生产者：[代码理解角色](../agents/code-understanding.md)。消费者：协调者、诊断、规划和优化。位于 C0 preparation → code-understanding → C1 diagnosis，C0—C5 编号保持不变；新阶段只使用 [公共契约](common.md) 的 Markdown 外壳，`contract_version=1`、`stage=code-understanding`、`role=code-understanding`，不新增机器 schema 或 runtime 阶段。

## 输入

引用 preparation、实际分析父版本源码及其身份、完整 workload/语义与精度契约、已有架构/SDK/编译条件，以及可复用的理解报告。已有计时或机制证据可辅助区分事实与推断，不是开始或完成理解的前置条件。沿实际调用和数据路径按需读取 host、tiling、kernel、公共函数、宏与编译入口。

## 唯一产物与内容

唯一新增产物是本阶段的一份中文 Markdown；理解正文直接写在 `结果` 内，`inputs`/Context 引用已有源码和证据，`outputs` 可以为空。不另建理解 JSON、API 索引或重复报告，也不要求运行脚本或机器验收命令。

正文按下列顺序连贯解释当前实现：

1. **整体算法与数值语义**：输入到输出的数学含义、分阶段计算、归约与广播/索引、精度和转换/舍入、特殊值、有效域及 fallback；区分整体算法与当前实现的选择。
2. **实际分派、任务、循环与已有策略**：host/tiling 如何根据元数据、key、入口及编译条件选择实际路径，任务如何划分，核内循环、尾块和已有 tile/buffer/流水策略怎样完成算法；说明 workload 分区及未覆盖的条件。
3. **数据所有权、布局、存储与依赖**：谁读写每项数据、地址/索引与布局、GM/片上存储和 workspace、有效范围与同时存活集合、搬运/计算/归约和同步先后；把访问和依赖关系连成完整数据路径。
4. **910C 硬件行为**：依据实际架构与 SDK 条件，将当前路径映射到相关计算/搬运单元、存储层级、指令/API、队列和同步；区分源码可确认的行为、条件化推断与尚无实测的性能判断。未确认平台或资源时明确适用条件，不猜核数、带宽、容量或收益。

关键解释附源码定位（路径、函数/符号、行号或稳定锚点）与必要的上下文片段，覆盖影响结论的 host、tiling、kernel、公共函数和编译片段；无需机械摘录全部文件或 API。片段服务于算法、控制和数据依赖解释，不代替解释本身。事实、推断、未知和已有测量各自标明来源。

此阶段恢复当前算法与策略，不预选 Problem、Action 或新的 C2 方案；诊断和策略选择仍由 C1/C2 完成。性能缺测不阻断理解，也不把静态解释写成瓶颈或收益证明。

数据相关路径按[工程阅读方法](../../skills/ascendc-code-understanding/references/engineering-reading.md#数据流要携带位置布局和单位)核对参与判断的输入、触发粒度与受影响循环；原始生成范围与合法输入域分开。只补充会影响当前理解的路径，不新增理解产物或必跑工具。

## 完成、复用与更新

请求范围内的主算法、实际路径、数据依赖及硬件映射已有连贯解释，即可 completed；非关键未知项列出影响范围与补查方式。只有缺失源码/语义/相关条件使当前理解无法成立时才 needs_input，不因缺 profiling、未运行设备或尚未选动作返回缺项阻断。

已有适用报告可直接作为本阶段结果复用，由接收请求记录原报告引用、身份和范围匹配依据；不为补齐格式另造第二份理解报告。报告供 C1、P/O 和 R2 共同引用，下游按当前任务核对其语义、分派、owner 与依赖，不从头重复恢复全套实现。

源码、workload/语义域、分派、SDK/编译条件或架构能力等相关条件变化时，标出受影响结论，仅更新这些部分并保存后继，保留原报告与未变部分引用；新候选的实际改动也按此处理。纯新增 profiling 交给 C1 更新机制判断，不触发重做理解；若新证据揭示原理解错误，仅修订受影响解释并保留依据。复用和更新不重置原任务预算。
