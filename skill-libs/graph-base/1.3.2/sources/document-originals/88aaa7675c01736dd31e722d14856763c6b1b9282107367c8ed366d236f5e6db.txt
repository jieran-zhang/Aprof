## 结论与交接状态

本轮选择一个共同方案，分别绑定子例 a、b：

> **保持输出分核、几何预计算和数值分支不变；把索引、权重的两次规则多块搬入合成一次位模式搬入，并将本域的 UB 行跨度由 1920 收紧为 256。**

登记一个 `action.coalesce_contiguous_transfers` 实例即可；合并存储、局部 tile 参数、尾块及同步是其配套实现，不另凑 Action。两例采用同一实现，但 **a 的加权计算为 Vector Mul/Add，b 为必须保留的软件整数 FMA**，因此成本构成和收益上限显著不同。

这是**条件化纸面方案及 C2/C3 交接**，不是已实现候选。未使用工具，未编译、未修改源码、未运行正确性或硬件计时。目标平台按任务约束绑定为 **910C/dav-2201**；实际 SDK、可用 UB、启动核数及完整 Host 接线仍需后继核验，不伪造 hash 或路由执行记录。

# 一、共同代码理解：当前实际执行什么

## 1. 实际路径与数值关系

本题明确执行 `GridSampler3DWeighted<float>`，不能把最初摘录中的 `GridSampler3DScalar<float>` 当成当前路径，也不能把 half 路径的 Cast 成本计入本题。

记：

- 输入空间长度 \(I=DHW=4096\)；
- 输出空间点数 \(S=256\)；
- 几何长度 \(G=NS=256\)；
- 输出元素数 \(NCS=2048\)。

`GridGeometryRange`（243–270 行）先生成每个空间点的八个**空间内字节偏移**和八个 float 权重：

\[
w_k=\operatorname{fl}\bigl(\operatorname{fl}(w_xw_y)w_z\bigr).
\]

几何与通道无关，输入值与通道有关。表布局为：

```text
geometry:
  index[k,p] : uint32，k=0..7，行跨度 G
  weight[k,p]: float， k=0..7，行跨度 G
```

总有效大小：

\[
8G\cdot4+8G\cdot4=64G=16384\text{ B}.
\]

`GridSampler3DWeighted<float>::Process` 的阶段为：

```text
本核拥有的连续输出区间
  → 按通道边界截断为片段
  → 搬入该通道完整 X 平面到 UB
  → 对完整通道执行 GridNeedsFma32
  → 搬入该片段的八行 index 和八行 weight
  → 两次 Gather，各取四邻居
  → 按 k=0..7 加权累加
  → 只写有效 count 个 float
```

对每个输出，初值为 `+0.0f`，邻居顺序不变：

- `software=false`：每邻居先 binary32 `Mul`，再按顺序 `Add`；
- `software=true`：每邻居调用一次正确的 `GridFma32Bits`，计算 fused multiply-add 的 binary32 结果。

**两条路径不能任意互换。** 实数公式相同不构成逐位等价；这里的软件 FMA 也不是一条硬件 FMA 指令。

## 2. 两例共同地址事实

`alignCorners=false`、尺寸为 16 时，源码坐标变换对应：

\[
u=((g+1)\cdot16-1)/2.
\]

给定 grid 在 \([-0.8,0.8]\)，坐标约在 \([1.1,13.9]\)，八邻居坐标处于 1 到 14，均在界内。仍保留源码的越界哨兵机制：非法邻居偏移为 \(I\cdot4=16384\)，指向 UB 中显式写入的零。

此事实只用于解释这两个输入，**不用于取消边界检查或按输入分布派发**。

## 3. 当前分配与有效工作量

由 457–460 行，float 路径：

\[
cb=\frac{4096+64}{64}\cdot64\cdot4=16640\text{ B},
\]

\[
T=\min\left(1920,\left\lfloor
\frac{196352-8192-cb}{128\cdot84}
\right\rfloor128\right)=1920.
\]

显式 UB 分配为：

| 区域 | 字节数 |
|---|---:|
| cache | 16640 |
| index，\(8T\) 个 uint32 | 61440 |
| weight，\(8T\) 个 float | 61440 |
| values，\(4T\) 个 float | 30720 |
| acc，\(T\) 个 float | 7680 |
| **合计** | **177920** |

源码中的 196352、8192 是当前预算表达式，不直接证明目标可分配容量或 API 预留已闭合。

每个计算片段都被通道剩余空间截到 `count≤256`。所以在本域中：

- 每片 `count != 1920`，会初始化全部 \(8T=15360\) 个索引；
- 两次 Gather 共处理 \(8T=15360\) 个值；
- 但最多只有 \(8\,count≤2048\) 个邻居值参与数学计算。

这是明确的**物理执行域大于有效域**，不需要性能测量才能确认；其耗时占比仍未知。

为避免猜核数，定义 \(J\) 为所有核的有效“核×通道片段”数。保持当前连续区间映射时，本域一个这样的片段不会因 \(T=1920\) 再切成多片，故通道 cache 搬入次数也是 \(J\)。具体 \(J\) 由实际 `blockLength/BlockDim` 决定。

共同逻辑请求量包括：

- X 平面搬入：\(16384J\) B；
- 几何消费：\(2048\times64=131072\) B；
- 输出：\(2048\times4=8192\) B；
- 几何生产有效写出：16384 B，读取 grid：3072 B。

这些是源码请求量，**不是 HBM 实测流量**。

# 二、子例 a

## 1. 当前路径、关键事实

每个通道所有 X 值有限且在 \([-1,1]\)。`GridNeedsFma32` 的正、负阈值检查都不命中，故：

```text
完整通道阈值检查
  → software=false
  → 两组 Gather
  → 八次逐元素 Mul，八次有序 Add
```

全输出有效加权工作：

- 16384 个 binary32 乘法；
- 16384 个按既定顺序的 binary32 加法；
- 软件 FMA 调用数为零。

每片有八次 Mul、八次 Add；Add 间存在真正的累加依赖，不能将其直接合成无序归约。

## 2. 主要方案：合并几何搬入，并收紧局部跨度

将 `index_`、`weight_` 改为一个 **16 行、每行跨度 \(T'=256\) 元素**的 VECIN TBuf：

```text
第 0..7 行：uint32 index 位模式
第 8..15 行：float weight 的原始位模式
```

用一次 uint32 `DataCopyPad` 搬入 16 行；权重部分仅作 `ReinterpretCast<float>`，不作数值转换。

本域取 \(T'=256\)，不会增加片段数，因为原有每片已经满足 `count≤256`。其变化为：

| 工作 | 当前 | 候选 |
|---|---:|---:|
| 每片几何 DMA 调用 | 2 次，各 8 行 | 1 次，16 行 |
| 几何有效字节 | \(64\,count\) B | 不变 |
| 索引初始化 | 15360 个 uint32 | 2048 个 uint32 |
| 两次 Gather 总执行量 | 15360 个 float | 2048 个 float |
| 有效 Mul/Add | 各 \(8\,count\) | 不变 |
| 输出、cache 搬入、阈值检查 | 原路径 | 不变 |

每片索引初始化减少 **13312 个元素/53248 B 写入**。Gather 的索引读取、cache 取数及 values 写入各自对应的元素域由 15360 降至 2048；这里减少的是 UB 工作，不混称为 GM 删读。

显式分配变为：

\[
U'=16640+16T'\cdot4+4T'\cdot4+T'\cdot4
=38144\text{ B}.
\]

比当前少 **139776 B**。这不自动意味着提速，也不据此认定原实现存在容量瓶颈。

**选择理由：**该方案同时针对每片确定存在的两次搬运发射和大范围 dummy Gather/初始化；不改浮点操作、不减少独立 owner，也不增加 GM 有效字节。它比只缓存少量字段更直接覆盖当前可数的数据路径。

## 3. 最有竞争力的替代：四邻居 Mul 合批

替代方案是在相同的 \(T'=256\) 局部布局下，对 `software=false && count==T'` 的四行连续区域，一次执行 `Mul(...,4*T')`，代替每组四次 `Mul(...,count)`：

- 两组 Mul 调用从八次降到两次；
- 有效乘法数不变；
- 八次有序 Add 保留；
- 短片仍走原四次 Mul，避免为合批额外初始化和计算权重 dummy；
- 无新增 GM workspace，显式容量可同为 38144 B；
- 若不合并几何搬入，仍保留两次几何 DMA。

它可用 `action.batch_vector_api_calls` 表达，且数值上比改为 FMA 更容易守住原边界。但是，它在本域的实际优化覆盖取决于是否存在 `count=256`：若分核将通道分成多个短片，合批分支可能完全不执行。主方案的初始化/Gather 缩减则覆盖每个有效片段。因此本轮选择前者，不将两者无依赖地叠加。

其他明显方向：

- **几何跨通道驻留**：可能减少几何重读，但需改变 owner/遍历组织，见后文共同比较。
- **删 cache 全区清零**：确有“有效搬入覆盖原零”的分析机会，但必须逐项证明 Compare/Gather 的完整读取域；不是本轮合并搬运必需步骤，不夹带删除。
- **只收窄同步**：先保留原完成边，本轮不以屏障数量推断可删依赖。

# 三、子例 b

## 1. 当前路径、关键事实

每个通道最后一个 X 元素是 \(2^{125}\)，满足正阈值 \(x≥2^{124}\)。

`GridNeedsFma32` 检查的是**完整 4096 元素通道 cache**，不是 Gather 后的邻居集合，因此：

```text
完整通道正阈值检查命中
  → software=true
  → 负阈值检查因 || 短路可不执行
  → 所有输出都执行软件加权
```

虽然最后元素从不被采样，仍不能将本例改派到普通 Mul/Add。

全输出必须执行：

\[
2048\times8=16384
\]

次 `GridFma32Bits`。其中每个输出在两组软件函数调用中分别读取、写回 accumulator，两个 group 各消费四邻居。这个整数算法内部的指令数量与分支成本，输入没有给出完整实现，不能编造。

## 2. 主要方案及与 a 的成本差异

仍采用上面的单次 16 行几何搬入及 \(T'=256\) 布局。

变化与 a 相同：

- 几何 DMA：\(2J\to J\)；
- 索引初始化：\(15360J\to2048J\) 个元素；
- Gather：\(15360J\to2048J\) 个元素；
- 显式 UB：177920 B → 38144 B；
- 有效几何 GM 字节、X 搬入、输出和完整通道阈值检查保持。

不同之处是：

- **16384 次软件 FMA 一次也不减少；**
- 不存在可在此实际路径应用的四邻居普通 Mul 合批收益；
- 软件加权的 Scalar GetValue/SetValue、整数 FMA 工作仍然保留。

因此，本方案对 b 只覆盖搬运准备和邻居取得阶段，不能宣称解决其主要计算成本。仍值得作为静态可行试验：减少的是确定执行的工作，且不以丢弃软件 FMA 换取收益。净收益可能被软件 FMA 的成本稀释，需后测。

## 3. 最有竞争力的替代：跨输出批量实现精确整数 FMA

不同输出 p 之间独立，理论上可将软件 FMA 的整数步骤按 p 向量化，仍在 k 方向顺序递推：

\[
a_{k+1,p}=\mathrm{FMA32Bits}(v_{k,p},w_{k,p},a_{k,p}).
\]

这比合并一次几何 DMA 有更大的计算覆盖潜力，但本轮存在具体能力缺口：

1. 输入只承诺 `GridFma32Bits` 正确，没有提供其完整整数算法；
2. 不能核验其中宽整数、移位、进位、规格化、舍入、特殊值处理能否由 dav-2201 API 等价表达；
3. 向量化后新增临时 tensor、mask、整数宽度和 scratch 数量无法闭合。

所以只能保留为 **`action.vectorize_scalar_loop` 的待证提案**，不能注册为 ready 实施实例。其潜在新增代价为按算法状态数 \(m\) 计的若干 \(AlignUp(mT's,32)\) 临时字节、逐步 mask/选择和特殊值处理；没有算法正文，不能填具体数值。

以下“替代”则明确不合法：

- 改为硬件 FMA或普通 Mul/Add；
- 只检查采样邻居而不保持原完整通道触发规则；
- 因采样未触及极值就删除软件路径；
- 按 a/b 的数据分布创建 Host 派发条件。

# 四、Action 实例与共同机会比较

## 1. 本轮实例

纸面实例身份可记为 **GS3D-geometry-copy-compact-v1**：

| 项目 | 绑定 |
|---|---|
| Action | `action.coalesce_contiguous_transfers`，输入所给版本 |
| 父实现 | 当前 Weighted<float> 摘录 454–485 行及辅助函数 |
| target | 几何 workspace 的 index、weight 两个连续行组 |
| stage | `Process` 468–470 行 GM→UB |
| workload | 两例相同 shape、float、NCDHW、bilinear/zeros/alignCorners=false |
| 变换 | 两个 8 行请求 → 一个 16 行 uint32 位模式请求 |
| 配套参数 | 本域局部行跨度 1920 → 256，owner/有效片段不变 |
| 结构依据 | 源 GM 的八行索引紧接八行权重；两组行跨度同为 G |
| 语义依据 | 只搬运位模式；权重不 Cast；有效 count 和 k 顺序不变 |
| 容量状态 | 已算出需求，目标实际可用容量尚待绑定 |
| 性能状态 | 未测；不认定 setup 主导 |

`symptom.source.inner_loop_copy` 可由源码确认；地址合并等价可纸面证明。容量前提在后继确认实际预算前保持条件状态，不伪填 true。正式实例还缺父源码、模板、计划的真实 hash；本轮不虚构这些身份。

## 2. 为什么不优先改为跨通道几何驻留

若同一 owner 连续消费 \(C_t\) 个通道，同一空间片几何可从读 \(C_t\) 次降为一次。全通道同 owner 的理想几何请求量可由 131072 B 降至 16384 B。

但完整代价包括：

- owner 从输出连续片改为通道块×空间片；
- 空间片长 \(S_t\) 时，任务数约为
  \[
  N\lceil C/C_t\rceil\lceil S/S_t\rceil;
  \]
- 若每个空间片仍搬入完整通道，则 X 请求量约为
  \[
  NC\lceil S/S_t\rceil I\cdot4,
  \]
  除非另有合法驻留组织；
- b 中每 owner 还承担更多软件 FMA，可能拉长最长核；
- 几何需要更长存活期，不能再借作阈值检查的死 scratch；
- 跨通道仍必须分别检查各通道的完整 X，不得共享一个软件标志。

因此它是有竞争力的重规划方向，但实际核数、cache 重读与任务粒度会改变结论。本轮选择不改变 owner 的方案；这不是因为缺实测统一拒绝驻留。

# 五、统一 C2：所有权、布局、workspace、同步与容量

## 1. 保持与改变

**保持：**

- 每核输出区间：
  \[
  [b\cdot blockLength,\min((b+1)blockLength,outputNumel)).
  \]
- 按通道边界截断的原片段；
- 几何生产者、所有消费者和 GM 表布局；
- X/Y 外部 NCDHW 布局；
- 完整通道 `GridNeedsFma32`；
- 两组四邻居、总 k=0..7 的数值顺序；
- 原输出 DMA 和无跨核归约的结构。

**改变：**

- 本域 \(T'=256\)；
- 独立 index/weight 分配变成一份 \(16T'\cdot4\) B 的 VECIN 分配；
- 两次几何 DMA 合一。

这不是完整 `P_KEEP`：虽然 owner 不变，局部物理布局和参数自由度需要新共同计划。若工程没有父计划，先提取旧计划，再建立此变化版；不能将“提取已有计划”计为并行优化。

## 2. 几何搬入参数

令 \(v=count\)，\(T'=256\)，\(G=256\)。一次 16 行 GM→UB：

\[
blockCount=16,\quad blockLen=4v,
\]

\[
srcStride=4(G-v)\quad\text{（GM 字节间隔）},
\]

\[
dstStride=\frac{4T'-AlignUp(4v,32)}{32}
\quad\text{（UB 的 32B 块间隔）}.
\]

源起点仍为原 `idx_[gp]`。第 8 行自然落到权重第 0 行的同一 gp；UB 第 8 行作为 float 视图使用。

本域 `blockLen≤1024B`，行数 16，参数范围小于所给 A3 文档上限。短行可沿用 uint32 哨兵 padding，权重有效位原样搬入；权重 dummy 不参与有效 count 计算，不能把它当数学零。

## 3. Workspace 与容量

- 几何有效 workspace 仍为 **16384 B**；
- 不删除、不缩小未展示的框架保留段；
- 不新增全局标志或跨核交换空间；
- 候选显式 UB 为 **38144 B**；
- 实施门禁：
  \[
  38144+B_{\text{API/框架/其他实际预留}}\le U_{\text{available}}.
  \]

相同预留下候选显式分配小于父实现，这是有利的资源关系，但不冒充实际容量探测。

## 4. scratch 与同步生命周期

必须保留以下边：

1. X 的 MTE2 完成 → 完整通道阈值检查、Gather；
2. 阈值检查结束 → index/acc 死租约可被几何和累加覆盖；
3. 几何 MTE2 完成 → Gather/加权；
4. Gather 完成 → 软件 Scalar 读取或 Vector Mul；
5. 每个邻居累加完成 → 下一邻居累加；
6. acc 计算完成 → MTE3；
7. MTE3 读完 acc → 下一片覆盖。

特别核验收紧后的 scratch：

- `GridAnyCompare32(count=4096)` 的 `firstMask` 需要 128 个 uint32；
- temp 至少覆盖 `temp[64]` 所在区域及相关 64 元素操作；
- 新 index 区有 2048 个 uint32，acc 有 256 个 uint32，仍足够；
- 调用时它们确为死租约，不能在保留活几何或未完成输出时复用。

本轮保留原保守屏障，不另实施同步收窄，也不宣称建立了流水重叠。几何生产完成到消费者启动的跨阶段依赖需沿实际 Host/launch 协议核验，核内 `PIPE_ALL` 不能代替它。

## 5. 派发与 fallback

两例必须命中相同元数据域，不能按数值分布分派。候选域限定所列 shape、dtype、布局和模式；其他元数据保持原通用路径。

优先在现有入口内作元数据守卫及局部参数选择，不为本轮强造新 Key。实际扩展 tiling/Host 未完整提供，C2 不虚构既有 key 或 entry。若后继工程必须新增 key，应先冻结真实互斥表，再交 C3 接线。

# 六、C3 准确实施步骤及知识正文的实际影响

以下为交给后继的步骤，**本轮均未执行**。

1. **绑定真实父本与接线。**确认实际 Weighted<float> 入口、扩展 tiling、BlockDim、几何 workspace 分配及生产完成协议；冻结真实源码身份。
2. **加入本域参数。**在合法元数据域取 \(T'=256\)，其他域原样 fallback；不改变 `blockLength`。
3. **合并物理分配。**删除原独立 index/weight 两次分配，改为一份 16 行 VECIN；索引前半视图为 uint32，后半视图为 float。不能只合并变量名而仍保留两份分配。
4. **保持阈值检查位置。**仍先完成 cache 搬入及完整通道检查，再覆盖 index/acc scratch；b 必须继续得到 software=true。
5. **替换几何搬入。**用上述 16 行参数复制原始 uint32 位模式，保持 gp 和每行有效 v。
6. **统一更新局部跨度。**所有初始化、Gather、权重寻址、values、acc 分配与调用都使用 \(T'\)，不能只改分配而漏改 `k*stride`。
7. **保持数值实现。**`GridApplyWeightedFour` 和 `GridSoftwareWeighted` 的有效 count、group、k 顺序不变；不顺便合批 Mul、换 FMA 或删零项。
8. **保留完成边。**先完成现有同步链的等价实现；任何后续收窄另回交接。
9. **审查、构建、完整验证后才计时。**完整输出覆盖所有已声明路径与 fallback，特别检查位模式、短片、跨通道片段和软件 FMA 触发。记录失败，不将未测写成通过。
