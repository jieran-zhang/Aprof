## 结论与交接状态

本轮选择两份**分别针对子例评估的纸面候选**：

- **子例 a：完整通道任务，空间 tile=256。** 每个任务处理一个通道的全部 256 个采样点，减少小任务重复装入、扫描以及大量无效 Gather lane。
- **子例 b：每通道拆成 4 个空间任务，每任务 64 点，物理 tile=128。** 保留全部软件 FMA，缩短单任务整数计算链，同时大幅缩小当前过大的 Gather/初始化域。

两者均用一个 `action.decompose_tasks_dynamically` 实例表达“重新组织独立输出任务并选择核数”，tile、搬运和生命周期调整是该任务方案的配套实现，**不额外凑 Action**。

**重要限制：a、b 元数据相同，不能根据输入分布选择这两份计划。** 它们是两个子例各自的候选分析，不是可直接拼接的生产派发器。任何一份候选都必须对相同元数据下的 a、b 及原数值合法域保持正确；若最终只允许一个实现，应比较两个候选的完整结果后选择其一，不能在 Host 判断“输入属于 a 还是 b”。

当前仅完成纸面 C1/C2 和 C3 实施交接；未修改、编译、运行。所有性能结论为预测，状态为 **not_measured**。实际可用 UB、当前完整 Host/Weighted tiling ABI、源码及模板 hash 未提供，不能虚构正式注册或 C3 completed。

# 一、共用的实际路径与数值依赖

## 1. 当前执行的不是原始 `Scalar<float>` 路径

按题目指定，实际执行的是后续摘录中的：

```text
GridGeometryRange
  → GM geometry：8 组 uint32 字节偏移 + 8 组 float 权重
  → GridSampler3DWeighted<float>
```

原始 `GridSampler3DOne<float>` 只用于理解坐标、邻域顺序等来源，不能把其逐输出几何重算计入当前 Weighted 路径的优化收益。

实际数据流为：

```text
grid GM
  → 标量生成几何
  → geometry GM
  → index/weight UB
                         ┌→ GridNeedsFma32：扫描整个通道
x GM → 完整通道 cache UB ┤
                         └→ 两组 Gather，各4邻居
                            → Vector Mul/Add 或软件整数FMA
                            → acc UB → y GM
```

VECIN、VECCALC、VECOUT 在该目标均为 UB，不是三个独立容量池。

## 2. 数学与舍入必须按实际分支描述

本例 `alignCorners=false`、尺寸为 16，反归一化实数表达式为：

\[
u=8(g+1)-0.5
\]

给定 grid 范围对应内部约 `[1.1,13.9]`，8 邻居均合法。代码仍必须保留通用越界哨兵，不得把“内部 grid”当元数据派发条件。

几何权重按当前源码：

\[
w_k=\operatorname{fl}(\operatorname{fl}(w_xw_y)w_z)
\]

计算，邻居顺序为 `k=0…7`。随后：

- `software=false`：
  \[
  a_{k+1}=\operatorname{fl}\bigl(a_k+\operatorname{fl}(x_kw_k)\bigr)
  \]
- `software=true`：
  \[
  a_{k+1}=\operatorname{FMA}_{32}(x_k,w_k,a_k)
  \]

软件 `GridFma32Bits` 是正确 binary32 fused multiply-add 的整数实现，不能按“一条硬件 FMA”估算，也不能改成普通 Mul/Add。

**即使实际采样值很小，两条路径也不能据此认定逐位等价。**

## 3. 可由源码确定的容量和工作量

记：

- 输入每通道 \(I=4096\) 个 float，16384B；
- 输出 \(O=8\times256=2048\) 个 float，8192B；
- geometryLength \(G=256\)；
- 几何有效存储：
  \[
  8G\times4+8G\times4=16384\text{B}
  \]
- 所有输出消费 geometry 的逻辑读取：
  \[
  O\times(8\times4+8\times4)=131072\text{B}
  \]

当前 float 缓冲公式得到：

\[
cb=((4096+64)/64)\times64\times4=16640\text{B}
\]

\[
tile=\min\left(1920,\left\lfloor
\frac{196352-8192-16640}{128\times84}
\right\rfloor128\right)=1920
\]

当前显式静态 UB：

\[
16640+84\times1920=177920\text{B}
\]

源码另留 8192B，但这只是源码预算，**不证明当前平台实际可用容量及全部隐含开销已闭合**。

每次循环被通道边界裁剪，故 `count≤256<1920`，但每组 Gather 仍执行 `4*1920`，两组合计 **15360 个 float lane**；每轮还初始化 `8*1920=15360` 个索引。

令 \(M\) 为当前有效核区间与通道区间的非空交集数。因 tile 大于单通道输出长度：

- 当前循环次数为 \(M\)；
- 完整通道装入及检测次数也是 \(M\)；
- \(M\ge8\)，具体值需要实际 `blockLength/BlockDim`；
- 输入逻辑搬入：`16384M` B；
- Gather：`15360M` 个 lane；
- 索引初始化：`15360M` 个 uint32；
- 有效邻居值始终仅 `8O=16384` 个。

这些是逻辑请求和执行域，不能等同实际 HBM 字节或耗时。

# 二、子例 a

## 1. 当前实际路径与关键事实

每通道所有值在 `[-1,1]`：

- `GridNeedsFma32` 正向、负向检测均为 false；
- 每次装入通道后执行两次完整检测；
- 加权阶段实际为 Vector Mul/Add；
- 整体有效运算为 16384 次乘法、16384 次按序加法；
- 权重已经预计算，当前没有跨通道重复生成几何的问题。

本例主要可减少的是**完整通道重复装入/检测、过大物理 tile 的无效 Gather 和初始化**，不是再把加权循环“向量化一次”。

## 2. 主方案：完整通道任务

纸面计划 `A-channel-owned`：

- 逻辑任务：8 个 `(n,c)`，每任务处理 `p=[0,256)`；
- 每任务 `count=tile=256`；
- 启动核数 \(K=\min(A,8)\)，\(A\) 为实际可用 AIV 核数；
- 用商余方式将完整任务连续分给核，不拆一个通道；
- 同核处理多个通道时顺序切换 cache；
- 所有检测、权重、加法顺序和写回语义保持。

### 工作变化

| 项目 | 当前 | 主方案 |
|---|---:|---:|
| 输出处理循环 | \(M\) | 8 |
| 通道装入/检测 | \(M\) | 8 |
| 输入逻辑搬入 | \(16384M\) B | 131072B |
| 检测源元素比较 | \(8192M\) | 65536 |
| Gather lane | \(15360M\) | 16384 |
| 索引全区初始化 | \(15360M\) | 可删除：没有短 tile |
| geometry 有效读 | 131072B | 131072B |
| 输出有效写 | 8192B | 8192B |
| 有效 Mul/Add | 各16384 | 不变 |

`count==tile` 后，8 行索引被 DMA 完整定义，可以不执行原短 tile 的 sentinel 初始化。cache 的零哨兵仍保留。

显式 UB：

\[
U_A=16640+84\times256=38144\text{B}
\]

连同源码原 8192B 预留为 46336B，再加实际尚未识别的 SDK/编译开销。

### 覆盖及新增代价

- 优化覆盖：指定元数据下全部 2048 个输出。
- 未改变：几何预计算、geometry GM 存储、完整通道扫描、特殊值路径、软件 FMA 实现。
- 新代价：最大只有 8 个独立通道任务；若当前使用更多核，可能损失并发。
- 不新增转置、Cast、GM workspace 或跨核归并。

本例选择该方案，是因为实际有效 Vector 工作很小，而重复装入、检测和 dummy lane 有明确数量；减少这些工作值得作为静态可行试验，尚不等于确认其占关键路径。

## 3. 最有竞争力替代：每通道 4 个空间任务

即下文 b 的 `Q=4、每任务64点、tile=128` 方案。

其循环数为32，完整通道装入数 \(R_4\) 取决于任务到核的映射及同核 cache 复用，满足：

\[
8\le R_4\le32
\]

成本为：

- 输入 `16384R₄` B；
- 检测源比较 `8192R₄` 个元素；
- Gather 32768 lane；
- 索引初始化32768个 uint32；
- geometry/output 有效字节及算术不变；
- 显式 UB 27392B；
- 提供最多32个独立任务。

它以更多装入、检测、API 发射和 padding 换更高任务并行。若完整通道方案的最长核确实较慢，而额外核可明显缩短关键路径，该替代可能更好。因此 a 的选择对实际核数和每阶段延迟敏感，不声称 Q=1 已最优。

# 三、子例 b

## 1. 当前实际路径与关键事实

每通道末元素为 \(2^{125}\)，尽管所有采样都不读该位置：

- 检测扫描的是完整4096元素通道，不是采样邻域；
- 正向比较发现 `>=2^124`，`GridNeedsFma32` 返回 true；
- `||` 短路使负向检测不执行；
- 每个输出仍执行8次 `GridFma32Bits`，总计：
  \[
  2048\times8=16384
  \]
  次软件整数 FMA。

**“异常大值没有被采样”不能用于关闭软件路径。** 检测影响最终舍入路径，属于当前外部数值契约，而非可任意收窄的数据筛选。

相比 a，完整通道检测少了一次极性扫描，但加权阶段变成大量逐输出整数工作，任务并行的价值明显不同。

## 2. 主方案：每通道 4 个独立空间任务

纸面计划 `B-spatial4-owned`：

- 任务 `(c,j)`，`c∈[0,8)`、`j∈[0,4)`；
- 输出范围 `p=[64j,64(j+1))`；
- 共32任务，每任务64输出；
- 物理 `tile=128`，有效 `count=64`；
- 启动 \(K=\min(A,32)\) 个核，连续商余分任务；
- 同核相邻任务若属于同通道，保留原 cache 和 `software` 结果，不重复装入。

选择128而非64的一个**结构性理由**是：现有检测临时借用 `acc`，其 `temp[64]` 比较写入需要至少128个 uint32 的空间。直接把 acc 缩到64元素会破坏现有租约，不能只看输出 count。

### 工作变化

| 项目 | 当前 | 主方案 |
|---|---:|---:|
| 输出处理循环 | \(M\) | 32 |
| 通道装入/检测 | \(M\) | \(R_4\)，8…32 |
| 输入逻辑搬入 | \(16384M\) B | \(16384R_4\) B |
| 检测源元素比较 | \(4096M\) | \(4096R_4\) |
| Gather lane | \(15360M\) | 32768 |
| 索引初始化 | \(15360M\) | 32768 |
| 软件 FMA 次数 | 16384 | 16384 |
| 单任务软件 FMA | 按当前分区 | 512 |
| geometry/output有效字节 | 131072B / 8192B | 不变 |

即便当前最少只有 \(M=8\)，Gather lane 也由122880降至32768；这只是工作域缩减，不是加速比。

显式 UB：

\[
U_B=16640+84\times128=27392\text{B}
\]

加原8192B预留为35584B，仍须核验实际可用容量。

### 新增及保留代价

- 若当前 \(M<32\)，geometry 搬入、Gather 和写回调用次数会增加。
- 输入搬入/检测未必减少：由 \(M\) 与 \(R_4\) 比较决定，不能一概记收益。
- 每任务有64个无效空间 lane，8邻居累计产生16384个额外 Gather lane。
- 软件 FMA 总量、整数实现、特殊值处理全部保留。
- 不改变每输出8邻居顺序；没有 partial、原子和跨核求和。

本例不选完整通道作为首选，是因为它将每任务软件 FMA 链增至2048次，并将任务数限制为8；减少 dummy 工作仍有价值，但不能忽略软件整数计算的并行机会。Q=4是本轮有界折中参数，**不是测得最优阈值**。

## 3. 最有竞争力替代：完整通道任务

使用 a 的方案：

- 8任务、每任务256输出、tile256；
- 输入131072B；
- 正向检测32768个源元素；
- Gather16384 lane，无短 tile 索引初始化；
- 显式 UB38144B；
- 软件 FMA仍16384次，每任务2048次。

它在逻辑工作量和接口次数上优于Q=4，但可用并行任务更少。若实际可用核不超过8，或装入/检测/发射占主导，它可能胜出；若软件 FMA 是主要关键链且有更多核，Q=4更值得试。

更细拆分如Q=16会产生128任务，每任务128次软件FMA，但 tile128 下 Gather升至131072 lane，完整通道装入最多128次。故不因软件路径重就无限细分。

## 4. 更激进路线的能力缺口

`action.vectorize_scalar_loop` 可以作为“跨输出并行实现精确整数 FMA”的分析入口，但目前不能登记为可实施实例：

- 未提供 `GridFma32Bits` 正文，无法展开其整数位宽、移位、规格化、舍入和特殊值分支；
- 已给 Vector 正文不提供一份精确 binary32 软件 FMA 的等价向量实现；
- 不能用硬件 FMA、Mul/Add、降低精度替代。

因此本轮不选择此路线。阻塞点是**精确实现与目标 API 合法性证明缺失**，不是“没有性能测量”。

# 四、Action 实例与统一 C2 合同

## 1. 实例登记

分别提出：

- `A1`：`action.decompose_tasks_dynamically`  
  目标：`Weighted<float>` 输出任务；阶段：Host任务分配及 `Process`；参数：Q=1、tile256。
- `B1`：同一注册 Action 的独立实例  
  参数：Q=4、每任务64点、tile128。

父本均绑定本题指定的 Weighted 摘录，而非原始 Scalar 实现。

实施条件：

- 固定线性任务映射：源码事实成立，不代表已测欠并行；
- 输出所有权与数值顺序：可按下述公式证明；
- 容量：给出需求，实际上限仍待补齐；
- 精确模板/hash、父源码hash：当前无法计算，正式实施前补，不能填伪值。

不另注册输入驻留 Action：已有 cache 机制保留，装入次数变化来自重新分配任务，不把同一删读收益重复记账。

## 2. 所有权和布局

候选任务 \(t=cQ+j\)：

\[
Y[c,\ j(256/Q):(j+1)(256/Q)]
\]

由唯一 owner 写入。任务集合互斥，联集恰为全部2048输出。

- X保持外部NCDHW，通道起点 `c*4096`；
- Y保持通道平面连续，每平面256元素；
- geometry保持8组偏移、8组权重的SoA；
- 邻域偏移是**字节**，合法值及零哨兵不变；
- 每输出独立，仅允许跨输出并行，不拆分8邻居累加。

## 3. Workspace与同步

geometry有效区仍为16384B；不删除或缩小未知框架保留区。几何生产者完成后消费者才可启动。当前完整启动序列未展示，C3必须保留已有阶段依赖，不能用核内 `PIPE_ALL` 代替跨核发布。

核内保持现有保守完成关系：

1. cache初始化完成后才能DMA覆盖；
2. 通道DMA完成、零哨兵写入完成后才能检测/Gather；
3. 检测归还 idx/acc 临时租约后，才能搬入真实索引和初始化acc；
4. index/weight DMA完成后才能消费；
5. Gather完成后才能Mul/Add或软件FMA；
6. 输出就绪后才能MTE3；
7. MTE3读完acc、所有Gather读完cache后才能覆盖对应区。

本轮**不附带缩屏障或双缓冲**，也不声称已有有效重叠。

## 4. P/KEEP依据

没有提供可引用的完整父计划，故不能标 `P_KEEP`。本轮为 **P_CHANGE**：

- 提取已有 cache、geometry、数值与同步计划；
- 实际改变任务到核映射及物理tile；
- 不把“提取旧计划”本身统计为并行优化。

C3可调自由度仅为冻结任务内的合法 API 参数和已列缓冲；改变Q、跨核协议、geometry布局、软件数值路径或派发域必须返回C2。

# 五、C3准确实施步骤及正文实际影响

## 1. 实施顺序

1. **接齐完整父工程。** 确认实际Weighted入口、包含`geometryLength`的真实tiling结构、Host启动和workspace序列；不能把早期47行头文件冒充完整Weighted ABI。
2. **仅以元数据限定候选域：** float、N=1/C=8/D=H=W=16/S=256、bilinear/zeros/alignCorners=false及NCDHW。其余元数据保持原通用fallback。不得加入x范围或grid分布条件。
3. Host建立Q对应任务表，按实际AIV核数商余分配；没有核数来源时不得写死设备核数。
4. `Init`分别分配tile256或128的五类缓冲；cache仍16640B，保留检测所需idx/acc容量。
5. 用任务循环替代原`linear=blockIdx*blockLength`区间循环；每任务显式取得通道和空间区间，同核同通道保留cache。
6. 几何搬入保持原8行形式：
   \[
   blockLen=4\,count,\quad srcStride=4(G-count)
   \]
   \[
   dstStride=(4\,tile-\operatorname{AlignUp}(4\,count,32))/32
   \]
   GM stride是字节，UB stride是32B块。
7. a的完整tile无需索引全区初始化；b仍初始化8×128索引为零哨兵，再覆盖每行64个有效索引。
8. 保持两组Gather、`GridNeedsFma32`及`GridApplyWeightedFour`原分支和k顺序；b的软件函数不能删改。
9. 仅写有效`count*4`字节，保留完成后复用。
10. 后续有权限时再做审查、构建、全输出oracle和完整序列计时；本次不执行这些步骤。

## 2. P/O正文如何真正影响了方案

- **`planning.indexing.coordinate_neighborhood`：完整采用条件化骨架。**  
  G/B/H绑定源码坐标、padding、索引和权重；F绑定实际两种舍入路径。它促使方案按`[c,p]`矩形独占输出，但不授权重写插值数值实现。

- **`planning.elementwise.continuous`：只参考所有权原则。**  
  采用商余分任务及唯一写回；采样依赖间接邻域，不满足“同下标逐元素输入”的完整适用条件，因此不冒充完整命中。

- **`implementation.tiling-tail.valid-length`、`memory-transfer.strided-pad`：实际用于DMA参数。**  
  明确count、tile和每行物理跨度不同，形成上面的双端stride公式；不能把tile128的padding写入GM。

- **`implementation.buffer-lifetime.reuse`、`precision-boundaries.bounds`：用于容量与租约审计。**  
  不能因检测时acc“还没累计”就缩至64元素；idx/acc视图是已有物理区租约，不另计一份，也不能提前覆盖。

- **`precision-boundaries.numeric`：直接排除错误捷径。**  
  b不能因大值未采样而关闭软件FMA；两组之间acc必须延续，不能重结合8邻居。

- **`pipeline-sync.pipeline`及fallback：保留浅流水。**  
  新方案短任务不自动值得加槽；保留真实完成边，不以barrier数量作为收益。

- **`action.vectorize_scalar_loop`正文：限制而非强行选用。**  
  a已是Vector数据计算；b缺精确整数向量FMA实现，不能仅凭标量循环存在就提交替换。
