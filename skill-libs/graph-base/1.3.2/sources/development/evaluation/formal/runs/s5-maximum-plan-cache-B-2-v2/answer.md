## 结论与交付状态

本轮选择一个**连续搬运合并方案**，a、b 都采用：

> 每核把相邻两个原始 4096 元素 tile 合成一个至多 8192 元素的搬运批次；两路输入各搬入一次、输出搬出一次，但计算仍按至多 4096 元素调用原来的 `AscendC::Max`。保持核数、每核区间、数学语义、输出所有权和 queue 管理方式不变。

这样减少的是 **DMA、queue 管理及外层批次控制次数**，不减少必要输入输出字节，也不声称减少 Max 的有效计算量。它比“直接把 Max count 改为 8192”更保守：不需要额外假定该 Max 重载的新 count 范围。

最有竞争力的替代是：**4096 元素不变，两路输入各两物理槽、输出一槽，显式安排下一 tile 预取**。下文完整比较两者。

本次仅完成纸面决策与条件化 C2/C3 交接。没有执行工具、修改源码、计算 hash、编译或上板；不生成虚假的路由回执、正确性结果或性能数字。当前状态为 **`conditional_plan / not_measured`**，不是 C3 completed。

# 一、当前实现的共同事实

### 1. 实际路径和数学依赖

当前指定路径是 `KernelMaximumSame<float>`，不是 `MaximumScalar<float>`：

- `maximum_kernel.asc:178` 选择 float；
- `DispatchMaximum<float>` 的 sameShape 分支位于 `165–166`；
- 每个有效元素执行 `AscendC::Max(out,a,b,count)`，位于 `61`；
- bf16/int8 的转换及临时区分支均不执行。

数学目标为：

\[
y[i]=\max(x_1[i],x_2[i]),\quad 0\le i<N,\quad N=1048576.
\]

没有归约、广播、跨元素递推或跨核合并。输入有限且非 NaN；本方案仍保留原 Max 原语及参数顺序，因此不主动改变相等值、符号零或次正规数处理。

核 \(c\) 的区间由源码 `12–17` 给出：

\[
B_c=c\cdot blockLength,\qquad
L_c=\min(blockLength,\max(N-B_c,0)).
\]

题设确认这些输出区间互斥、覆盖完整，尾块也完整处理。不能从这项事实推断硬件核数或输入输出别名合同。

### 2. 当前核内数据流和完成边

每个原 tile：

```text
GM x1/x2 → MTE2 → 两个 VECIN queue 槽
                     ↓ 输入就绪
                Vector Max
                     ↓ 输出就绪
GM y       ← MTE3 ← 一个 VECOUT queue 槽
```

三个位置都在 UB，不是三个物理存储层级。

源码 `35–66` 每 tile 执行：

- 2 次 GM→UB `DataCopyPad`；
- 1 次 Max；
- 1 次 UB→GM `DataCopyPad`；
- 3 次 Alloc、3 次 EnQue、3 次 DeQue、3 次 Free，共 **12 次源码级 queue 管理调用**。

queue 协议承担：

1. 输入 DMA 完成后才能计算；
2. Vector 最后读完输入后才能覆盖输入槽；
3. Vector 写完输出后才能搬出；
4. MTE3 最后读完输出后才能覆盖输出槽。

没有手写 event 不等于没有同步；当前单槽及发射顺序也不能证明硬件完全串行。尤其原实现可能已有“前一输出搬出与下一输入搬入”的重叠。

### 3. 工作量和资源账

令原计算粒度 \(T=4096\)，有效核集合为 \(A\)：

\[
K_c=\left\lceil L_c/T\right\rceil,\qquad K=\sum_{c\in A}K_c.
\]

不能只因 \(N/T=256\) 就断言全调用恰好 256 个 tile；分核边界若不与 T 对齐，各核尾片会影响 K。

当前有效逻辑流量：

| 对象 | 字节数 |
|---|---:|
| x1 读取 | 4,194,304 B |
| x2 读取 | 4,194,304 B |
| y 写出 | 4,194,304 B |
| Maximum 合计 | **12,582,912 B，即 12 MiB** |

这是逻辑有效请求量，不是实测 HBM 字节。

当前 float 数据区：

\[
3\,AlignUp(4T,32)=49152\text{ B}=48\text{ KiB}.
\]

没有当前 float 分支的显式转换 scratch。框架、编译器及 API 其他实际资源仍须由目标构建确认，不能把 48 KiB 当作完整可用 UB 证明。

# 二、所选方案及最强替代的完整工作变化

## 方案 S：两个原 tile 合成一个搬运批次

新搬运容量 \(U=2T=8192\) 元素。每批次有效量 \(v\le U\)：

1. 搬入 x1 的 v 个元素；
2. 搬入 x2 的 v 个元素；
3. 对前 `min(v,T)` 个元素执行原 Max；
4. 仅当 \(v>T\)，对偏移 T 的剩余 `v-T` 个元素再执行原 Max；
5. 整批有效输出一次写回。

合批只在**同一 owner 的连续区间内**进行，不跨核边界。

定义：

\[
M_c=\left\lceil L_c/(2T)\right\rceil
    =\left\lceil K_c/2\right\rceil,\qquad M=\sum_cM_c.
\]

因此：

| 项目 | 当前 | 方案 S |
|---|---:|---:|
| 输入 DMA 调用 | \(2K\) | \(2M\) |
| 输出 DMA 调用 | \(K\) | \(M\) |
| Max 调用 | \(K\) | **仍为 K** |
| queue 管理调用 | \(12K\) | \(12M\) |
| 有效读写字节 | 12 MiB | **不变** |
| 最大显式数据区 | 48 KiB | **96 KiB** |

减少的搬运批次数为：

\[
K-M=\sum_c\lfloor K_c/2\rfloor.
\]

若所有核长度均为 8192 的倍数，则有 \(K=256,M=128\)：DMA 调用从 768 减到 384，queue 管理调用从 3072 减到 1536，Max 仍为 256 次。**这是条件化计数示例，不是对未提供 blockNum 的实际计数断言。**

新增及保留代价：

- UB 数据区增加 49,152 B；
- 第二个原 tile 的输入、第一段结果驻留更久；
- 第一段输出要等第二段结果生成后才能整批搬出；
- 每批最多增加一次第二段判断和局部视图偏移；
- 序言的第一批输入变大；
- 不增加 GM workspace、准备 kernel、输入扫描、Cast 或整批清零；
- 不减少算法必要字节，不保证减少编译后 Max 指令数。

### 为什么选它

当前已经是连续、批量 Vector 路径，没有百万次标量解码可消除。方案 S 的价值依据是**确切减少批次管理及搬运发射**，不是把 16 KiB 主块武断归为“小包热点”。

相对于下面的流水替代，它用更多 UB 换取更少的发射和 queue 管理，而不是只尝试隐藏相同工作。单个 Max 的计算链很短，保留其原粒度、先检验管理与发射摊销，是本轮合理的有界试验；这不证明它必胜。

## 最强替代 P：双输入槽预取，输出仍单槽

参数保持 T=4096：

- x1、x2 各两物理槽；
- y 一物理槽；
- 仍用 queue 自动同步；
- 当前输入 DeQue 后、当前 Max 前，向另一输入槽发下一 tile 的 CopyIn。

完整变化：

| 项目 | 替代 P |
|---|---:|
| 输入/输出 DMA | 仍 \(3K\) 次 |
| Max | 仍 K 次 |
| queue 管理 | 基本仍 \(12K\) 次 |
| 有效流量 | 仍 12 MiB |
| 显式数据区 | \(5AlignUp(4T,32)=81920\) B，即 **80 KiB** |
| workspace | 0 |

它新增独立输入槽及预取控制，消除“下一 tile 的 MTE2 必须复用当前输入地址”的限制，创造 **MTE2(next) 与 V(current)** 的合法重叠窗口。输出单槽仍保留 MTE3→V 的复用约束。

准确的 queue 排程为：

1. 序言只 CopyIn tile 0；
2. DeQue 当前两输入；
3. 若 next 存在，分配另一输入槽、CopyIn next、EnQue next；
4. 分配输出、执行当前 Max；
5. 按原协议发布输出、归还当前输入、搬出并归还输出；
6. 下一轮再 DeQue next。

这样每条输入 queue 最多只有一个尚未 DeQue 的元素，**depth=1 仍可使用两物理块**；不能写成两次连续 EnQue 后才 DeQue。

它的竞争优势是比 S 少用 16 KiB，并可能缩短依赖链；代价是没有减少必要调用，短 owner 或单 tile 没有稳态预取收益。若后续发现 S 的大包首段延迟明显，或 P 的新增重叠足以覆盖管理成本，应重开比较。

# 三、子例 a：输出只做一次 D2H

## 当前实际路径、依赖和关键事实

Maximum 内部完全沿用第一节的 float sameShape 路径。y 的设备生产完成后，D2H 读取完整 4 MiB 输出；没有后继设备 kernel 读取 y。

因此：

- Maximum 的 12 MiB 逻辑请求仍全部必要；
- D2H 的 4 MiB 传输不能被本方案删除；
- 不能把 D2H 字节直接与 MTE/HBM 计数混为同一测量口径；
- 没有输入重读或跨调用输入复用，`reuse_input_tiles` 没有删读对象。

## 主要方案与替代选择

a 选择 S，工作变化、容量和覆盖均按第二节公式。

第一段写回变晚不会违反题设中的 D2H 顺序：D2H 本来就必须等待整个生产 kernel 完成。它仍可能影响生产 kernel 自身尾部时长和输出缓存轨迹，不能因此当作免费代价。

最强结构替代为 P。另一个值得保留的机会是缓存策略：

- x1/x2 是合计 8 MiB 的一次性流，可比较 NORMAL 与 DISABLE；
- y 没有后继设备复用，也可作为输出 DISABLE 的**条件候选**；
- 但 y 的实际搬出指令是否兑现 hint、SDK 支持及 D2H 一致性合同须核验，不能由 Add 输入样例直接推出写出行为。

本轮不把缓存修改夹带到 S 中：它不减少逻辑请求或调用数，实际替换成本未知；选定 S 已有独立、可复算的工作减少预测。这里不是因缺实测否决缓存试验，而是将它保留为未实施的竞争路线。

## Action 实例

纸面实例 **`A_a_merge2`**：

- 注册意图：`action.coalesce_contiguous_transfers`；
- parent：输入中的原始 `maximum_kernel.asc` 和 `maximum_tiling.h`；
- workload：a，sameShape、float32、连续、N=1048576；
- target：`KernelMaximumSame<float>` 内同 owner 的 x1/x2/y 连续搬运批次；
- stage：CopyIn、原 Max 计算衔接、CopyOut；
- 参数：原计算粒度 4096 元素，搬运容量至多 8192 元素。

状态：

- `inner_loop_copy`：源码事实成立；
- 地址相邻性、原 Max 数值路径：可以按上述区间证明；
- capacity：**待当前可用 UB 与完整分配账确认**；
- 输入输出别名：**缺调用合同**，见 C2 门禁；
- 不是带宽饱和或 setup 主导的确认结论。

Action 正文允许在缺少 setup 实测时按合法相邻区间提出试验，故不把性能 unknown 当作拒绝理由。

# 四、子例 b：输出随即被设备 kernel 顺序完整读取

## 当前实际路径、依赖和关键事实

Maximum 的内部路径与 a 相同，但 y 在下一设备 kernel 中再读一次：

\[
\text{Maximum 必要请求}=12\text{ MiB},\quad
\text{后继对 y 的逻辑读取}=4\text{ MiB}.
\]

仅就已知数据边，合计为 16 MiB；消费者的其他输入、计算、输出均未知，不补造。

“完整顺序读取”不证明消费者可以融合：其数学、核角色、owner、布局和全部消费者合同都未提供。

## 主要方案与替代选择

b 也选择 S。与 a 相同：

- 减少 \(3(K-M)\) 次 DMA 和 \(12(K-M)\) 次 queue 管理调用；
- Max 有效计算与调用数不变；
- Maximum 的输入输出逻辑字节不变；
- 后继 y 的 4 MiB 读取仍保留。

与 a 不同的成本和策略判断：

1. **y 保持 NORMAL。** 它确有紧邻设备消费者，不能仅因生产者只写一次就统一 bypass。
2. S 可能改变输出写入时序以及消费者启动时的缓存内容；NORMAL 只保留命中机会，不保证命中。
3. 题设是后继 kernel 消费，不是生产者与消费者按 tile 并发，故 S 不需要新增跨 kernel 的 tile-ready 协议。
4. 评价时必须同时看 Maximum 和“Maximum→消费者”链。生产者变快、消费者变慢时，不能只报前者。

最强结构替代仍为 P，80 KiB、相同请求和调用数，检验预取窗口。缓存替代在 b 应收窄为**只比较 x1/x2 的一次性输入策略，保留 y NORMAL**。相较 a，它少了输出 bypass 的候选范围，也少了一项损害后继复用的风险。

## Action 实例

纸面实例 **`A_b_merge2`** 使用相同注册 Action 和参数，parent、target、stage 与 a 相同，但 workload 和输出生命周期绑定 b。

不能沿用 a 的“无后继设备读”事实；b 的后继读取必须进入共同计划和未来链级比较。容量、别名及目标 SDK 门禁与 a 分别绑定，不能借 a 的通过状态代填。

# 五、其他主要机会为何未采用

- **静态 buffer/event 管理简化**：确有比较价值。单槽三块数据仍约 48 KiB，可把每 tile 12 次 queue 调用改成显式完成边。但它不是“删除同步”：捆绑两输入时，四类逻辑边每 tile 约需 8 次 Set/Wait，另有初始化、排空及事件管理。编译器内联后净工作未知。它不消除 DMA 发射，故本轮优先检验 S；不能据 API 数量直接判快。
- **字段缓存**：`tileElements` 在循环中重复出现，但只是每 tile 控制，不是每元素解码；编译器是否已外提未知。不将它因容易等价而置于主要搬运机会之前。
- **Compare+Select 替换 Max**：没有依据。当前实际路径不是标量三元选择；替换反而增加 predicate、比较、Select 及其临时区。所给正文还明确 A3 Compare 的整 256B 比较限制及 Select 模式临时资源，不能机械套用。
- **输入驻留、派生结果复用**：当前没有重复消费同一原输入的源码对象，也没有重复生成的数值派生表。
- **重分核、尾优化、广播重组**：题设确认均匀互斥连续分区，尾部已有有效 count 路径；当前没有广播。
- **带宽饱和、bank 冲突、spill**：没有相应目标证据，不作确认诊断，也不据此添加 padding 或新槽。

# 六、统一 C2 共同计划

## 1. 计划身份与 KEEP 判断

建立纸面后继计划 **`p_same_merge2`**，不是直接宣称 `P_KEEP`。

旧 `p_same` 可复用：

- float32 sameShape 范围；
- 每核连续区间唯一写者；
- workspace=0；
- 原单槽 queue 所有权方式。

但它只声明 4096 元素资源，没有许可 8192 搬运容量及相应更长租约。因此本轮为 **P_CHANGE：扩大搬运批次及资源合同**，不是并行分核优化。

不得借本轮计划授权替代 P 的双输入槽，或静态 event 方法；采用它们须形成相应计划后继。

## 2. 所有权、布局与数值

- 保留当前 blockNum、blockLength、核起点和核尾；
- 不因把 tile 改大而把启动核数减半；
- GM 和 UB 都是连续 float 布局；
- 输入两区、输出一区独立分配，不进行 UB alias；
- 每个原 4096 计算片的输入映射和 Max 参数顺序保持；
- 输出只写有效 v 个元素，不写对齐 dummy。

输入输出 GM 别名必须在实施前闭合：

- 无别名可采用；
- 精确同址逐元素 in-place 仅在原接口允许、且读完本批两输入后再写的合同下采用；
- 部分重叠、跨核读写相互影响不能默认安全。未证明时不进入新路径，也不能声称旧路径自动解决这类合法域。

## 3. Workspace、同步和容量

\[
workspace=0.
\]

最大搬运批次数据区：

\[
B_{\rm data}=3\,AlignUp(4U,32),\quad U=8192,
\]
\[
B_{\rm data}=98304\text{ B}.
\]

实施要求：

\[
98304+B_{\rm other}+B_{\rm API/reserved}
\le B_{\rm available}.
\]

不填入未提供的 910C 可用 UB 常数。容量不足时保留原 4096 路径；不能删输出槽、非法原地重叠或降精度凑容量。

同步继续使用一个 TPipe 的三条单槽 queue：

- 两次输入 DMA 都完成后才执行 Max；
- 两段 Max 都完成其读写后，整批输出才可被 MTE3 消费；
- 输入归还与输出归还继续服从 queue 的最后异步消费者关系；
- 不增加手写事件，不与 queue 的事件池另建一套无合同的管理。

## 4. 覆盖与 fallback

优化覆盖为 sameShape float32 中存在相邻原 tile 的 owner；单原 tile owner 没有合批收益。a/b 共用同一实现，不按子例名字分派。

沿现有 `dtype/sameShape` 条件在 `maximum_kernel` 内接线，**不为此新增 Tiling Key 或外部 entry**。8192 是本轮候选参数，不是已测最优阈值。

其他 dtype、broadcast、int64 保留原实现，不能用 `p_same_merge2` 声称它们已获完整计划证明。尤其原 half 非同形分支无形状判别就进入 last-axis 专用类；所给 tiling 接受的广播域更广。其通用 fallback 覆盖需要独立核对，必要时授权补充“专用形态判别→一般标量广播”的接线。**本轮不把未验证的原 fallback 宣称为全域正确，也不夹带这项独立修复。**

# 七、C3 准确实施步骤与知识正文的实际影响

以下是交接步骤，未实际执行。

1. **冻结父源码和计划身份**  
   后续生成真实 source/template/plan hash。本答复不伪造 hash 或正式 router 结果。

2. **补齐硬门禁**  
   确认目标 SDK 的 A3 DataCopyPad 重载、完整 UB 预算、GM 别名合同。性能计数缺失不属于这一步的安全阻塞。

3. **只为 float sameShape 建合批实现**  
   复用原分核公式；容量满足时使用至多 8192 搬运容量，其他分支仍用原参数。

4. **Init 一次分配三条单槽 queue**  
   每槽最大 32768 B，不把分配放入循环，不新增无用清零。

5. **Process 按有效批次执行**  
   对每批 v：
   - `blockCount=1`；
   - `blockLen=v*sizeof(float)`，单位为字节；
   - 两路 DataCopyPad，EnQue/DeQue；
   - 第一段 Max count=`min(v,4096)`；
   - 仅在 v>4096 时构造偏移 4096 的局部视图并执行第二段；
   - 发布输出，按原协议归还输入；
   - 一次 DataCopyPad 写出 v 个有效元素，再归还输出。

6. **不改缓存策略**  
   a/b 本候选都保留原默认模式；b 明确不得夹带输出 DISABLE。缓存试验另建选择记录。

7. **核对静态变化是否兑现**  
   必须得到 \(3M\) 次搬运、K 次 Max、约 \(12M\) 次 queue 管理及正确资源账；若实现反而增加整片初始化、复制或全流水 barrier，回传 C1 重比，不能继续沿用旧收益理由。

### P/O 正文怎样改变了本方案

| 正文 | 本轮实际影响 |
|---|---|
| `planning.elementwise.continuous` | 保留唯一连续 owner；把 tile 与核数分开，禁止因合批顺便减少核数；按真实物理分配计容量。 |
| `implementation.memory-transfer.coalesce` | 只合并同 owner、首尾相接的区间；输出等待两段都生成后才合并写回；有效字节保持。 |
| `implementation.tiling-tail.valid-length`、`precision-boundaries.bounds` | 有效 v、UB 容量、API 字节长度分别计数；保留短尾，不向上扩大 GM 读取。 |
| `implementation.pipeline-sync.pipeline` | 强制把双输入槽作为竞争方案分析，而非认为“已有 queue 就已流水”；本轮仍保持原单槽协议。 |
| `implementation.pipeline-sync.vector-static-lease` | 静态管理替代必须补四类完成边及首尾 token 闭环，不能按少 queue 调用宣称加速。 |
| `implementation.memory-transfer.cache-hint` | 将 a 的无设备复用输出与 b 的紧邻消费者输出区分；不使用预留 READ/WRITE 参数，不采用 PERSISTENT。 |
| `implementation.vector-api.batch`、`numeric` | 不从通用 count 说明推断新 Max count 合法；保留原 4096 Max 粒度，不改数值原语。 |

# 八、后继可复用摘要与待验证事项

## 当前状态

- 保留实现仍是原始源码；没有已修改候选或已验证探索父本。
- 本轮选择：a/b 均为同 owner 两原 tile 搬运合批，计算仍使用原 Max 粒度。

- 正确性、构建、性能均未验证；`formal_admission=not_evaluated`。

## 已分析路线

| 路线 | 静态预测 | 主要代价或重开条件 |
|---|---|---|
| 已选合批 S | DMA 和 queue 批次减少，Max 和有效流量不变 | 额外 48 KiB、首段延迟；调用减少若未体现到生成物，价值减弱 |
| 双输入槽 P | 新增 MTE2(next)/V(current) 窗口 | 80 KiB、调用不减；若 S 首包/尾部代价大，重开 |
| 静态管理 | 改变管理表达，不取消完成边 | event/分支/drain 成本及编译后净变化未知 |
| Cache hint | a 可分析输入及无后继设备复用输出；b 优先仅输入 | 实际指令兑现、替换及链级影响待验证 |
| b 链融合 | 可能有中间写读/launch 机会 | 消费者源码与完整合同缺失，当前不能实施 |

## 待验证：按影响分类

**实施前硬条件**

- 实际可用 UB、隐含资源与 96 KiB 数据区的总容量；
- 目标 SDK DataCopyPad 参数及位置支持；
- 输入输出别名及异步生命周期；
- 全域 fallback，尤其 half 一般广播的实际覆盖。

**后续正确性与结构验证**

- 每核长度为 0、1、4096±1、8192±1及多批次；
- 奇数原 tile 数、最后核、非零核起点、重复调用；
- 有限极值、相等值、±0、次正规数；
- 完整输出与原 oracle；未变 dtype/fallback 的回归覆盖。

**性能预测验证**

- 生成物是否确实减少搬运和管理，而没有新增等量工作；
- S 的首包等待及更长输出驻留是否抵消发射摊销；
- a 按固定口径比较 Maximum 与必要 D2H 范围；
- b 同时比较 Maximum、消费者及完整链，不能只选生产者时间；
- 如改试缓存，按对象核对实际 hint、HBM/L2 与 Task，不能用整体低命中率判错。

这些验证结果可能支持、削弱或无法回答当前预测；在没有结果前，既不宣称加速，也不因缺实测把这项静态可行试验统一否决。
