# 每轮实施一个完整优化方案

适用：runtime 0.8.1 的 `aprof.action-decision/v3`、`aprof.handoff/v4`。当前知识为 D v0007、P v0004、O v0007 和 routing v0006；历史决策与交接按各自版本回放。完整方案不是新的 Problem 或 Action 分类，也不是预选 P/O 组合。

## 方案怎样影响选择

先用代码理解和完整 workload 的工作路径比较机会，再把能完成预期变换的必要步骤组织成方案。方案回答：共同目标是什么、改变哪些对象和域、各步骤怎样衔接、减少/新增/保留什么工作、与最强可行替代相比为什么值得本轮尝试。不要先选容易实施的 Action，再为它补一张方案表。

单个注册 Action 能准确表达意图时直接使用，其实现可以包含 Host/Kernel、分块、搬运、转换、计算、尾块和同步等配套修改。多个必要 Action 有独立目标或约束时保留各自实例，并说明组合理由与依赖；不因多个 recipe、多个文件或多种 API 就拆成多个 Action。没有 Action 数、recipe 数、代码行数或严格单因素门槛。

比较完整方案时，使用同一父实现和 workload：

- 共享读取、解码或中间值只计算一次减少量；两个成员消除同一工作不能将收益相加。已有计划、原工作和残余工作与方案步骤相连。
- 内存按同时存活集合及物理别名核算，临时空间、padding、转换、初始化、事件和额外搬运全部计入。分别满足成员的单独预算不能证明共同计划可实施。
- 记录影响域与保持原样的域，区分“完整正确性覆盖”与“该方案实际优化覆盖”。不以覆盖 case 更多自动胜出。
- 有依赖的步骤可以同轮实施。无依赖的方向可以分开比较，避免无法解释回归；这不是默认消融要求。

性能未知允许来源知识支持的假设试验；实施合法性仍逐项满足。没有硬件数据不妨碍形成完整方案，也不能据逻辑工作减少编造时间占比或加速比。

影响选择的数据相关覆盖、准备工作收支和正确性修复后的重比，统一遵循 [Action 选择规则](action-selection.md#数据相关路径必须进入机会比较)。使用已有联合分析和选择理由记录它们怎样影响决定，不再另填成本表。仅把新增字节和减少调用并列，或仅说“频繁触发应计入”，不表示已经比较。

## 从方案到共同计划

C1 选方案及成员实例，提出条件化 P/O 请求，不提前锁定具体叶。C2 逐成员调用 P router，在共同计划里统一算法、任务/输出所有权、通路、布局、同步、workspace、容量、分派域和许可自由度。C3 再逐成员调用 O router，记录实际采用的方法、参数与源码变化。

正式路径的唯一选择来自 C1 `decision_ref` 与非空 `scheme_id/scheme_hash`。文字说明解释同一选择，不能与 JSON 分别维护两份已选方案。局部 Action ready、P/O 文档命中和共同计划/全部成员实际选择完成分别报告；不能以研究授权、文字计划或局部路由代替完整交接。实例化临时 Problem 不要求补造图边，但新独立 Action 意图仍须先注册。

成员的路由命中不能直接取并集：逐项检查是否使用相同对象、不同目标是否共享存储、数值/布局要求是否兼容、依赖顺序是否实现、共同峰值容量是否合法。路由提示不能产生 facts，也不能改写 platform/family/dtype/features。

前置步骤可以承诺后续步骤所需的保证条件，例如“该输入在第二消费者结束前不被覆盖”。把它写成明确依赖：谁产生、适用什么对象/范围、何时可用、由哪段实际源码兑现。C2 可以据此做条件分析；C3 核实最终源码实现这些保证后，才完成联合交接。计划中的保证不是现有源码事实，也不替代每个 Action 的原实施条件；无需逐步构建和测量中间候选。

P_KEEP 引用覆盖所有成员及目标的完整有效共同计划和许可自由度，不能拼接互不兼容的旧计划。成员 O_KEEP 表示不追加对应局部优化；P 改变时仍须实现新计划。仅当 P_KEEP 且所有成员 O_KEEP 时为 NOOP。缺文档、空命中、fallback 或 unknown 均不转换为 KEEP。

超过许可自由度的算法、owner、归并结构、同步拓扑、workspace 所有权、融合边界、通路或 dispatch 域变化返回 C2。无可用注册意图的独立变换保留提案缺口，不能借联合方案放宽已有 Action 或夹带未注册 Action。

## 联合结果怎样解释

一次候选的构建、完整正确性和有效计时评价整个实际方案。联合方案即使没有消融，也可以得到整体 accepted/rejected/inconclusive；限制的是把收益归因给某个成员或证明某个机制。

后继轮次先读[跨轮摘要](optimization-history.md)，按需展开方案、patch 和结果：检查预期工作是否实现、哪些域受益或退化、哪些代价出现、哪些预测仍未被回答，再比较扩展原方案、调整参数和其他路线。同一 Action 可继续，不强制换意图；更换 Action 也要有同样依据。正确性修复、无效计时和性能回归不能混为一种反馈。

## 纸面例一：一个 Action 足够的连续搬运方案

**原实现与目标。** 每核独占若干输出行；每行 E 个连续元素被拆为逐元素读取和写回，中间计算及精度顺序保持原样。目标是将合法连续区间合并搬运，而非宣称 Vector 或流水已经优化。

用 `action.coalesce_contiguous_transfers` 的一个实例描述对应输入/输出及当前父本。C2 确认 owner、行边界和允许的 tile 范围 T；C3 在同一方案里实现 Host 容量参数、UB 暂存、连续块搬运、原计算、有效尾块和所需依赖。不能为了每个配套步骤另开一轮，也不能因为修改了多个文件就添加 Action。

R 行、元素 s 字节时，逻辑传输字节不一定减少；调用粒度由逐元素变为约 `R × ceil(E/T)` 个片段，同时增加暂存与同步。T 的单位为元素，容量计算用字节并包含输入、输出和实际 scratch 的同时存活集合。API 的长度单位、尾块支持及地址对齐由实际重载确认，不能用上述调用模型替代 API 合法性。

替代包括保持原实现、仅合并确实连续的子区间、调整任务使其拥有更长区间。短行是否值得暂存仍是性能预测。若 batching 还需要改 owner 或访问顺序，先回 C2；不增加 case 特判或承诺加速比。

## 纸面例二：有依赖的两个 Action 共享容量

**原实现与目标。** 一个任务分阶段消费同一原输入块 X；X 在两次消费之间不变，但原实现重复读取。阶段临时值 U1、U2 的生命周期严格不交叠，原实现却分别分配。目标是在保持任务所有权和数值语义的前提下，为 X 的完整消费窗口保留空间。

如果只是驻留 recipe 的内部缓冲安排，一个 `action.reuse_input_tiles` 实例足够。本例假设临时存储复用本身也需要独立说明对象、生命周期和覆盖条件，因此登记两个实例：A1=`action.reuse_disjoint_onchip_buffers`，A2=`action.reuse_input_tiles`。A1 证明并实现 U1/U2 的物理存储复用；A2 依赖该布局腾出的空间，在最后消费者结束前保存 X。不能把派生临时值的复用当成原输入复用。

设 X 大小为 B 字节，两个临时值所需字节为 U1、U2，其余同时存活集合为 L 字节。仅在实际对齐、物理位置和 API 约束允许共享时，候选需求可写为 `B + max(U1, U2) + L`，而不是将两个独立方案的节省量或峰值相加。实际分配的对齐和 scratch 另计；容量边界是该同时存活集合不超过当前可用空间。

C2 对两实例分别路由，形成共同布局与释放/覆盖顺序。A1 的“U1 已不再被使用且共享区可供 U2 覆盖”与 A2 的“X 在两个消费者间保持原值”分别绑定对象和源码，不相互替代。C3 一次实现最终候选，核实这些保证，不要求测量只完成 A1 的中间版本。

预测是减少 X 的重复读取；代价包括更长驻留、较小可选 tile 和依赖维护。替代是保持分配而缩小 X tile，或维持重复读取以保留更大并行粒度。若最终发生 spill、tile 变小或同步增加，后继比较整个方案，而不是仅凭“少读一次”认定值得继续。本文没有设备实验或硬件收益结论。
