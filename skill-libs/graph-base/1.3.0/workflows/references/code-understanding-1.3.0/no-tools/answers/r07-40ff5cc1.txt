## 1. 输入输出与数值语义

这是逐元素指数算子，没有归约、广播或元素间依赖。输入、输出为相同 dtype 的一维连续 ND 数组；host 按原始二进制读写，不做文本解析或类型转换。支持 `float16 / float32 / bfloat16`，分别占 2/4/2 字节（`source/op_host/exp.asc:20–24,38–43,56–63`）。

`ComputeExpTiling` 将参数转换为两个 FP32 标量（`source/op_kernel/exp_tiling.h:27–28`）：

\[
L=\begin{cases}\log(base),&base>0\\1,&base\le0\end{cases},\quad
m=scale\cdot L,\quad s=shift\cdot L.
\]

device 逐元素执行 `Exp(Adds(Muls(x,m),s))`。因此理想实数语义为：
- `base>0`：\(y=base^{scale\cdot x+shift}\)；
- `base<=0`：\(y=e^{scale\cdot x+shift}\)，负数和零并不是指数底数；默认 `base=-1` 也走此路径。

实际语义是 host 的 FP32 参数计算，加上 device 分步 FP32 乘、加、Exp 和输出转换，不能等同于无限精度幂运算，也没有源码证据表明乘加会融合。

本次 `base=2, scale=0.5, shift=-1`，所以：
- `multiplier≈0.34657359`，`shift≈-0.69314718`；
- 理想函数为 \(2^{x/2-1}\)；
- 输入 `-2、0、2` 的理想输出分别为 `0.25、0.5、1`。这些值均可由 BF16 表示，但实际输出仍由设备 Exp 近似和转换舍入决定。

## 2. host 路径与实际分核

host 初始化 ACL、选择设备，查询 `ACL_DEV_ATTR_VECTOR_CORE_NUM`，计算 tiling；随后分配 host/device 输入输出及 device tiling，执行 H2D、kernel 启动、流同步、D2H、写文件（`exp.asc:45–68`）。本次每个输入/输出缓冲区均为：

\[
25019\times2=50038\text{ 字节}
\]

输入与输出是独立分配，不是原地计算。kernel 的三个实参只有输入、输出和 tiling 地址，没有额外全局工作区。

按 `exp_tiling.h:22–25`：
- `useful=ceil(25019/4096)=7`；
- 查询核数固定为 3，故 `blockNum=min(3,7)=3`；
- `blockLength=ceil(25019/3)=8340` 个元素；
- `tileElements=4096` 个元素。

启动配置是 `exp_kernel<<<3,nullptr,stream>>>`。入口按 tiling 的 dtype 实际选择 `KernelExp<bfloat16_t>`；FP32、FP16 分别选择 `float`、`half` 模板（`exp_kernel.asc:85–93`）。源码没有另一套按规模选择的 kernel。

`Init` 以 `blockIdx*blockLength` 求元素偏移，再截断到剩余长度（`exp_kernel.asc:9–15`）：

| block | 全局元素区间，左闭右开 | 实际元素数 | BF16 起始字节偏移 |
|---|---|---:|---:|
| 0 | `[0,8340)` | 8340 | 0 |
| 1 | `[8340,16680)` | 8340 | 16680 |
| 2 | `[16680,25019)` | 8339 | 33360 |

因此三块无重叠、无遗漏；末块仅比前两块少一个元素。这里的 3 是逻辑启动块数及题面查询值，不能据此认定整片 910C 只有三个物理向量核。

## 3. tile、尾块与搬运地址

每个 block 在 `Process` 内按 `off+=4096` 循环，顺序调用 `CopyIn→Compute→CopyOut`（`exp_kernel.asc:26–33`）。这里 `off`、`count` 均以**元素**计数；`DataCopyExtParams.blockLen` 则使用 `count*sizeof(T)`，单位是**字节**。

本次实际循环如下：

| block | 各轮 `count` | 最后一轮全局起始元素 | 最后一轮字节起点 / 长度 |
|---|---|---:|---:|
| 0 | 4096、4096、148 | 8192 | 16384 / 296 |
| 1 | 4096、4096、148 | 16532 | 33064 / 296 |
| 2 | 4096、4096、147 | 24872 | 49744 / 294 |

总计 **9 次 tile 处理，6 个满 tile、3 个尾 tile**；满 tile 每次输入和输出各搬 8192 字节。尾块沿用相同计算分支，仅 `count` 变小，不会按 4096 个元素写回。

`CopyIn/CopyOut` 均用单段 `DataCopyPad`，段间 stride 为零；输入 padding 参数关闭显式左右补值（`exp_kernel.asc:37–42,69–73`）。按该 API 的常规语义，这种扩展搬运可表达非整块长度，尾部只有有效元素参与计算和 GM 写回，不能把可能存在的 UB 对齐空间算作输出。

分核并未进行 32 字节边界取整：第二、第三块 GM 起点相对 32 字节边界分别偏 8、16 字节。源码选择了 `DataCopyPad` 路径，但实际访存事务拆分、对齐代价及尾部指令展开仍取决于 2201 编译实现，不能仅凭调用次数确定。

## 4. 本地存储、计算与依赖

每个 block 都拥有自己的 `TPipe`、输入/输出队列及计算缓冲区（`exp_kernel.asc:16–23,76–82`）。

本次 BF16 满 tile 的显式缓冲区容量为：
- `inQ_`：4096×2 = 8192 字节；
- `outQ_`：8192 字节；
- `fpIn_`、`fpOut_`：各 4096×4 = 16384 字节；
- 合计 **49152 字节，即 48 KiB/块**，不含编译器或运行时附加开销。尾轮仍使用这些固定容量。

两队列的模板深度及 `InitBuffer` 数量均为 **1**，不是双缓冲；两个 FP32 临时区也只有各一份。一次 BF16 tile 的数据链为：

`GM输入 → VECIN队列 → Cast到fpIn → Muls到fpOut → 原位Adds → 原位Exp → Cast到VECOUT队列 → GM输出`

输入上转 FP32 使用 `CAST_NONE`，输出 BF16 使用 `CAST_RINT`，即就近舍入模式（`exp_kernel.asc:55–63`）。FP16 同样上转 FP32计算，但输出转换为 `CAST_NONE`，不能直接将其舍入行为等同于 BF16。FP32 分支没有两次 Cast，也不分配 FP32临时区，直接在输出 tensor 上完成乘、加、Exp；其显式缓冲区合计为 **32 KiB/块**。

队列的 `EnQue/DeQue`、`FreeTensor` 表达搬运与计算之间的数据就绪和复用依赖。源码没有显式跨核同步，各块写入互不相交；也没有多个 tile 交错展开或显式 ping-pong。不同硬件流水线仍可能异步执行，但不能把单槽资源组织解释为已经实现跨 tile 双缓冲重叠。

## 5. 910C 执行含义与证据边界

**平台/API 层面：**目标 device 架构为 `__NPU_ARCH__=2201`。上述本地向量数据位于 UB 类存储路径，GM 与 UB 间搬运通常由输入/输出搬运流水线承担，Cast、标量乘加和 Exp 由向量流水线执行；这里的标量乘数是逐元素向量指令参数，并非 host 逐元素参与。源码没有矩阵乘法、Cube 计算、L1 矩阵复用或核间通信。

**由源码可作的推断：**本次启动三个独立的数据分片任务，各进行三轮处理；每轮包含串联的数值依赖。资源为固定满 tile 容量，即使最后只处理 147/148 个元素，也不缩小分配。三个尾轮均远小于满 tile，但没有测量就不能量化其耗时占比或判定整体瓶颈。

**尚不能确认：**物理核映射、实际并发驻留、编译生成的向量指令和同步事件数量、数据缓存命中、Exp 精度及特殊值行为、各阶段耗时，均需编译产物或运行证据。源码不存在 host `NPU_ARCH` 或 device 架构条件分支，不能混用二者，也没有依据引入 3510 的执行结论。

host 会拒绝未列出的 dtype，但没有额外约束 base 的数学定义域或检查 NaN/Inf；溢出、下溢等结果依赖 FP32 运算与输出格式。以上是静态实现理解，不构成对正确性误差、吞吐或性能瓶颈的测量结论。
