# 矩阵乘实现理解说明

以下源码定位以 `source/baseline/mmad.asc` 为主；variant 行号相同，唯一差异是第209行删除反向等待（`source/VARIANT.patch:3–8`）。数值、地址和次数是静态推导，不代表设备实测。

## 1. 算法、输入输出与实际分派

目标为：
\[
C[m,n]=\sum_{k=0}^{8191}A[m,k]B_{\rm file}[n,k]
\]
A 的 GM 布局是连续 `[M,K]`；B 文件是连续 `[N,K]`，存储逻辑 `[K,N]` 矩阵的转置；C 是连续 `[M,N]`。三者均按 half 解释，不能因 host 用 `sizeof(int16_t)` 计文件大小而理解为整数运算（38–40、597–599行）。每份完整文件为128 MiB。

Mmad 使用 half 操作数、float L0C 累加；每个输出 tile 的首个 K 块设置 `cmatrixInitVal=true`，其余累加，最后 Fixpipe 经 `F322F16` 转成 half 输出（501–541行）。没有 bias、激活或跨核部分和。这里能确定 dtype 和分块累加语义，不能据此保证与任意参考浮点矩阵乘逐位一致。

本次 host `NPU_ARCH=2201` 选择：
- `baseM/baseK/baseN=128/64/256`；
- `singleCoreM/K/N=2048/8192/1536`；
- `stepKa=8, stepKb=4, numBlocks=24`。

这些均是 main 的编译期模板参数，不存在独立运行时 tiling（577–590、626–627行）。`SCENARIO_NUM=1` 只调用 `Process()`；`ProcessL2Cache()` 不执行（562–572行）。device 的 `__NPU_ARCH__=2201` 另行决定 LoadData 重载，不能与 host 宏混用。

host 在 device 0 分配、上传 A/B，启动一次 kernel，流同步后下载并写出 C（601–631行）。没有数值校验；文件读取返回值、ACL 错误也未检查。`data_utils.h:25–61` 不强制文件恰好达到预期大小，因此上述完整输入契约以输入文件有效且足量为前提。

## 2. 分核、循环与尾块

由 `InitComputeParams()`（273–306行），block \(b\)：
- M 分区号 \(u=b\bmod4\)，N 分区号 \(v=\lfloor b/4\rfloor\)；
- 起始行 `2048u`，起始列 `1536v`；
- 每核 M 均为2048；N 在 \(v=0..4\) 时为1536，\(v=5\) 时仅512。

因此20个 block 各计算96个输出 tile，最后4个各计算32个。核内顺序是 **N tile → M tile → K 块**（170–192行）：
- M 循环16次；
- N 循环6次或2次；
- K 循环128次，每次64个归约元素。

虽然最后一组核的 N 分区较小，但512仍是256的整数倍；所有有效 tile 都是完整 `128×256`，`tailM/tailN/tail*Align` 均为0，尾 tile 分支实际不进入。K 又同时整除64、512、256，没有 K 尾包。

全矩阵覆盖 `64×32=2048` 个互不重叠输出 tile，每 tile 128次 Mmad；K 不分核，无核间合并。24是启动 block 数，不是物理核数声明。

若核内 tile 索引为 \(i,j\)，其全局起点为
`r=2048u+128i, s=1536v+256j`。所有 GlobalTensor 下标以 **half元素**计：
- A 大包：`r*8192 + q*64`，读取128行、每行512元素；
- B 大包：`s*8192 + q*64`，读取256行、每行256元素；
- C 写回：`r*8192+s`，写128行、每行256元素，GM行跨度8192。

这里 `q` 是“大包起始的64宽 K 块号”，不是紧凑包序号：A取0、8、16……，B取0、4、8……（178–188、238–254、343–388行）。

## 3. 数据路径与物理存储

依 A3/2201 平台资料 H03/H04/H09，当前 `__cube__` kernel 的路径为：

`GM ND → MTE2/ND2NZ → L1 → MTE1/LoadData → L0A、L0B → M/Mmad → float L0C → FIX/格式及类型转换 → GM ND`

A1、B1是同一 L1 的不同区域；A2和B2分别属于独立 L0A、L0B。此处没有 UB、Vector 或 MTE3 数据路径。

由52–72行得到每核物理区域；以下均为半开字节区间，KiB=1024B：

| 存储 | Ping | Pong | 每槽有效容量 |
|---|---|---|---|
| L1 A1 | `[0,128 KiB)` | `[128,256 KiB)` | `128×512` half |
| L1 B1 | `[256,384 KiB)` | `[384,512 KiB)` | `256×256` half |
| L0A A2 | `[0,16 KiB)` | `[32,48 KiB)` | `128×64` half |
| L0B B2 | `[0,32 KiB)` | `[32,64 KiB)` | `64×256` half |
| L0C CO1 | `[0,128 KiB)` | 无第二槽 | `128×256` float |

这是固定地址构造的双缓冲，不是 TQue；tensor 选择只是这些区域的别名。L0A 两槽之间存在空隙。

A 经 ND2NZ 后，2201 分支用一次 `LoadData3DParamsV2` 读取当前 `128×64` 切片，形成 L0A 的 Cube 输入排布（399–411行）。B 文件已转置存储；2201 分支用4次 LoadData2D，每次16个 `16×16` half分形，`ifTranspose=false`，形成 L0B 所需排布（433、459–468行）。其源、目的小循环步长均为4096 half，即8 KiB。物理格式转换不改变上述数学公式。

每 tile 请求搬入16个 A 大包、32个 B 大包，即 A 2 MiB、B 4 MiB；写出 C 64 KiB。不同输出 tile 会重新搬输入：A随 N tile 重读，B随 M tile 重读。此为代码请求量，不能等同实际 HBM 流量或忽略 cache。

## 4. 一个 tile 的前10次 K 迭代

选择 block 0 的首个 tile，即 C 行 `[0,128)`、列 `[0,256)`。令 `t=kBlockIdx`，其 K 范围为 `[64t,64(t+1))`。

表中 A1/B1 是 **L1切片起始字节地址，单位KiB**；L0列同时表示各自 L0A、L0B 内的目标槽起点，并非两者共享存储：

| t | A1切片起点 | B1切片起点 | A2/B2槽起点 |
|---:|---:|---:|---:|
| 0 | 0 | 256 | 0 |
| 1 | 16 | 288 | 32 |
| 2 | 32 | 320 | 0 |
| 3 | 48 | 352 | 32 |
| 4 | 64 | 384 | 0 |
| 5 | 80 | 416 | 32 |
| 6 | 96 | 448 | 0 |
| 7 | 112 | 480 | 32 |
| 8 | 128 | 256 | 0 |
| 9 | 144 | 288 | 32 |

计算依据是194–206、399、433行：
- A 槽号 `(t/8)%2`，槽内偏移 `(t%8)*16 KiB`；
- B 槽号 `(t/4)%2`，槽内偏移 `(t%4)*32 KiB`；
- L0槽交替，所有 Mmad 都累加到同一 CO1。

搬运提交过程如下，描述的是依赖顺序而非实测时间线：
1. 循环前 A Ping 装入块0–7，B Ping装入块0–3。
2. t=0提交 Compute 后，按代码顺序预取 B Pong块4–7、A Pong块8–15。
3. t=3消费完 B Ping，释放后将其覆盖为块8–11。
4. t=7释放 B Pong与A Ping，再依次预取 B Pong块12–15、A Ping块16–23。
5. t=8因此读取 A Pong旧包的首片和 B Ping新包的首片。

## 5. 事件依赖与版本差别

按 H04，SetFlag 在源流水前序操作完成后置位；WaitFlag阻塞目的流水并消耗状态。方向与ID共同标识事件。

- **L1覆盖保护**：`MTE1_MTE2` ID0/1对应A Ping/Pong，ID2/3对应B Ping/Pong；初始化为可写。MTE2覆写前等待，MTE1读取包内最后一片后发布释放（159–162、179–187、224–228、241–252行）。
- **L1就绪保护**：DataCopy后置 `MTE2_MTE1`，包内首片读取前等待。前10轮中，t=0等待ID0、2；t=4等待ID3；t=8等待ID1、2（211–216行）。
- **L0就绪保护**：每轮 LoadData后，以 `MTE1_M` 当前槽ID建立该轮搬入完成→Mmad读取关系（506–507行）。
- **L0复用保护，仅baseline完整保留**：209行等待 `M_MTE1` 当前槽ID；519行在 Mmad后发布释放。初始ID0/1令前两轮可用，从t=2开始，同槽覆盖须等t−2的Mmad完成。因此“本轮数据就绪”和“旧数据已读完可覆盖”是两条不同方向的依赖。

Mmad前127轮 `unitFlag=2`，最后一轮为3；Fixpipe也使用3（516、540行），采用UnitFlag方式衔接累加结果与搬出，而非显式 `M_FIX`。它不是被删除的 L0A/B释放等待。核尾仍有事件收尾和 `PIPE_ALL`，host另有流同步。

**variant只删除209行，但仍保留初始化及每轮 `M_MTE1` Set。** 因而在显式事件图中，t=2覆盖Ping之前不再保证t=0的Mmad已读完，t=3覆盖Pong同理。正向 `MTE1_M` 只约束M等待搬入，不能反向阻止MTE1过早覆盖；L1事件也不保护L0消费。循环末尾等待不能追溯补上这些先后关系。

同时，variant对同一 `M_MTE1` ID反复置位而不逐轮消费，不能把事件当作计数队列理解。现有材料不足以确定该序列在实际编译产物上是否出现覆盖错误、停滞或其他事件行为；同样不能断言必然错误或必然正常。可确定的是：两版数学意图、地址、槽选择相同，variant失去了源码层面可证明的L0复用依赖。实际执行是否偶然受流水背压或其他机制限制，以及重叠程度、正确性和耗时，均没有编译、运行或profiling证据支持。
