# 矩阵乘代码理解说明

以下源码定位以 `source/baseline/mmad.asc` 为准；variant 同名符号、行号相同，唯一变化见 `source/VARIANT.patch:3–9`。

## 1. 算法、数值与实际入口

输入均为 half：A 按 `[M,K]` 行连续存储；B 文件按 `[N,K]` 行连续存储，记为 \(B_T\)。目标是：

\[
C[m,n]=\sum_{k=0}^{8191}A[m,k]B_T[n,k]
\]

即逻辑 `[M,K]×[K,N]` 矩阵乘，不是额外对逻辑 B 再转置。C 是行连续 `[8192,8192]` half。`Init:36–40` 将 GM 指针解释为 half；host 用 `sizeof(int16_t)` 计算文件字节数只是取两字节宽度，不表示整数计算。

每个输出 tile 分128次、每次64个K元素归约；`Compute:501–520` 用 half 操作数、float L0C 累加，k=0 时初始化而非读取原C，其余累加。最后 `CopyOut:525–541` 用 `F322F16` 转回half；无显式bias或激活。不能据此保证与其他浮点归约实现逐位一致，特殊值、舍入细节也未由本题完整规定。

host 常量就是编译期tiling，没有独立tiling结构或workspace。题设 host `NPU_ARCH=2201` 选择 `baseM=128、stepKa=8、singleCoreN=1536、numBlocks=24`；device `__NPU_ARCH__=2201` 独立决定LoadData分支。`SCENARIO_NUM=1` 进入 `Process`，不执行 `ProcessL2Cache`，也不执行3510路径（`562–595`）。

`main:597–631` 分配A/B/C各128MiB，读文件、H2D、启动kernel、同步stream后D2H写文件。代码没有结果校验；ACL及文件函数返回值没有检查。`data_utils.h:25–61` 还允许非空短文件，因此完整输入是使用契约，不能说host已验证文件恰好满足shape。

## 2. 分核、循环与尾部覆盖

由 `InitComputeParams:273–306`，block \(b\in[0,24)\)：

- \(i=b\bmod4,\ j=\lfloor b/4\rfloor\)；
- M起点为 `2048i`，N起点为 `1536j`；
- A/B/C的GM起始偏移依次为  
  `2048i*K`、`1536j*K`、`2048i*N+1536j`，均以half元素计，字节地址再乘2。

每block独立生成一块C，K不跨核切分，无部分和合并或核间通信。24是启动block数，不是已知物理核数。

实际循环为 **N tile→M tile→K tile**（`170–258`）：

| block | 实际输出区域尺寸 | nLoop | mLoop | kLoop |
|---|---:|---:|---:|---:|
| 0–19，j=0…4 | 2048×1536 | 6 | 16 | 128 |
| 20–23，j=5 | 2048×512 | 2 | 16 | 128 |

最后一组N起点7680，只处理余下512列，但512仍整除256；M也整除128。因此本workload没有不满的base tile，`tailM/tailN=0`不被有效迭代使用。合计 `64×32=2048` 个输出tile，每个128次Mmad。每tile重新搬入完整K方向的A/B；没有跨输出tile保留数据的显式复用，实际cache命中不能从此推定。

## 3. 物理存储与数据路径

`Process:52–72` 的LocalTensor构造中，地址以字节计、长度以元素计。由常量推导，每block布局如下；区间为左闭右开：

| 位置 | Ping / Pong字节区间 | 单槽有效容量 |
|---|---|---:|
| A1，共享L1 | `[0,128KiB)` / `[128,256KiB)` | 128×512 half |
| B1，同一L1 | `[256,384KiB)` / `[384,512KiB)` | 256×256 half |
| A2，L0A | `[0,16KiB)` / `[32,48KiB)` | 128×64 half |
| B2，L0B | `[0,32KiB)` / `[32,64KiB)` | 64×256 half |
| CO1，L0C | `[0,128KiB)`，单份 | 128×256 float |

A2/B2相同数字地址属于不同物理存储，互不重叠；A1/B1则不是两套独立L1。没有TQue，双缓冲由静态地址和标志手工管理。

依据内联 `910c-hardware.md` 的A3映射及事件语义，路径为：

```text
GM A、B_T（ND）
  ─MTE2 / ND→NZ→ L1 A1、B1
  ─MTE1→ L0A A2（ZZ）、L0B B2（ZN）
  ─M / Mmad→ L0C CO1（NZ、float）
  ─FIX / NZ→ND、float→half→ GM C
```

`DataCopyInA/B:343–388` 每包分别读取128×512和256×256，GM行跨度均为8192元素。`kChunkIdx` 实际是以baseK块计的起始索引，不是“大包序号”：A依次0、8、16，B依次0、4、8，GM列起点再乘64。

2201的A每K步使用一次LoadData3D V2（`399–411`）。B已按转置存储，使用4次LoadData2D，每次搬16个16×16 half分形，`ifTranspose=false`；每次源、目的增量均为4096 half，即8KiB（`433–468`）。这里的格式转换不改变上述数学语义。

## 4. 一个tile的前10次K迭代

选block0的首个输出tile，即C的行`[0,128)`、列`[0,256)`。所有迭代都累加至同一CO1地址0。下表列出A/B在L1中**本次切片的起始字节偏移**，单位KiB；L0列表示A2/B2同时选槽，其槽内起点始终为0。

| kBlockIdx | 逻辑K区间 | A1槽/切片起点 | B1槽/切片起点 | L0槽 |
|---:|---|---|---|---|
| 0 | [0,64) | Ping / 0 | Ping / 256 | Ping |
| 1 | [64,128) | Ping / 16 | Ping / 288 | Pong |
| 2 | [128,192) | Ping / 32 | Ping / 320 | Ping |
| 3 | [192,256) | Ping / 48 | Ping / 352 | Pong |
| 4 | [256,320) | Ping / 64 | Pong / 384 | Ping |
| 5 | [320,384) | Ping / 80 | Pong / 416 | Pong |
| 6 | [384,448) | Ping / 96 | Pong / 448 | Ping |
| 7 | [448,512) | Ping / 112 | Pong / 480 | Pong |
| 8 | [512,576) | Pong / 128 | Ping / 256 | Ping |
| 9 | [576,640) | Pong / 144 | Ping / 288 | Pong |

公式来自 `194–206、399、433`：A槽内偏移为`(k%8)*8192 half`，B为`(k%4)*16384 half`。B表中起点之后还有前述4次8KiB分段LoadData。

搬包/复用的源码顺序（不代表测得时间线）：

- 循环前：A Ping装K `[0,512)`，B Ping装`[0,256)`。
- k=0的Compute发射后：先B Pong装`[256,512)`，再A Pong装`[512,1024)`。
- k=3：B Ping最后一片已由MTE1取走，释放该槽，随后装`[512,768)`。
- k=7：释放B Pong和A Ping；随后分别装`[768,1024)`、`[1024,1536)`。
- k=8开始读取A Pong和重装后的B Ping。L0则从k=2起每步复用两步前的槽。

## 5. 事件关系及两版本区别

事件方向与ID共同确定关系，不同方向的同号事件不是同一个状态。

1. **L1可写**：`159–162` 预置 `MTE1_MTE2`，ID0/1保护A Ping/Pong，ID2/3保护B Ping/Pong。MTE2搬包前Wait；最后一个切片LoadData后Set，保证覆盖前MTE1已读完旧包。
2. **L1就绪**：搬包后Set `MTE2_MTE1`；每包首片Wait。前10步中k=0等A0/B2，k=4等B3，k=8等A1/B2。包内后续LoadData依赖相同MTE1流水顺序。
3. **L0就绪**：`506–507` 每步Set/Wait `MTE1_M`，保证当前Mmad前A2/B2已写好。
4. **L0复用**：baseline先预置 `M_MTE1` ID0/1；每步在LoadData前Wait所选槽（`209`），Mmad后Set（`519`）。因此k=2覆盖Ping前，必须等k=0的Mmad完成；k=3覆盖Pong前等k=1，以此类推。
5. **输出/收尾**：Mmad非末步`unitFlag=2`、末步3，Fixpipe为3，使用unit-flag协议组织M与FIX的输出同步，并非手写`M_FIX`事件。末尾`265–270`排空复用事件，入口`572`还有全流水屏障；host stream同步保护随后D2H。具体unit-flag底层实现未在题面展开。

variant只删去第4项的逐步Wait，其他地址、预取、正向事件、反向Set和末尾Wait全保留。它仍证明“当前LoadData完成后当前Mmad才可读”，却**不再显式证明旧Mmad读完后同一L0槽才被覆盖**：最早候选冲突是k=0读Ping与k=2写Ping。L1事件保护的是L1，正向`MTE1_M`也不能反向替代这条依赖；末尾屏障不能修复此前覆盖。

此外variant的`M_MTE1`被初始化并反复Set，循环内却不再消费；不能将事件当成无限计数队列。未消费状态上的重复Set会如何体现，题面不足以确定。

## 6. 静态结论边界

910C各流水可异步执行，源码中的函数调用顺序不是跨流水完成顺序。baseline明确表达了L1、L0的生产与复用依赖；variant破坏了L0反向握手的可证明闭环。但这不等于已证明variant必然错算、必然挂起或必然更快：实际调度、事件重复置位行为及编译器生成指令均无运行证据。双buffer和预取说明存在流水重叠条件，不证明真实重叠率、带宽或瓶颈。

当前K恰好整除64、包长和步数；源码没有通用K尾包裁剪。任意shape、不同launch数量或资源预留条件下的适用性不能由本workload外推。
