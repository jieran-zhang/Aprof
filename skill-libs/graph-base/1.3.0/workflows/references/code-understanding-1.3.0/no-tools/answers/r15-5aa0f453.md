# `data_copy_pad.asc` 代码理解说明

## 1. 算法、输入输出与实际分支

**源码事实：**分析对象为 `source/current/data_copy_pad.asc`（下简称 `.asc`）。`scenarioNum=2` 固定于第20行；host 模板参数为 `<5,13,16,120>`（220–223、264行），入口实例化 `KernelDataCopyPad<float,...>`（194–201行）。这是 **float32 分行抽取、经 UB 填充后按另一种行距写回**，没有加法、归约、类型转换或浮点舍入计算。

workload 的输入物理形状为 `[5,20]`，共400B；每行只抽取前13个 float，即 `100*r` 至 `100*r+12`。输出分配为 `[5,18]` 的360B空间，事先逐字节置为 `0xA5`（244–259行）。按下述 API 语义推导，最终：

- `output[r,0:13] = input[r,0:13]`；
- `output[r,13:18]` 不被 kernel 写入，仍为每个 float 槽四字节均为 `0xA5`，即位模式 `0xA5A5A5A5`，**不是零填充**。
- UB 中确实生成每行3个零，但这些零不在最终写回有效范围内。

`DST_COLS=16` 决定显式右补数，`DST_TOTAL_LENGTH=120` 决定 UB 容量；二者均不表示输出 GM 的物理行长。当前变化在 `source/VARIANT.patch:18–49,70–96` 可追溯，不能沿用 upstream 的 `[32,59]→[32,64]` 描述。

## 2. 分工与执行组织

host 启动 `numBlocks=1`（225、264行），kernel 标为 `__vector__`（195行）。因此只有一个逻辑 Vector block 执行整批5行；这不是910C物理核数的声明。代码没有核号偏移、跨核通信、runtime tiling 结构或 workspace；编译期常量就是当前任务参数。

`KernelDataCopyPad::Process`（58–70行）依次执行：

1. 静态分配一份 `srcLocal`，120个 float，即480B UB；
2. `Duplicate` 将全部120个元素置零；
3. 等待 Vector 清零完成，再一次调用 `CopyIn`；
4. 等待搬入完成，再一次调用 UB→GM `DataCopyPad`。

没有软件行循环、tile 循环、队列或双缓冲；5行由搬运参数中的 `blockCount=5` 表达。当前路径也不启用 `SetLoopModePara`。场景3–6对应的3510条件代码在实际 device 宏2201下不编入（107–186行）；其他 `if constexpr` 分支不执行。

## 3. 地址、填充与写回范围

以下区间均为**相对各自 buffer 起点的字节半开区间**。

### API 单位与当前参数

依据随题 `references/910c-hardware.md` 的 DataCopyPad 节（H05/H06，A3普通重载）：

- `blockLen` 以字节计；
- GM侧 stride 是前块有效末尾到下一块开头的**字节间隔**；
- UB侧 stride 是块间间隔，以**32B dataBlock**计；
- UB普通模式每块按32B对齐；
- 左右 padding 以 **T元素个数**计，而非字节。

**搬入，`CopyIn:95–105`：**

```text
copyParams = {5, 52B, 28B, 1个32B块, 0}
padParams  = {isPad=true, left=0, right=3个float, value=0}
```

因此 GM 行起点跨度为 `52+28=80B`，恰为20个 float。UB 每行有效52B，右补12B后为64B，再留32B间隔，起点跨度为96B，即24个 float。

**搬出，`Process:68–69`：**

```text
copyParams = {5, 52B, 1个32B块, 20B, 0}
```

UB源块按 `ceil(52/32)*32=64B` 占位，再加32B源间隔，起点跨度仍为96B；GM目标起点跨度为 `52+20=72B`，恰为18个 float。**每行只写52B，不会把 UB 的64B整块有效输出。**

### 各行实际区间推导

| 行r | 输入GM读取 | 输入未读取尾部 | UB有效数据 | UB显式补零 | UB间隔/末尾余区 |
|---|---|---|---|---|---|
| 0 | `[0,52)` | `[52,80)` | `[0,52)` | `[52,64)` | `[64,96)` |
| 1 | `[80,132)` | `[132,160)` | `[96,148)` | `[148,160)` | `[160,192)` |
| 2 | `[160,212)` | `[212,240)` | `[192,244)` | `[244,256)` | `[256,288)` |
| 3 | `[240,292)` | `[292,320)` | `[288,340)` | `[340,352)` | `[352,384)` |
| 4 | `[320,372)` | `[372,400)` | `[384,436)` | `[436,448)` | `[448,480)` |

UB全部480B先清零，MTE2随后覆盖5段有效数据，并显式产生5段12B padding；32B间隔不是有效输入或显式 padding，其零值来自先前 `Duplicate`。最后的 `[448,480)` 是分配余区，没有第6行，不能据 stride 字段断言搬运额外写了这一段。

| 行r | 输出GM写回 | 保持0xA5的范围 |
|---|---|---|
| 0 | `[0,52)` | `[52,72)` |
| 1 | `[72,124)` | `[124,144)` |
| 2 | `[144,196)` | `[196,216)` |
| 3 | `[216,268)` | `[268,288)` |
| 4 | `[288,340)` | `[340,360)` |

所以 UB→GM 的源有效区与搬入产生的有效区逐行相同，右补零和32B间隔均不进入输出。输入最大有效访问终点372B、UB填充终点448B、输出有效写入终点340B，分别在400/480/360B边界内；各行互不重叠。这里的52B非32B对齐尾部由 `DataCopyPad` 普通重载处理，不存在另一个软件尾块任务。

## 4. 数据生命周期与同步依赖

`Init` 仅将两个 GM 指针重解释为 float 并绑定 `GlobalTensor`，没有长度参数或运行时形状检查（53–56行）。唯一用户 UB tensor 的生命周期贯穿本次 `Process`：先由 V 清零，再由 MTE2覆盖有效区，最后供 MTE3读取；没有下一轮复用。

| 同步位置 | 生产者、消费者及依赖 |
|---|---|
| 63–64行 `V_MTE2`，ID0 | V的 `Duplicate` → MTE2搬入。确保整区清零完成后才覆盖，避免晚完成的清零抹掉输入；同时保留间隔区初值。 |
| 66–67行 `MTE2_MTE3`，ID0 | MTE2写入 UB → MTE3读取同一 UB有效区。保证有效输入就绪后才写回GM。 |
| 212行 `PipeBarrier<PIPE_ALL>()` | kernel末尾核内相关流水屏障，收束包括搬出的工作；不是跨核或host同步。 |
| 266行 `aclrtSynchronizeStream` | host等待该stream的kernel结束，之后才进行D2H和文件写出（268–269行）。 |

依据事件契约，Set由源流水在前序操作完成后置位，Wait使目标流水等待并消费状态；相邻书写不是事件无效的证据。两对事件虽同用ID0，但方向不同。清零→搬入→搬出的依赖链已明确；不存在下一轮覆盖，因此也没有循环复用事件。

## 5. 910C执行行为与证据边界

**平台/API知识：**A3/2201下该 `__vector__` 路径使用AIV侧UB；Scalar负责控制与指令发射，`Duplicate` 在V流水执行，GM→UB由MTE2承担，UB→GM由MTE3承担（随题硬件参考H01–H06、H14–H16）。本实现不使用Cube、L1、L0或FIX路径。

**静态推导：**kernel逻辑有效GM读取、写回各 `5×52=260B`；另有480B UB清零和60B显式右补零。这些不是实测总线流量：32B对齐占位、底层事务、cache行为、指令展开及隐含资源不能由上述有效字节数直接确定。480B只是可见用户UB数据区，不代表完整编译产物总占用。没有测量，不能裁定等待时长、流水重叠、带宽利用率或性能瓶颈。

**适用边界：**以上结论以题设400B输入内容、成功分配及正常API执行为前提。host未检查ACL调用与文件读写的返回值；`ReadFile` 还会按引用改写 `inputByteSize`（`source/current/data_utils.h:25,59`），本题完整输入下仍为400B，不能据此推广到短文件或读取失败。材料没有设备编译、运行或结果校验记录；因此地址与输出语义是源码结合A3 API契约的推导，不是已观测执行结果。
