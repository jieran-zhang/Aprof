# 代码理解说明

## 1. 输入输出与数值语义

本次输入、输出均为连续一维 ND、25019 个 **bfloat16** 元素，各占 **50038 字节**。host 从文件读入原始二进制数据，不进行数值转换；输出按相同类型和元素数写文件（`source/op_host/exp.asc:38–63`，`data_utils.h:6–14`）。

`ComputeExpTiling` 并不把 base 传给设备，而是在 host 上预先计算两个 float 参数（`exp_tiling.h:27–28`）：

\[
m=\mathrm{scale}\cdot L,\quad s=\mathrm{shift}\cdot L,\qquad
L=\begin{cases}\log(\mathrm{base}),&\mathrm{base}>0\\1,&\text{其他}\end{cases}
\]

设备逐元素执行 `Exp(Muls(x,m)+s)`。因此，对正 base，实数意义为
\[
y=\mathrm{base}^{\mathrm{scale}\,x+\mathrm{shift}};
\]
base 非正时实际执行自然指数 `exp(scale*x+shift)`，并非计算负底数幂。

本次 base=2、scale=0.5、shift=-1，传入的 `multiplier` 约为 0.34657359，`shift` 约为 −0.69314718，理想结果为 \(2^{0.5x-1}\)。输入 −2、0、2 分别对应 0.25、0.5、1。

**实际浮点语义**还有以下限定（`exp_kernel.asc:45–64`）：

- bfloat16 先转 float，再依次执行 float `Muls`、`Adds`、`Exp`，最后以 `CAST_RINT` 转回 bfloat16；该模式按 API 表示最近偶数舍入。
- float16 也使用两个 float 临时张量完成上述运算，最终转回 half，但代码指定的是 `CAST_NONE`，不能将其理解为“不发生精度损失”。
- float32 直接在输入、输出 float 张量上计算，不分配转换临时张量。
- 源码表达的是分开的乘、加、指数操作，而非保证一次融合的精确数学幂。host 参数舍入、各步 float 运算、指数近似及最终窄化都可能影响结果；没有运行证据，不能承诺上述代表值的逐位结果。

## 2. host 路径与实际分核

host 解析参数，初始化 ACL 和设备，查询向量核数量，再生成 tiling；分配 host 输入/输出及 device 输入/输出/tiling，完成 H2D 后在一个 stream 上启动 kernel。随后同步 stream，再 D2H、写文件并释放资源（`exp.asc:38–68`）。这里没有 host 端正确性校验或性能计时。

本题固定查询结果为 3。按 `ComputeExpTiling`（`exp_tiling.h:18–29`）：

| 字段 | 本次值及单位 |
|---|---|
| `totalLength` | 25019 个元素 |
| `useful` | ceil(25019/4096)=7 |
| `blockNum` | min(3,7)=3 |
| `blockLength` | ceil(25019/3)=8340 个元素 |
| `tileElements` | 4096 个元素 |
| `dtype` | `EXP_BFLOAT16=2` |

启动的是 **3 个逻辑 block**，不是 7 个 block，也不是每个 tile 单独启动。设备入口根据 `dtype` 进入 `KernelExp<bfloat16_t>`（`exp_kernel.asc:85–93`）。host 拒绝未列出的类型；设备入口本身则把非 float32、非 float16 的值都归入 bfloat16 分支。

## 3. 分块、循环与尾块

每个 block 用 `GetBlockIdx()*blockLength` 得到以**元素**计的全局起点，并以剩余总长度截断自己的 `length_`，再绑定独立的输入、输出 GM 区间（`exp_kernel.asc:9–15`）。

本次实际划分如下，区间均为左闭右开：

| block | 全局元素区间 | 长度 | 输入/输出起始字节偏移 | 各次 `count` |
|---|---|---:|---:|---|
| 0 | [0,8340) | 8340 | 0 | 4096、4096、148 |
| 1 | [8340,16680) | 8340 | 16680 | 4096、4096、148 |
| 2 | [16680,25019) | 8339 | 33360 | 4096、4096、147 |

每块循环局部 `off` 为 0、4096、8192，均是元素偏移（`exp_kernel.asc:26–33`）。因此共有 **9 次 tile 处理**，每次顺序调用 `CopyIn → Compute → CopyOut`。

三个尾 tile 的全局元素起点分别是 8192、16532、24872；对应字节起点为 16384、33064、49744，长度为 296、296、294 字节。最后一次写入结束于字节偏移 50038，恰好覆盖输出。

`DataCopyExtParams` 的块数为 1、长度为 `count*sizeof(T)` **字节**，其余 stride 等参数为 0（`exp_kernel.asc:37–42,69–73`）。这里没有按完整 4096 元素回写尾块。每次计算也仅使用 `count`，不依赖尾块后面的缓冲区内容。

## 4. 数据、存储与依赖

每个 block 独立持有 `TPipe`、两个深度为 1 的队列，以及转换用的两个 `TBuf`（`exp_kernel.asc:16–23,76–82`）。本次每块的显式本地张量容量为：

- `inQ_`：4096×2＝8192 字节；
- `outQ_`：8192 字节；
- `fpIn_`、`fpOut_`：各 4096×4＝16384 字节；
- 合计 **49152 字节，即 48 KiB/块**，不含框架管理或可能的实现开销。

尾 tile 仍使用这些完整容量，只缩小有效计数。float16 的容量组织相同；float32 无两个转换缓冲区，两个队列各 16384 字节，合计 32 KiB/块。各块资源独立，不应把三块容量理解成一个共享缓冲池。

单 tile 数据路径为：

1. GM 输入通过 `DataCopyPad` 进入 `VECIN`，入队；
2. 出队后转换到 `fpIn_`，写 `fpOut_` 完成乘、加、指数，再转换到 `VECOUT`；
3. 输出入队、出队后由 `DataCopyPad` 写回 GM，并释放张量。

队列/API 管理搬运与计算的就绪关系；乘、加、指数之间还有对同一输出张量的读写依赖。块间输入输出区间不重叠，无归约、跨块通信或跨块同步。tiling 是所有 block 只读的 GM 数据；具体读取是否被编译器缓存或提升，源码不能确定。

## 5. 910C 上的执行含义与证据边界

**平台/API 层面**，目标 device 架构为 `__NPU_ARCH__=2201`。本源码没有据此做条件分支，也没有使用 host `NPU_ARCH` 分派，不能引入 3510 的行为。算子以向量计算为主：GM↔本地 UB 搬运通常分别由 MTE2/MTE3 路径承担，Cast/Muls/Adds/Exp 使用向量计算资源；没有矩阵计算或 Cube 数据路径。

`DataCopyPad` 是处理此类非整块字节长度的接口。本次后两个 block 的 GM 起点分别相对 32 字节边界偏移 8、16 字节，尾搬运长度也不是 32 字节整数倍；不能把它等同于只适用于对齐整块的普通拷贝。API 的内部补齐、事务拆分与实际指令数不能仅由源码确定。

当前两个队列都只有一个缓冲槽，循环也没有显式提前搬运下一 tile 或双缓冲轮转。因此源码没有组织多 tile 的双缓冲流水；但这并不等于所有硬件引擎必定完全串行，实际重叠还取决于编译器、事件调度和接口实现。

本次逻辑 GM 输入读取与输出写回各 50038 字节，合计 100076 字节，另有 tiling 访问；这不是实测总线流量。3 个 block 可分派到向量执行资源，但物理驻留、并发时序、带宽、指数吞吐、延迟及瓶颈均无测量依据。

适用边界方面，源码仅接受三种 host dtype；没有检查 base、scale、shift 的有限性或为指数溢出、下溢提供特殊处理，也没有对任意超大长度的整数运算提供溢出保护。上述静态推导足以确定本次覆盖范围、类型路径与资源组织，但不足以给出性能结论或所有特殊浮点输入的逐位行为。
