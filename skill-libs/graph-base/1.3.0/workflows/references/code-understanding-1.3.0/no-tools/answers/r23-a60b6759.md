# `matmul_leakyrelu_basic_api.asc` 代码理解

以下源码行号均指 `source/matmul_leakyrelu_basic_api.asc`，简称 **主文件**。平台解释依据题面内联的 `910c-hardware.md`（H02/H04/H05/H06/H09 等），具体范围、次数和容量是由本次常量推导，并非运行结果。

## 1. 算法、接口与数值语义

输入 A、B 分别是连续 ND 的 half 矩阵 `[512,128]`、`[128,128]`；输出 C 是 half、ND 的 `[512,128]`。数学目标为：

\[
S_{m,n}=\sum_{k=0}^{127}A_{m,k}B_{k,n},\qquad
C_{m,n}=\begin{cases}S_{m,n},&S_{m,n}\ge0\\0.001S_{m,n},&S_{m,n}<0.\end{cases}
\]

**实际数值路径不能省略中间 half 转换**：

1. half 输入送入 `Mmad`，结果保存在 float 的 L0C；
2. `Fixpipe` 以 `F322F16` 将结果转换为 half，写入 GM；
3. AIV 再读这个 half 中间结果，以 `(half)0.001` 为斜率执行 half `LeakyRelu`，原址写回。

因此应理解为对**已经转换到 half 的矩阵乘结果**执行激活，而不是在 float 累加结果上先激活再转 half。斜率本身也经过 half 表示；具体舍入、特殊值和溢出行为不能仅凭这里的源码承诺逐位结果。无 bias；Fixpipe 的 `reluEn=false`，激活只发生在 AIV（L61、L115、L125–127、L166）。

Host 的输入/输出缓冲大小分别为 A 131072B、B 32768B、C 131072B。`main` 初始化 ACL/device 0/stream，读取两个文件并 H2D，启动一次 kernel，等待 stream 后 D2H、写文件并释放资源（L197–258）。没有独立 tiling 结构或运行时 shape 分派；L200–210 的模板常量就是本次切分来源。

## 2. 实际分核、范围及循环

`numBlocks=(512/256)*(128/128)=2`，入口为 `__mix__(1,2) void mmol...`，实际符号是 **`mmad_vec_custom`**（L188、L215、L242–243）：按该混合执行配置使用 **2 个 AIC、4 个 AIV**。这是本任务启动规模，不是 910C 总物理核数。

AIC 按自身 `GetBlockIdx()` 对 A、C 沿 M 偏移，B 不偏移；AIV 则用 `GetBlockIdx()/2` 找到对应 AIC 的输出，再按奇偶选择上下半块（`Init` L31–45，`LeakyReluCompute` L150）。

| 执行角色/核号 | 输出行范围，半开区间 | 相对原始 C 的起点，half 元素 |
|---|---|---:|
| AIC 0 | `[0,256)`，所有 N 列 | 0 |
| AIC 1 | `[256,512)`，所有 N 列 | 32768 |
| AIV 0 / 1 | `[0,128)` / `[128,256)` | 0 / 16384 |
| AIV 2 / 3 | `[256,384)` / `[384,512)` | 32768 / 49152 |

上述元素偏移乘 2 才是字节偏移。AIC 的 A 起点同样为 0、32768 个 half，分别读 A 的 256 行；两核各自读取完整 B。每个 AIV 处理 `128*128=16384` 个 half，即 32768B；各自读写区域不重叠。

每个 AIC **只计算一个 `256×128` 输出 tile**，K=128 一次完成。没有 M/N tile 遍历，也没有 K 分段累加循环。`MmadParams{256,128,128,0,false,true}` 初始化本次结果，不依赖 C 的旧值（L115）。`singleCoreK` 未参与 device 运算；`singleCoreN` 在此仅参与 host 启动数计算，device 地址并未实现一般的 N 方向分核。

本次所有维度均整除 16，M 也整除分核大小，故无尾 tile、无有效尾长分支。`LeakyReluCompute` 仅调用一次，`mIndex=nIndex=0`、`tileLen=16384`（L138）；函数中的通用索引参数不意味着实际存在外层循环。

## 3. 数据、存储与 2201 搬运排布

依据 2201 的物理存储契约，AIC 与 AIV 是独立执行核，不共享这里的片上 tensor，双方通过 GM 的 C 交换数据。完整路径为：

```text
A/B：GM half ND → MTE2 → L1 half NZ
                         ↓ MTE1
                  L0A half ZZ / L0B half ZN
                         ↓ M/Mmad
                    L0C float NZ
                         ↓ FIX：NZ→ND、float→half
                    GM C half 中间值
                         ↓ MTE2
                    AIV UB half
                         ↓ V/LeakyRelu，原址计算
                    AIV UB half
                         ↓ MTE3
                    GM C half 最终值
```

L52–61 的分配以**元素数**为单位，每个 AIC 的显式用户数据区如下：

| tensor | 位置/排布 | 数据量 |
|---|---|---:|
| `a1Local` | L1，half NZ | 32768 元素，64KiB |
| `b1Local` | 同一 L1 的另一分配区，half NZ | 16384 元素，32KiB |
| `a2Local` | L0A，half ZZ | 64KiB |
| `b2Local` | L0B，half ZN | 32KiB |
| `cLocal` | L0C，float NZ | 32768 元素，128KiB |

每个 AIV 另分配 `vecLocal`：UB half、16384 元素、32KiB（L133–134）。不同存储层容量不可合并解释为 UB 占用。L0C 用户区达到材料给出的标称 128KiB；这不等于已经验证编译器预留和完整产物资源合法。

`DataCopy` 的 `Nd2NzParams`（L65、L68）分别读取 A 的 `256×128` 和 B 的 `128×128`，GM 行跨度分别为 K=128、N=128 个元素，并转换为 L1 NZ。half 分形是 `16×16`、256 元素、512B。

本次 device 宏为 **2201**，因此执行 L75–91：

- A：循环 16 次；第 i 次目的偏移 `i*128*16=2048i` 个 half，即 4096i B，源偏移 `i*512/sizeof(half)=256i` 个 half，即 512i B。每次加载 8 个分形，源分形步长 16，即 8192B，形成 L0A ZZ。
- B：循环 8 次；目的同样每次前进 4096B，源每次前进 512B。每次加载 8 个分形，源分形步长 8，即 4096B，并设置 `ifTranspose=true`，形成 L0B ZN。

这里的循环是**排布搬运循环**，不是额外的矩阵归约。B 的局部分形转置不改变数学上 `A×B` 的含义。

Fixpipe 输出 `nSize=128,mSize=256,srcStride=256,dstStride=N=128`（L125–127），把完整 tile 写为 GM ND。随后每个 AIV 的 `DataCopyPad` 按 128 行搬运：`blockLen=128*2=256B`，GM 行间间隔 `(N-baseN)*2=0B`，UB 间隔也为零（L146–158、L174–176）。256B 已对齐 32B，左右 padding 均为零，故本次不增加填充元素，UB 中是连续的半块输出。

## 4. 依赖、同步与生命周期

源码使用单组静态 tensor，没有 TQue、双缓冲、地址轮换或跨 tile 复用。关键依赖由以下机制建立：

| 源码位置 | 被保护的生产者→消费者关系 |
|---|---|
| L72–73，`MTE2_MTE1` | 两次 GM→L1 搬完后，LoadData 才读取 L1 |
| L110–111，`MTE1_M` | L0A/B 就绪后，Mmad 才读取 |
| L119–120，`M_FIX` | Mmad 写完 L0C 后，Fixpipe 才读取 |
| L129、L136，跨核 flag | AIC 的 FIX 写回就绪后，对应两个 AIV 才读取 GM C |
| L162–163，`MTE2_V` | GM→UB 完成后，V 才原址激活 |
| L170–171，`V_MTE3` | 激活完成后，MTE3 才读取 UB 写回 |

`CrossCoreSetFlag<0x2, PIPE_FIX>(0)` / `CrossCoreWaitFlag<0x2>(0)` 是这里跨 AIC/AIV 的发布与等待；核内事件不能替代它。AIV 写回覆盖的是自己已经读入 UB 的区域，两个消费者区域不重叠，且 AIC 不再写该 tile，故无需核间结果合并。

入口末尾的 `PipeBarrier<PIPE_ALL>()`（L194）收束各核相关流水，不是跨核全局屏障；host 的 `aclrtSynchronizeStream`（L244）保证 kernel 完成后才取最终输出。各本地 buffer 从生产到最后消费一次，没有下一轮覆盖依赖。

## 5. 适用边界与证据不足

- L92–106 的 **3510 分支本次不执行**；它使用 V2 LoadData，且 A 的 L0A 排布不同，不能把其路径套到 910C。当前源码没有 host `NPU_ARCH` 分派，不能混同 device 宏。
- 当前正确覆盖依赖固定常量关系：K/N 不分块、每核大小等于 base tile、M 可整除且 AIV 平分行数。源码没有一般余数处理、参数校验或任意 shape 支持的证明。
- `source/data_utils.h:25–61` 仅检查文件非空且不超过容量，未要求恰好等于张量大小，还会更新传入的 `fileSize`。主文件忽略读写及 ACL 返回值；上述语义以文件完整、API 成功为前提。
- 未提供设备编译或测量。流水可异步执行、任务有独立区域，但实际重叠程度、cache/HBM 流量、等待时间及吞吐均尚未确认；静态数据流不构成性能瓶颈结论。
