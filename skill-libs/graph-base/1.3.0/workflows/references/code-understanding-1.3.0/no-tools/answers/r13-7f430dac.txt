# `data_copy_pad.asc` 代码理解说明

以下源码行号均指 `source/current/data_copy_pad.asc`，简称 **current**；硬件/API依据来自题内 `references/910c-hardware.md` 的 A3/2201 说明。区间统一为**相对各缓冲区基址的字节半开区间**。

## 1. 输入输出与整体语义

**源码事实：**`scenarioNum=2`（L20），host 固定模板参数为 `<5,13,16,120>`（L220–223、L264），输入输出 dtype 均为 float（L228–229、L198–201）。这里：
- 输入实际分配 `5×20×4=400B`，物理布局为每行20个 float；
- 输出实际分配 `5×18×4=360B`，物理布局为每行18个 float；
- `dstCols=16` 决定搬入 UB 时的右填充数量，**不是输出 GM 行长**；
- `dstTotalLength=120` 决定 UB 申请元素数，**不是输出分配元素数**。

输出先由 `aclrtMemset` 全部置为字节 `0xA5`（L244–259）。结合下述 API 单位与地址推导，当前输入到输出的变换为：

\[
z[r,c]=x[r,c]=100r+c,\quad 0\le r<5,\ 0\le c<13.
\]

每行 `c=13..17` 的20个字节不写回，仍为 `0xA5`，即每个对应 float 槽的位模式为 `0xA5A5A5A5`；这不是浮点零。输入每行 `c=13..19` 不作为有效数据搬入。

这是**选取行首13个 float、经 UB 对齐填充后按另一 GM 行距写出**，不是产生完整的 `[5,16]` 补零输出。有效数据没有算术、归约或类型转换，float 位模式按搬运语义保持；给定的整数输入均可由 float 精确表示。

## 2. 实际分派、任务与存储

`main` 仅启动一次 kernel，`numBlocks=1`（L225、L264）；入口为 `__global__ __vector__ data_copy_pad_custom`（L194–213）。没有独立 tiling 结构，参数全部由 host 编译期常量进入模板；没有核号偏移或跨核合并。

2201 下实际执行顺序是：

```text
V：将整份 UB 置零
    → V_MTE2 事件
MTE2：5块 GM→UB 搬运，逐块右补零
    → MTE2_MTE3 事件
MTE3：5块 UB→GM，仅写每块52B
    → kernel末尾 PIPE_ALL 屏障
```

`Process` 仅申请一份 `srcLocal`：`Alloc<float,120>()`，用户数据区为 **480B**（L60–62；静态 Alloc 的数量单位为元素，参考 H15/H16）。同一 UB 同时承担搬入目的和搬出源，没有第二份结果 tensor、TQue、双缓冲或软件 tile 循环。其生命周期是置零→局部覆盖→读出→kernel结束。

`CopyIn` 中场景4/5/6的额外置零不执行；场景1及其他 dtype 分支也不执行。L107–186 的3510条件分支在目标 `__NPU_ARCH__=2201` 下被排除，不涉及 Compact 或 loop mode。每次搬运的 `blockCount=5` 表示一次 API 调用中的5个数据块，不是5个 kernel block。

## 3. 搬入：GM 行距80B，UB 行距96B

L98–105 的参数实际为：

```text
copyParams = {5, 52, 28, 1, 0}
padParams  = {true, 0, 3, 0}
```

**API知识（H05）：**A3 普通 GM→UB 重载中，`blockLen`、GM侧 `srcStride` 以字节计；UB侧 `dstStride` 以32B dataBlock计；左右 padding 以元素计。stride 是块间空隙，而不是行起点跨度。

因此：
- GM 下一块起点增量为 `52+28=80B`；
- 每块13个 float 加右侧3个零，共 `52+12=64B`，恰好32B对齐；
- UB 额外间隔为 `1×32=32B`，下一块起点增量为 `64+32=96B`。

**由上述规则推导：**

| 行r | 输入GM有效读取 | UB有效数据 | UB显式右填零 | UB行槽余区 |
|---|---|---|---|---|
| 0 | `[0,52)` | `[0,52)` | `[52,64)` | `[64,96)` |
| 1 | `[80,132)` | `[96,148)` | `[148,160)` | `[160,192)` |
| 2 | `[160,212)` | `[192,244)` | `[244,256)` | `[256,288)` |
| 3 | `[240,292)` | `[288,340)` | `[340,352)` | `[352,384)` |
| 4 | `[320,372)` | `[384,436)` | `[436,448)` | `[448,480)` |

输入每个80B行槽的最后28B被跳过，包括最后一行的 `[372,400)`。UB 前四个32B余区是块间间隔；最后的 `[448,480)` 是分配尾部，不需要再连接下一块。它们均先被 `Duplicate` 清零，不是由 `dstStride` 执行填充。

搬入后，480B UB 可分解为：260B有效输入、60B显式右填零、160B间隔及尾部零区。不存在额外的非对齐 dummy 空间，因为13+3个 float 已达到64B。

## 4. 写回：仅写52B，不写UB padding

L68–69 使用 UB→GM 重载，参数为：

```text
copyParams = {5, 52, 1, 20, 0}
```

**API知识（H06）：**此方向的 UB `srcStride` 单位为32B，GM `dstStride` 单位为字节；UB 每块按有效长度向上32B对齐定位下一块，但 GM 只写 `blockLen` 个有效字节。

故：
- UB 源块起点跨度为 `ceilAlign(52,32)+32=96B`，与搬入布局一致；
- GM 目的块起点跨度为 `52+20=72B`，即18个 float；
- 每块只取对应 UB 行首52B，右填充及间隔均不写入 GM。

| 行r | 输出GM写入范围 | 保留0xA5的范围 |
|---|---|---|
| 0 | `[0,52)` | `[52,72)` |
| 1 | `[72,124)` | `[124,144)` |
| 2 | `[144,196)` | `[196,216)` |
| 3 | `[216,268)` | `[268,288)` |
| 4 | `[288,340)` | `[340,360)` |

最后一次有效源访问止于 UB 的436B，最后一次有效写入止于 GM 的340B，均在对应分配内。没有行数余块或软件尾 tile；每行52B这个非32B对齐尾部由 `DataCopyPad` 的普通路径处理，不能解释为向 GM 写64B。

## 5. 同步依赖与910C执行行为

依据 current L62–69、L212及 H04：

- **`V_MTE2` Set/Wait（L63–64）：**生产者是 V 流水的480B清零，后继是 MTE2 的部分覆盖。它保证清零完成后才搬入，避免较晚完成的清零破坏输入；未覆盖间隔也因此具有确定初值。这不是循环首轮的空事件初始化。
- **`MTE2_MTE3` Set/Wait（L66–67）：**生产者是 GM→UB 搬运及填充，消费者是 UB→GM 读取，保证写出看到已就绪的数据。
- 两对事件虽均用 `EVENT_ID0`，方向不同，且各自 Set/Wait 配对。它们是核内流水依赖，不是跨核同步。
- **`PipeBarrier<PIPE_ALL>()`（L212）：**在 kernel 末尾完成相关核内流水的同步收尾；没有下一轮 UB 覆盖需要另行保护。
- **`aclrtSynchronizeStream`（L266）：**host 等待 kernel 完成后，才执行360B D2H及文件写出（L268–269）。

A3/2201 的实际路径是 GM—MTE2→UB—MTE3→GM，V 只负责初始化；Scalar 发射指令并处理控制。没有 Cube、L1/L0 或矩阵格式转换。硬件流水可异步工作，但源码事件只证明上述先后依赖，不证明真实重叠率或等待时间。

## 6. 可确认范围与证据边界

以上地址、保留字节及数值结论，是由**当前源码事实、题给输入、A3 API契约**共同推导的静态结果。kernel有效搬运请求为读260B、写260B；这不等于实测HBM事务量。480B仅为可见 UB 用户数据申请量，也不代表编译产物总资源使用。

当前路径没有动态shape或stride校验；结论依赖固定参数与题给物理布局。host未检查多数运行时及文件API返回值；`ReadFile` 还会经引用修改 `inputByteSize`（`source/current/data_utils.h:25–61`）。题设完整400B输入使该处长度保持400B，不能据此保证其他文件或失败路径。

没有设备编译、运行或profiling结果，因此尚不能确认编译产物细节、API调用成功、实际事务粒度、缓存行为、物理核利用率及耗时；这些边界不改变上述代码路径与地址覆盖推导。
