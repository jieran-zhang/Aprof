本实现计算连续ND矩阵A[512,128]与B[128,128]的乘积，再逐元素执行负斜率为0.001的LeakyRelu，输出C[512,128]，输入输出均为half。更准确地说，先由Cube以half输入、float累加得到S，再经FIX将S按F322F16转换为half值H，最后执行C=H（H≥0）或half(αH)（H<0），其中α=(half)0.001，约为0.00100040436。因此激活前已有一次half舍入，不能直接等同于全float激活后才转half。依据为[源码](/tmp/eval/source/matmul_leakyrelu_basic_api.asc:115)中的Mmad、Fixpipe及LeakyRelu调用；固定文档Mmad.md、Fixpipe_L0CToGM.md和LeakyRelu.md补足类型、转换与分段公式。

main（L197起）直接把全部尺寸作为模板实参传入，没有独立host tiling函数、运行时tiling结构或workspace。A、B、C分别占512×128×2=131072、128×128×2=32768、512×128×2=131072字节。host读取x1_gm.bin、x2_gm.bin并拷入设备，启动kernel，等待stream完成，再将C拷回并写入output.bin。numBlocks=(512/256)×(128/128)=2；入口mmad_vec_custom声明__mix__(1,2)，对应两个组合，每组一个AIC、两个AIV，即2个Cube核、4个Vector核。这是本次启动的逻辑分工，不能据此推断910C整卡核数或物理核编号。

Init（L31—45）按M方向定位。根据固定语言扩展文档，Mix(1,2)中的GetBlockIdx返回逻辑编号：AIC为p=0、1，AIV为v=0、1、2、3。AIC的A、C起点都偏移p×32768个half，即p×65536字节；分别计算输出行0—255、256—511，全部128列。B没有偏移，两核各读完整B。AIV先用floor(v/2)定位Cube块，再由LeakyReluCompute中的v%2选择半块；最终C起点为v×16384个half，即字节0、32768、65536、98304，对应行0—127、128—255、256—383、384—511。各AIC输出及各AIV写回区域互不重叠，合计覆盖全部65536个输出元素。

Process的AIC分支（L50—68）用LocalMemAllocator顺序分配本地张量，不使用TPipe/TQue：L1中的a1为32768个half、64KiB，b1为16384个half、32KiB，共96KiB；独立的L0A分配64KiB，L0B分配32KiB；L0C为32768个float、128KiB。AIV各自在UB分配16384个half、32KiB。这些是每核申请量，不是全芯片共享缓冲的总量。

MTE2把A的256×128和B的128×128从GM搬到L1，同时ND转NZ。Nd2NzParams中srcDValue分别为K、N，均为128个元素；dstNzC0Stride分别为256、128，单位却是32字节，所以相邻16列条带起点间隔为8192、4096字节；dstNzNStride=1表示条带内每行前进32字节。以half元素索引表示，A的L1地址为floor(k/16)×4096+m×16+k%16，B为floor(n/16)×2048+k×16+n%16。列宽均已对齐，无需补齐；ndNum=1，两个矩阵间stride字段为0且不参与寻址。依据为L65、68及DataCopy_GMToL1_ND2NZ.md。

本题按sdk-contract.md选择__NPU_ARCH__=2201，执行L75—91的LoadData循环。每个half分形为16×16=256元素=512字节。A循环16次，第i次从L1的i×256元素处起读，repeatTimes=8，源步长16个分形，即8192字节；目的从i×2048元素处起连续放8个分形，即4096字节，不作分形内转置。它将L1按K块优先排列的NZ重排成L0A按M块、K块排列的Zz，共128个分形、64KiB。B循环8次，第i次同样从i×256元素处起读，重复8次，源步长8个分形即4096字节，目的从i×2048元素处起连续放置，并转置每个16×16分形，形成L0B的Zn，共64个分形、32KiB。这里的转置服务于存储格式，数学计算仍为A×B。所有目的偏移均满足LoadData的512字节对齐要求；srcStride是相邻起点距离，dstGap=0则表示目的分形紧接，二者含义不同。

随后每个AIC只调用一次Mmad，参数为m=256、n=128、k=128，cmatrixInitVal=true使C从零开始，cmatrixSource=false不引入Bias。整个K维已一次装入，没有跨tile或多次Mmad的K累加循环。L0C保存float、Nz格式的256×128结果。Fixpipe默认ROW_MAJOR配置将其转成GM中的half、ND；nSize=128、mSize=256，srcStride=256的单位为16×sizeof(float)=64字节，即相邻16列条带起点相差16384字节；dstStride=128的单位为half元素，故输出行距256字节。ndNum=1，矩阵间stride不生效；reluEn=false保留负值，unitFlag=0未启用分形级Mmad/FIX协同。每核写回65536字节。

每个AIV等待Cube完成后，在LeakyReluCompute（L143—176）搬入128行。DataCopyExtParams的blockCount=128、blockLen=128×2=256字节，GM行间额外间隔srcStride=(N-baseN)×2=0，UB的dstStride=0，故得到连续32768字节。GM侧stride单位是字节，UB侧是32字节块；本次均为0。虽然isPad=true，但左右padding均为0，且每行256字节已对齐，不增加元素。LeakyRelu原地处理tileLen=16384个half，再按相同128行写回原GM半块；写回时UB源stride为0，GM目的额外间隔仍为0。

依赖链由显式同步闭合：AIC在两次GM→L1之后用MTE2_MTE1事件保证LoadData读取前搬运完成；全部LoadData之后用MTE1_M保证Mmad输入就绪；Mmad后用M_FIX保证Fixpipe读取的是完成的L0C。三组SetFlag/WaitFlag虽都用EVENT_ID0，但属于不同HardEvent通路。FIX之后CrossCoreSetFlag<2,PIPE_FIX>(0)只在本组写回完成后通知对应两个AIV；模式2是组内AIC与AIV同步，不要求两个Cube组相互等待。按A3契约，CrossCoreWaitFlag会阻塞全部流水的后续指令下发，因此其后的MTE2不能提前读取C。AIV再以MTE2_V保证激活输入就绪，以V_MTE3保证写回读取激活结果。源码没有下一轮缓冲复用，故无需AIV向AIC回报消费完成。入口末尾PipeBarrier<PIPE_ALL>()收束各核流水，host的aclrtSynchronizeStream保证整个混合kernel结束后才回读输出。

这是单tile、无尾块的固定形状实现：baseM=singleCoreM、baseK=K、baseN=singleCoreN=N，尺寸均为16的倍数，且M可被256整除。模板中的singleCoreK没有驱动循环，singleCoreN只参与host核数计算；不存在通用N方向地址分核、多tile遍历或越界保护，不能仅替换常量就认定支持任意尺寸。3510分支使用LoadData2DParamsV2，并让L0A保持Nz，只是另一平台的静态对照，本题不执行；其他架构也没有对应装载分支。

以上区分了源码事实和固定API契约，没有设备运行证据。可计算所需存储量与逻辑搬运量，但材料不足以确认实际可用容量余量、物理调度、指令展开、缓存命中、时延或带宽，也不能把GM逻辑搬运量当成HBM实测流量。输入数值未提供，无法列出具体矩阵结果。分析还以文件完整、ACL调用成功及地址满足API对齐为前提：data_utils.h的ReadFile会把实际文件长度写回fileSize，main未检查读写或ACL返回值，也没有数值校验；异常文件和运行失败不在源码中形成可靠处理路径。
