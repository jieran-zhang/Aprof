本实现计算 C[m,n]=Σₖ A[m,k]·Bfile[n,k]：A 为行连续的 [8192,8192] half，B 文件为 [N,K] 行连续存储，对应逻辑 [K,N] 矩阵的转置存储；输出 C 为行连续 half。乘积在 float L0C 中累加，最后转换为 half，不包含 bias。`source/baseline/mmad.asc` 的 `main`（575—643行）为三个矩阵各分配 8192²×2=134217728 字节，即128MiB；读取两个输入文件，复制到设备，启动 kernel，等待 stream，取回并写出 output.bin。`data_utils.h` 只负责文件读写；main 未检查其返回值，因此完整有效输入是执行前提。

这里没有运行时 tiling 结构：参数由 main 的模板常量确定。SCENARIO_NUM=1 进入 Process，ProcessL2Cache 及3510分支均不执行。host 的 NPU_ARCH 与 device 的 __NPU_ARCH__ 分别选择2201参数和指令路径，不能互相替代。以下源码行号以 baseline 为准；variant 除209行删除一次等待外完全相同，见 `source/VARIANT.patch`。

`InitComputeParams`（273—307行）把24个 block 排成4份M×6份N：核号 b 对应 i=b%4、j=b/4，起点为(m₀,n₀)=(2048i,1536j)。j=0…4各负责2048×1536，j=5负责2048×512。三个 GM 起始偏移分别为2048i×8192、1536j×8192、2048i×8192+1536j，单位均为 half 元素，转字节须乘2。核内按 nBlock→mBlock→kBlock 循环：baseM=128、baseN=256、baseK=64，M循环16次，N循环6或2次，K循环8192/64=128次；没有跨核归约，每核独立完成全部K。20核各算96个输出 tile，4核各算32个，共2048个 tile、262144次 Mmad。固定尺寸均整除基本块，最后四核的512列也由两个完整 tile 组成，tailM/tailN 分支实际不被选中。

数据路径是 GM→MTE2→L1→MTE1→L0A/L0B→Cube→L0C→FIX→GM。`DataCopyInA/B`（343—389行）随搬运进行 ND2NZ：A一次搬128×512，涵盖8个K迭代；B一次搬256×256，涵盖4个K迭代，各为65536个half、128KiB。两者源行距均为8192个half。Nd2NzParams 的 dstNzC0Stride 分别为128、256，单位是32字节，并非元素；dstNzNStride=1。half的C0含16元素，例如包内(r,c)的NZ元素偏移为⌊c/16⌋×H×16+r×16+c%16，其中A的H=128、B的H=256。

`DataLoadA`（395—424行）在2201使用 LoadData3D V2，l1H=1、l1W=128、channelSize=kExtension=64、mExtension=128，把一片A装入L0A的ZZ布局。`DataLoadB`（429—496行）采用已转置存储分支，不再转置分形：循环4次，每次 LoadData2D 的 repeatTimes=16，按512字节分形连续搬运8192字节；四次共32KiB，形成L0B的ZN布局。srcStride=1和dstGap=0分别表示相邻源分形间隔512字节、目的分形连续。

`Process`（50—72行）直接构造静态 LocalTensor。构造地址是字节，长度是元素数；以下区间及表中数字均为核内相应物理存储的KiB偏移，1KiB=1024字节。A1/B1共用L1：A Ping/Pong占[0,128)、[128,256)，B占[256,384)、[384,512)。L0A的A2占[0,16)、[32,48)，L0B的B2占[0,32)、[32,64)；A2/B2地址相同也不别名，因为属于不同物理存储。唯一CO1位于L0C的[0,128)，存128×256个float。

选核0首个输出 tile C[0:128,0:256]，令t=kBlockIdx从0计数。每轮处理K区间[64t,64t+64)。A的L1切片起点为128(⌊t/8⌋%2)+16(t%8)，B为256+128(⌊t/4⌋%2)+32(t%4)；L0选择t%2。因此前十轮为：

|---|---:|---:|---:|
|0|0|256|0|
|1|16|288|32|
|2|32|320|0|
|3|48|352|32|
|4|64|384|0|
|5|80|416|32|
|6|96|448|0|
|7|112|480|32|
|8|128|256|0|
|9|144|288|32|

B每片内部四次LoadData的源、目的起点还分别加0、8、16、24KiB。前十轮始终累加到同一CO1地址0；t=0初始化C，后续累加。表中是源码选择的地址，不代表不同流水已按表逐行完成。

`ProcessLoop`（148—270行）先搬A/B Ping，包的K起点均为0。t=0发出Compute后，按B再A的源码顺序预取Pong，B从K=256、A从K=512开始。t=3释放B Ping并向其预取K=512；t=7释放B Pong与A Ping，分别预取K=768、1024。故t=8读取A Pong和已经复用的B Ping。对所选tile，起始K=q的包，A、B的GM首地址均相对各自基址偏移2q字节，但每行跨度仍为16384字节；它们不是GM中的一段紧凑连续包。

事件按“源流水_目的流水”解释，类型不同则即使ID相同也不是同一事件。初始化的 MTE1_MTE2 ID0/1管理A Ping/Pong，ID2/3管理B；首次写入先消费可写事件，搬完置 MTE2_MTE1，同一包首轮才等待就绪。因此A在t=0、8等待ID0、1；B在t=0、4、8等待ID2、3、2。包的最后切片完成Load后，MTE1置反向事件，允许MTE2覆盖L1。此时无需等待Cube，因为操作数已经进入L0。

baseline每轮还先等待 M_MTE1 ID=t%2，再装载L0；装载后用 MTE1_M Set/Wait 保证Cube能读，Mmad后置 M_MTE1 释放该槽。初始化两个释放事件供t=0、1消费，随后形成 Compute(t)完成→Load(t+2)覆盖的依赖，同时允许另一槽搬运与计算重叠。收尾等待消费剩余两槽释放事件及四个L1可写事件。K循环128次为偶数，下一输出tile仍从L0 Ping开始。

`Compute/CopyOut`（501—541行）每轮Mmad为128×256×64。前127次unitFlag=2，最后一次=3；Fixpipe也为3，按L0C内存块建立计算完成→搬出→下一tile复用的关系。Fixpipe默认NZ2ND，srcStride=128的单位是16×sizeof(float)=64字节，dstStride=8192的单位是half元素；每tile输出128行、每行512字节、行距16384字节。F322F16按文档采用CAST_RINT转换。kernel最后还有PIPE_ALL屏障。固定tile的(128/16)×(256/16)=128，大于Mmad文档的小矩阵阈值10，因而不能仅凭未写PIPE_M屏障认定K累加缺少同步。

variant删除209行后，L1保护和装载→计算的正向依赖仍在，但计算→L0覆盖的反向依赖不再成立：t=2可覆盖仍被t=0计算读取的地址。Pong只延后复用两轮，并不能证明旧读取已经完成。更直接地，初始化的 M_MTE1 ID0、1未被消费，t=0、1又分别置同一事件，随后持续重复置位。每tile每槽新增64次Set，而循环中没有Wait，整个ProcessLoop末尾每槽只Wait一次。

固定rawdocs的 SetFlag/WaitFlag 契约规定：Set等待源流水前序读写完成，但不阻塞后续源指令；Wait消费并清零标志，二者必须配对；同类型同ID未经消费连续Set属于未定义行为，并给出后续屏障卡死示例。因此变体既失去可证明的L0生命周期依赖，也违反事件配对约束。正向等待、L0C的unitFlag、末尾屏障都不能补回循环内缺失的依赖；静态材料支持“无正确执行保证”，不能断言实际必然出现某个错误值或必然卡死。

以上硬件解释依据 `workload/sdk-contract.md` 指定的910C/Atlas A3、2201契约，以及rawdocs中ND2NZ、LoadData、Mmad、Fixpipe、UnitFlag和核内同步文档。24是启动block数，不能据此声称设备恰有24个物理核或测得重叠、带宽和性能。固定参数没有K尾包问题，但源码未实现通用K尾处理；本地分配要求L1覆盖512KiB、L0B覆盖64KiB、L0C覆盖128KiB。UnitFlag文档还要求计算方向匹配输出布局，而源码未显式设置方向，InitSocState内部及默认配置未展开。没有编译和设备观测，不能把baseline的依赖设计进一步等同于已验证的运行结果、数值误差或性能。
