该程序计算 half 矩阵乘后接 LeakyReLU，输入 A、B 分别是连续行优先 ND 的 [512,128]、[128,128]，输出是同样连续 ND 的 half 矩阵 [512,128]。对每个输出位置，先由 Cube 计算 S[m,n]=Σ(k=0…127) A[m,k]B[k,n]，在 float L0C 中累加；再由 Fixpipe 按 F322F16（文档规定 CAST_RINT）转换为 half 值 H；最后 Vector 对 H≥0 保留原值，对 H<0 计算 half 斜率乘 H。斜率是源码的 `(half)0.001`，其值约为 0.0010004043579101562。因此实际精度顺序包含激活前的一次 float→half 转换，不能直接等同于先在 float 中完成激活再转 half。

完整调用位于 `source/matmul_leakyrelu_basic_api.asc`。`main`（197–259 行）把全部尺寸作为编译期模板参数，没有独立 tiling 函数或 tiling 数据结构。A、B、C 分配量分别为 512×128×2=131072B、128×128×2=32768B、512×128×2=131072B，即 128、32、128KiB。host 从 `input/x1_gm.bin`、`input/x2_gm.bin` 读入并复制到 device，启动 kernel，等待 stream 完成后将 C 复制回 host，写入 `output/output.bin`，随后释放资源。kernel 不需要外部 workspace。

`numBlocks=(512/256)×(128/128)=2`，入口 `mmad_vec_custom`（188–195 行）使用 `__mix__(1,2)`：启动两个组合，每组一个 AIC、两个 AIV，共两个 AIC、四个 AIV。这是本次启动的分工，不是芯片总核数。固定契约指定 910C/Atlas A3、`__NPU_ARCH__=2201`。本地 `simd_builtin_keywords.md` 明确：混合模式下基础 API `GetBlockIdx()` 返回展平逻辑索引，因此 AIC 为 0、1，AIV 为 0、1、2、3；它不同于组合内共享的内置 `block_idx`。

`KernelMatmul::Init`（31–45 行）中，AIC g 的 A、C 基址均偏移 g×256×128 个 half，即 g×65536B。AIC0 负责输出行 [0,256)，AIC1 负责 [256,512)，都覆盖全部 128 列和全部 K。B 不偏移，两核各读取完整 B。AIV v 先用整数除法 v/2 找到所属 Cube 块，再在 `LeakyReluCompute`（143–176 行）中按 v%2 偏移 128×128 个 half。四个 AIV 依次处理行 [0,128)、[128,256)、[256,384)、[384,512)，在整个 C 中的起始元素偏移为 0、16384、32768、49152，字节偏移为 0、32768、65536、98304。各自覆盖 16384 个 half，输出范围互不重叠。

AIC 的 `Process`（50–129 行）直接使用 LocalMemAllocator 分配本地张量，不使用 TPipe/TQue。每核 L1 的 A1 为 32768 个 half（64KiB），B1 为 16384 个 half（32KiB），合计 96KiB；L0A 的 A2 为 half、64KiB，L0B 的 B2 为 half、32KiB，L0C 的 C 为 32768 个 float、128KiB。每个 AIV 的 UB 是 16384 个 half、32KiB。Alloc 的长度单位是元素，以上是各存储层的申请量，不能跨层相加当作单一 SRAM 容量。

两次 `DataCopy`（65、68 行）由 MTE2 完成 GM→L1，并随路 ND→NZ。A 的参数 `{1,256,128,0,128,256,1,0}` 表示搬一个 256×128 矩阵，源行距 128 个元素；目的 `dstNzC0Stride=256`、`dstNzNStride=1` 的单位都是 32B，分别为 8192B、32B。B 对应一个 128×128 矩阵，源行距同为 128 个元素，目的上述间距为 4096B、32B。只有一个矩阵，两项矩阵间 stride=0 不参与寻址。以各 L1 张量起点为基准，A[m,k] 的 half 元素偏移是 `(k/16)×256×16+m×16+k%16`，B[k,n] 是 `(n/16)×128×16+k×16+n%16`，其中除法取整数商。

2201 的 L1→L0 使用 `LoadData2DParams`（75–91 行）。half 分形为 16×16，即 256 个元素、512B。A 循环 16 次，每次搬 8 个分形：源起点 i×256 个 half，相邻 repeat 源起点相距 16×512=8192B；目的起点 i×2048 个 half，目的分形连续、不转置。合计 128 个分形，形成 L0A 的 Zz 排布。B 循环 8 次，每次也搬 8 个分形，源起点 i×256 个 half，源 repeat 间距 8×512=4096B，目的起点 i×2048 个 half；每个 16×16 分形转置，形成 L0B 的 Zn 排布。这里是存储分形转换，逻辑乘法仍为 A×B，没有把输入 B 改成数学意义上的 Bᵀ。各起点及步长满足这些搬运所需的对齐。

`Mmad`（115 行）只调用一次，参数为 m=256、n=128、k=128，`cmatrixSource=false`、`cmatrixInitVal=true`，因此从零开始得到完整单核结果，不依赖 L0C 旧值或偏置。没有跨 tile 的 K 累加循环；两核总计完成 512×128×128=8388608 次乘加。C 在 L0C 中为 float NZ。`Fixpipe`（125–127 行）将整个 256×128 块转为 half ND 写入 GM；nSize=128、mSize=256，源 stride=256 个 `16×sizeof(float)=64B` 单位，即 16384B，目的 stride=N=128 个 half，即每行 256B。它关闭普通 ReLU，保留负值交给后续 LeakyReLU；ndNum=1，两项矩阵间 stride 无效。Mmad 和 Fixpipe 的 unitFlag 都是 0，没有启用按分形计算、搬出的细粒度联动。

AIV 等待 Cube 后执行 `DataCopyPad`（155–158 行）：blockCount=128，blockLen=128×2=256B，GM 源行间空隙 `(N-baseN)×2=0B`，UB 目的空隙为 0 个 32B 块。因此实际连续读取 32768B。虽然 isPad=true，但左右 padding 都是 0，且每行已按 32B 对齐，不增加填充值。随后 `LeakyRelu` 原地处理 count=16384 个 half；这里 count 是元素数。最后反向 DataCopyPad 连续写回同一区域，UB 源空隙单位为 32B、GM 目的空隙单位为字节，本例均为零。

依赖保障来自显式事件，而不是函数调用顺序本身。AIC 依次以成对 SetFlag/WaitFlag 建立 MTE2_MTE1、MTE1_M、M_FIX，使 GM→L1 完成后才能读取 L1，L1→L0 完成后才能矩阵计算，矩阵计算完成后才能由 FIX 读取 L0C。之后 `CrossCoreSetFlag<0x2,PIPE_FIX>(0)` 在 FIX 前序操作完成后通知本组合的两个 AIV。A3 支持模式 2；其配对 `CrossCoreWaitFlag<0x2>(0)` 阻塞后续所有流水指令下发，所以 AIV 的 GM 读取在 Cube 写回完成之后。它不是两个组合间的全局屏障。AIV 再以 MTE2_V 和 V_MTE3 事件保证 UB 输入就绪、激活完成后才写回。各核内事件虽都用 EVENT_ID0，但分别属于不同 HardEvent，且均配对消费。当前仅一个 tile，不复用 Cube 输出，两个 AIV 又写不同半区，因此没有下一轮覆盖需要的反向握手。入口最后的 `PipeBarrier<PIPE_ALL>()` 收束本核流水，host 的 stream 同步覆盖整个 kernel 完成后才回读输出。

按 API 请求的数据量，两个 AIC 共读 A/B 192KiB、写中间 C 128KiB，四个 AIV 共读写 C 256KiB，合计 GM 搬运 576KiB；这不等于实测 HBM 流量，缓存及实际调度未观测。两组之间没有数据依赖，具备独立执行条件；组内 Vector 要等整个 Cube 块写回。源码没有双缓冲或多 tile 流水。

上述单位、排布与同步由本地 rawdocs 中的 DataCopy_GMToL1_ND2NZ、LoadData_2D、Mmad、Fixpipe_L0CToGM、DataCopyPad、LeakyRelu 和核内/核间同步文档补足。3510 分支采用 LoadData2DParamsV2，L0A 注释为 Nz，只是另一平台的静态对照，不参与本次 2201 数据路径，也不能据此证明完整源码在 3510 可运行。
