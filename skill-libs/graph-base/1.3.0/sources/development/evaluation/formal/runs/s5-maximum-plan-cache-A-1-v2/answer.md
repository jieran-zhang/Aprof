## 结论与状态

本轮选择一个**条件化、可交给 C2/C3 落地的连续搬运合并方案**，a、b 使用相同生产 kernel 方案：

> 在同一 core 的连续区间内，将相邻两个 4096 元素 tile 的输入、输出搬运合为最多 8192 元素的一组；计算仍分成原来的两个 `Max(..., count≤4096)`，不更换数值 API、不增加流水槽、不改核间所有权。

选择它的理由是：它能从源码直接推导出搬运调用和队列管理次数的减少；相比双输入槽预取，不依赖“新增重叠窗口能隐藏多少时间”的判断。代价是多 tile core 的显式 UB 数据区由 **48 KiB 增至 96 KiB**，并延长输入、输出存活期。原单次搬运已经是 16 KiB，**不能因此判定当前是小包 setup 瓶颈，也不能承诺合并后加速**。

最有竞争力的结构性替代是：**保持 4096 元素计算粒度，两个输入各双物理槽、输出单槽，建立一 tile 超前预取**。它的数据区为 80 KiB，不减少调用或必要字节，但可能增加合法重叠。

本轮仅完成纸面选择、条件规划及实施交接，**未修改、未编译、未运行，也未完成正式机器登记**。当前实现保留为原始源码。容量、SDK 和别名合同的具体门禁见下文；缺少性能测量不是否决本方案的理由。

# 一、两子例共用的当前实际路径

### 1. 数学及实际分支

当前输入是 sameShape、float32，执行路径为：

`maximum_kernel` → `DispatchMaximum<float>` 的 sameShape 分支 → `KernelMaximumSame<float>`。

对应源码为 `maximum_kernel.asc:173–180、164–168、9–67`。

每个有效元素执行：

\[
y_i=\operatorname{Max}_{当前AscendC调用}(x1_i,x2_i)
\]

这是逐元素 Maximum，无归约、无跨元素递推。float 分支直接执行第 61 行的 `AscendC::Max`，**不执行 BF16/INT8 的 Cast 和临时区路径，也不执行广播坐标解码**。

有限、非 NaN 不排除正负零。本方案保留同一个 Max API、操作数顺序及每个原计算片段，不引入“Max 与比较选择是否等价”的新问题。

### 2. 分核与覆盖

设实际启动 core 数为 \(C=t.blockNum\)，分区长度为：

\[
B=\lceil N/C\rceil,\quad
b_c=cB,\quad
n_c=\min(B,\max(0,N-b_c))
\]

core \(c\) 独占输出区间 \([b_c,b_c+n_c)\)。用户已明确这些区间连续、互斥并完整处理尾部，本轮不改变它们。

Host 对当前 \(N=1048576\) 算出的 useful 为 256，但**没有给出实际 `cores` 和启动证据，不能直接认定 C 为某个硬件核数**。

定义：

\[
T=4096,\qquad k_c=\lceil n_c/T\rceil,\qquad K=\sum_c k_c
\]

\(N/T=256\) 并不意味着实际总 tile 数一定为 256，因为核边界可能产生核内短尾。一般有：

\[
256\le K\le 256+C-1
\]

### 3. 当前数据流、工作量和依赖

每个 tile：

1. 两次 GM→UB `DataCopyPad`，各搬 `valid*4` 字节；
2. 输入队列 `EnQue/DeQue` 后执行一次 `Max`；
3. 输出队列发布后，一次 UB→GM `DataCopyPad`；
4. 按队列协议释放输入、输出槽。

数据路径为：

`GM --MTE2--> UB --Vector Max--> UB --MTE3--> GM`

VECIN/VECOUT 都是 UB，不是不同物理存储层。

当前每 core 显式数据分配：

\[
3\,AlignUp(4T,32)=49152\text{ B}=48\text{ KiB}
\]

float 路径没有初始化那些类型转换 TBuf。这里的 48 KiB 是所列数据区，**不是完整编译产物全部 UB 使用量的证明**。

整个 Maximum 的必要有效请求为：

- x1：4 MiB；
- x2：4 MiB；
- y 写出：4 MiB；
- 合计：**12 MiB，即 12,582,912 B**。

这是逻辑有效 GM 请求，不是实测 HBM 字节。源码级调用为 `2K` 次输入搬运、`K` 次 Max、`K` 次输出搬运，以及每 tile 三组 Alloc/EnQue/DeQue/Free，即约 `12K` 次队列接口调用。

需要保留四类依赖：

- MTE2 写输入完成 → V 读输入；
- V 最后读输入完成 → 下次 MTE2 覆盖该输入槽；
- V 写输出完成 → MTE3 读输出；
- MTE3 读输出完成 → 下次 V 覆盖输出槽。

当前队列骨架承担这些依赖。**单槽限制了一些预取机会，但不能推断整个 kernel 完全串行**；例如下一 tile 的搬入可能与上一 tile 的搬出重叠。

# 二、子例 a：输出只 D2H 一次

## 1. 关键事实与选择

生产 kernel 的工作量就是上述 12 MiB、\(K\) 个 Max 片段。完成后还需传输 4 MiB 输出到 Host；该 D2H 必须保留，不能算成可消除的中间 GM 往返。D2H 的实际缓存通路没有提供。

选择 **S-a-merge2：同 owner 两 tile 搬运合并**。没有后续设备消费者，因此不存在本轮可融合的设备计算链。

## 2. 主方案的全部工作变化

对每个 core，把原来最多两个相邻 tile 组成一组：

\[
k'_c=\lceil k_c/2\rceil=\lceil n_c/(2T)\rceil,\quad
K'=\sum_c k'_c,\quad
\Delta=K-K'=\sum_c\lfloor k_c/2\rfloor
\]

| 项目 | 原实现 | 主方案 |
|---|---:|---:|
| 输入搬运调用 | \(2K\) | \(2K'\) |
| 输出搬运调用 | \(K\) | \(K'\) |
| Max 调用 | \(K\) | **仍为 \(K\)** |
| 队列接口调用 | 约 \(12K\) | 约 \(12K'\) |
| Maximum 有效 GM 请求 | 12 MiB | 仍为 12 MiB |
| 后续 D2H | 4 MiB | 仍为 4 MiB |
| 多 tile core 的显式数据区 | 48 KiB | 96 KiB |

因此减少 `3Δ` 次搬运调用及约 `12Δ` 次队列接口调用，不把 Max 调用减少夹带进去。

最大搬运长度为：

\[
8192\times4=32768\text{ B}
\]

仍使用有效字节长度的 DataCopyPad。8192 是本轮“合二为一”的候选参数，不是目标平台最优阈值。

**新增代价：**

- 显式数据区增加 49,152 B/core；
- 第一份输入要存活到该组全部 Max 读完；
- 第一段输出需等第二段生成后一起搬出；
- 计算子片循环和最后一组判断；
- 可能因更大工作集、较晚写回或缓存行为变化而回退。

不会初始化整块 UB，也不会把对齐 dummy 加入有效计算。因 \(T\) 本身为 32B 对齐长度，合并不需要新增有效元素计算或整块补零。

**实际优化覆盖**是 \(k_c\ge2\) 的 owner。单 tile owner 没有可合并工作，应保留原单槽、原容量路径。若当前实际分核恰使每核只有一个 tile，则该 workload 不执行这一变换，不能把增加空闲 UB 分配称作优化。

## 3. 最强替代：双输入槽预取

保持 \(T=4096\)，x1/x2 各两个物理槽，y 一个槽：

\[
U_{\rm data}=5\,AlignUp(4T,32)=81920\text{ B}=80\text{ KiB}
\]

- 有效 GM 字节、三路搬运次数、Max 次数均不变；
- 输入槽代次、预取序言、next-tile 判断和排空逻辑增加；
- 多占 32 KiB 显式数据区；
- 不改变 D2H；
- 可能让下一 tile 搬入与当前计算、已有搬出窗口交错，但 y 单槽仍保留输出复用约束。

选择合并而不是它，是因为本轮优先检验**确定减少发射和管理次数**的预测。预取方案更省 UB，且若实际等待主要来自输入槽复用，它可能更优；这一排序不是测量结论。

# 三、子例 b：输出随即由设备 kernel 完整顺序读取

## 1. 当前路径与新增依赖

Maximum 内部路径、数学、12 MiB 请求和 \(K\) 个计算片段与 a 完全相同。

区别在输出生命周期：

`Maximum 写完整 y` → **kernel/stream 完成依赖** → `后继 kernel 顺序读完整 y`

后继已知读取 4 MiB y，因此已知这段生产消费链的有效请求为：

\[
12+4=16\text{ MiB}
\]

这不包括后继 kernel 未提供的其他输入和输出，不能称为整个后继链总流量。

## 2. 主方案及成本变化

选择 **S-b-merge2**，与 a 使用同一实现骨架及参数：

- 输入搬运：`2K → 2K'`；
- 输出搬运：`K → K'`；
- Max：仍为 `K`；
- 队列接口：约 `12K → 12K'`；
- Maximum 仍请求 12 MiB；
- 下游仍读取 4 MiB；
- 多 tile core 数据区仍由 48 KiB 增至 96 KiB。

与 a 相比：

- 更晚形成部分输出**不破坏本例的消费次序**：给定的是 Maximum 完成后才启动的独立 kernel，不是逐 tile 提前消费协议。
- 但生产者的访问节奏可能改变完成时 y 的缓存状态，进而影响下游读等待；这是 a 没有的设备端成本。
- 本轮**不修改 y 的 cache hint**，也不声称保留 NORMAL 能保证 4 MiB y 驻留。

仍选合并，是因为它减少生产者调用次数的静态依据未变，而本轮没有增加跨 kernel 协议或改变下游数学的条件。

## 3. 最强可规划替代及融合机会

可完整规划的竞争替代仍是上一节的 **80 KiB 双输入槽预取**：调用数、生产消费字节都不减少，只改变生产者排程；它同样可能改变下游看到的缓存状态。因此 b 后续必须比较生产者和后继完整序列，不能只看 Maximum 单 kernel。

另有潜在更大机会——融合消费者：

- 若 y 只是可删除的内部边，理论上最多可省去 y 的一写一读，即 **8 MiB**，并减少一次 launch；
- 若 y 仍需外部物化，则不能把这 8 MiB 全部计作可消除量；
- 目前只有“完整顺序读”，没有消费者数学、其他输入、输出 owner、布局、核角色和外部可见性合同。

所以本轮不实例化 ready 的 `action.fuse_kernel_chain`。缺的是**融合合法边界及完整消费者合同**，不是缺性能测量。取得这些材料后，融合可能改变下一轮优先级。

# 四、影响选择的其他机会

这些结论分别用于 a、b，而不是因找到一个 ready Action 就停止比较。

| 方向 | 当前判断及正文对判断的影响 |
|---|---|

| 输出统一 bypass | 不采用。b 有明确近邻设备读，不能因生产 kernel 内只写一次就当作整个序列无复用。a 的 D2H 缓存路径也未提供；所给 cache recipe 的明确实现片段是输入读策略，不能据此冒充输出写方向已核验。 |

| 改核数、均衡尾部 | 用户已给均匀连续分区；没有实际核数不足或集中尾工作的新依据。保留核分区，不套来源固定核数。 |

# 五、Action 实例与统一 C2 交接

## 1. 纸面登记

a、b 各登记一个相同模板的 workload 实例，不是叠加两个变换：

| 项目 | a | b |
|---|---|---|
| 实例 | `A-a-merge2` | `A-b-merge2` |
| 注册 Action | `action.coalesce_contiguous_transfers` | 同左 |
| 父实现 | 输入所给原始 `KernelMaximumSame<float>` | 同左 |
| 目标 | 同 owner 的 x1/x2 CopyIn 与配套 y CopyOut | 同左 |
| 阶段 | Init 分配、核内连续 tile 循环 | 同左 |
| 参数 | 计算片 T=4096 元素；搬运组最多 2T | 同左 |
| 预测 | 少 `3Δ` 次搬运及约 `12Δ` 次队列接口调用 | 同左；另观察下游读成本 |

一个 Action 已足够。输出合并是这次扩大连续搬运组的配套实现，不额外凑 `batch_writeback`；Max 调用没有合批，不登记 `batch_vector_api_calls`。

Action 使用输入提供的 D v0006 正文。父源码和模板的精确 hash 本轮没有计算，故这里是**纸面实例登记**，不是已通过 runtime 校验的正式实例。后继封存时须补真实内容 hash，不能填虚构值。

## 2. 条件状态

- `symptom.source.inner_loop_copy=true`：第 39、40、65 行位于 tile 循环。
- 相邻性：同 core 原 tile 的末端等于下一 tile 起点；只能在该 owner 内合并。
- 数学等价：保留原 Max 调用及有效计算子域；没有 Cast、归约重排。
- 覆盖与唯一写者：沿用原 \([b_c,b_c+n_c)\)，合并不越核。
- **capacity：待补当前可用 UB 与完整保留区。**
- **SDK/API：待绑定实际目标 SDK，确认所用重载及分配预算。**
- **别名：输入未给完整合同。**输入输出不重叠，或仅精确原址且无跨元素别名时，可按上述独立元素关系证明；部分重叠 view 不能直接授权这种提前读下一片的重排。不得新增 `restrict` 假设，应保留原受支持路径或补接口依据。

后面三项是实施前门禁；“setup 是否关键”“总时间是否改善”只是待测试预测。

## 3. 共同计划

建议新计划身份为 **`p_same_merge2_paper`**，当前尚未封存 hash。

- **所有权**：原 core 连续区间不变。
- **布局**：GM、UB 均为连续 FP32；每组有效长度 \(v\le8192\)，计算按两个最多 4096 的子视图执行。
- **workspace**：0；不引入 GM 中间值。
- **物理数据区**：

\[
U_{\rm merge}=3\,AlignUp(4U,32)+H_{\rm merge}
\]

其中多 tile owner 的 \(U=8192\)，单 tile owner 保留 \(U=4096\)；\(H_{\rm merge}\) 为实际框架/API 保留等未包含部分。必须满足：

\[
U_{\rm merge}\le U_{\rm available}
\]

96 KiB 是数据区，不默认把标称物理 UB 全部当作可分配预算。

- **同步**：仍由一套 TPipe、三条单物理槽队列管理；输入最后读者扩大为整组所有 Max，输出发布点移到整组计算完成后。无新增跨核事件。
- **输出外部依赖**：a 保留完成后 D2H；b 保留生产 kernel 完成后再消费。
- **缓存**：本方案不改变 hint；不将未测命中填为事实。
- **分派**：沿用 `maximum_kernel` 和既有 dtype/sameShape 结构，不为 a/b 增加 Key。实际 launcher、机器 dispatch 身份及启动证据仍待工程接线核验。

### KEEP 判断

**不能 P_KEEP 原 `p_same` 来授权这次变化。**它只声明三个 4096 元素单槽，未授权本次更大物理区及延长的生命周期。即使 owner 不变，也需要 **P_CHANGE**。

新记录应分清：

1. 原所有权和 fallback 路径的**提取/补全文档**；
2. 搬运组、容量及生命周期的**真实变化**。

不能把前者统计成并行优化，也不能用 `p_same` 为 broadcast/int64 背书。

未命中新方案域时保留原 `DispatchMaximum`。其中 float 广播和 int64 的通用索引路径可单独提取计划，仍未完成动态验证。原 half 非 sameShape 分派直接进入 LastAxisBroadcast，其适用形状是否由上层保证，当前材料未闭合；本轮不夹带修复，也不宣称其已覆盖全部合法 half 广播。

# 六、C3 准确实施步骤与 P/O 正文影响

以下是交接步骤，**不是已产生的 patch**。

## 1. 主方案实施步骤

1. **先补门禁**：绑定 SDK、可用 UB/保留区及别名合同，封存父源码和 Action 正文身份。
2. 仅在获批的 sameShape FP32 路径实现新循环，其他路径保留。
3. 取原计算片大小 `T=4096`。多 tile owner 申请 x1/x2/y 各 `2*T*4` 字节，仍各一物理槽；单 tile owner保留原容量。
4. 外循环按最多 `2*T` 个有效元素推进，先计算 `v=min(U,length-off)`，再构造地址。
5. 每组仅发两次输入 DataCopyPad，`blockLen=v*4`、stride 为 0；不得向上扩大 GM 有效读取。
6. 输入 EnQue/DeQue 后申请一份输出。依次执行：
   - 第一个子片：`Max(out,a,b,min(T,v))`；
   - 若 `v>T`，第二个子片：在各 local tensor 的 `T` 元素偏移处执行 `Max(...,v-T)`。
   
   两次调用写不相交输出，所有有效 Max 的操作数顺序和原计算片段保持不变。
7. 所有子片计算发射后才发布整组输出并交回输入槽；队列依赖须覆盖**最后一个子片的输入读取**。
8. 输出 DeQue 后一次 DataCopyPad 写回 `v*4` 有效字节；MTE3 最后读取完成前不得复用输出槽。
9. 空 owner 不发 DMA/Max；短组只计算有效子片。保留正常队列收尾，不新增每组 `PIPE_ALL`。
10. 后继工程阶段再做审查、目标 SDK 构建、完整 oracle 和边界检查。任何源码变化后不得复用旧正确性资格。

## 2. 竞争替代的闭合排程

若后续重选双输入槽预取，不能只把 `InitBuffer` 的 num 改成 2。一个符合 depth=1 的骨架是：

- 序言只搬 tile 0，并各 EnQue 一次；
- 当前输入 **DeQue 后**，才向另一物理槽搬 next tile 并 EnQue；
- 再申请输出、计算当前 tile、按队列协议释放当前输入并搬出；
- 最后一轮不发 next；退出时排空已提交操作。

这样每条输入队列最多一个未 DeQue 项。当前输入和 next 输入同时存活，故需四份输入区；y 仍单槽。不能连续两次 EnQue 后才首次 DeQue，也不能将 DeQue 当作最后读取完成。

## 3. 实际采用的知识

| P/O 正文 | 对本方案的实际影响 |
|---|---|
| `planning.elementwise.continuous` | 采用连续 owner、有效长度循环和按物理份数计字节的合同；保留当前已证明的分区，不擅自改成模板的 q/r 分区公式。 |
| `implementation.memory-transfer.coalesce` | 限定只合并同 owner 相邻区间；促成“两倍搬运组、保留原 Max 子片”的实现，而不是换算法或删字节。 |
| `implementation.tiling-tail.valid-length`、`precision-boundaries.bounds` | 将有效 count、UB 分配长度、API 字节字段分开；禁止补齐 GM 读写或整块清零。 |
| `implementation.pipeline-sync.pipeline` | 用于核验扩大后的最后消费者，并形成竞争预取方案；正文阻止把双槽声明当作已有效重叠。 |
