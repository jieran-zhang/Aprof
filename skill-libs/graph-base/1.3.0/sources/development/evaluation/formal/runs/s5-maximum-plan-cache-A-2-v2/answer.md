## 结论与交接状态

**本轮为 a、b 选择同一个条件化方案：仅对实际的同形 FP32 路径建立“一 tile 前瞻”的输入软件流水，两个输入各用两个物理槽，输出仍用一个槽；保持 `tileElements=4096`、原分核、原 `Max`、有效尾长及 GM 输出不变。缓存策略本轮不改。**

选择的注册意图为 `action.software_pipeline_stages`，不再为增加槽、调整循环和处理尾块拆出其他 Action。

这是**纸面 C1→C2→C3 条件交接**，不是已实施候选：

- 已有源码足以指出独立 tile 和可建立的预取窗口，不因缺少 overlap 测量否决试验。
- 实施前仍须闭合实际可用 UB、目标 SDK 队列资源、输入输出别名契约。下面给出具体门禁，不能预填为 true。
- 本轮没有修改、编译、测试或计时；状态为 `conditional_plan / not_measured`，不声称正确性通过或确定加速。
- 不虚构 router 执行结果、源码 hash、模板 hash 或机器契约验证。本文按输入正文手工路由；正式产物身份需后继补齐。

## 一、共用的当前实现理解

### 1. 实际数学与分支

两个子例当前均执行 `KernelMaximumSame<float>`，并非 `MaximumScalar<float>`。实际计算为：

\[
y_i=\operatorname{Max}_{FP32}(x1_i,x2_i),\qquad 0\le i<N,\quad N=1048576
\]

依据：

- 入口与分派：`maximum_kernel.asc:154–182`；
- 同形 FP32 实际计算：`:44–62` 中最终进入 `AscendC::Max(out,a,b,count)`；
- 没有执行 BF16/INT8 的 Cast 链，也没有执行广播坐标解码。

本轮保留相同 API、输入顺序、FP32 表示及有效 count。有限非 NaN 不排除正负零和次正规数；因此不把 `Max` 改成三元选择、Compare/Select 或低精度计算，也不声称这些替换天然等价。

### 2. 分核与 tile 数

令实际启动核数为 \(C\)，`blockLength=B`。核 \(c\) 的区间为：

\[
O_c=cB,\qquad L_c=\min(B,\max(N-O_c,0))
\]

其 tile 数：

\[
K_c=L_c/4096+[L_c\bmod4096\ne0],\qquad K=\sum_c K_c
\]

源码位置为 `:12–17、31–34`。用户已给定区间互斥、均匀且尾部完整处理，本轮不重新分配所有权。

若按给出的 tiling 公式：

\[
C=\max(1,\min(\text{cores},256)),\quad B=\lceil N/C\rceil
\]

实际核数未知，**不能直接把全调用 tile 数写成 256**。核边界可能产生额外短 tile；对这些非空连续分区，有：

\[
256\le K\le256+C-1
\]

### 3. 当前数据流与依赖

每 tile 当前顺序为：

```text
分配 a、b
  → 两次 GM→UB DataCopyPad
  → 输入 EnQue/DeQue
  → 分配 out，Max
  → 输出 EnQue，归还 a、b
  → 输出 DeQue
  → UB→GM DataCopyPad
  → 归还 out
```

对应 `:35–66`。VECIN、VECOUT 都是 UB，不是两个物理存储层。

当前每个输入只有一个物理槽。下一 tile 输入覆写必须等待当前 Vector 最后读取结束，因此没有独立输入槽承载“下一 tile 搬入与当前 tile 计算”的窗口。但这**不证明所有阶段完全串行**：当前实现仍可能让后续搬入与先前搬出存在重叠。

### 4. 可直接算出的工作量

令 \(W=4N=4194304\) B，即每个完整 tensor 为 4 MiB。

| 项目 | 当前 Maximum 的逻辑工作 |
|---|---:|
| x1 读取 | \(W\) |
| x2 读取 | \(W\) |
| y 写出 | \(W\) |
| 合计有效 GM 请求 | \(3W=12582912\) B，12 MiB |
| DataCopyPad 调用 | \(2K\) 次搬入、\(K\) 次搬出 |
| Max 调用 | \(K\) 次，总有效元素 \(N\) |
| 满 tile 每路有效字节 | \(4096\times4=16384\) B |
| 显式数据区分配 | \(3\times16384=49152\) B，48 KiB |

这是请求层和源码调用量，不是实测 HBM 字节、硬件指令数或时间占比。

## 二、子例 a：输出仅 D2H 一次

### 当前路径和关键事实

Maximum 的计算、分核及上述工作量全部适用。随后 y 必须保持外部可见，供一次 4 MiB D2H 使用；没有后继设备 kernel 读取 y。

关键判断：

1. 两个输入各读一次，无跨调用复用，**不存在输入驻留可删除的重读**。
2. y 的最终 GM 写出不能删除；D2H 不是本核 UB 消费者。
3. 没有真实 cache 管理周期或命中数据，不能判断默认缓存一定拖慢这次扫描。
4. 本核若有至少两个 tile，存在独立的输入预取对象；若只有一个 tile，则没有此机会。

### 主方案：输入双槽、一 tile 前瞻

减少的不是字节或数学工作，而是**单输入槽对下一 tile 发射的限制**。

- 保留：\(2W\) 输入读、\(W\) 输出写、\(N\) 元素 Max、\(3K\) 次搬运、\(K\) 次 Max。
- 新增物理数据区：
  \[
  U_{\rm data}= (2+2+1)\operatorname{AlignUp}(4T,32)
  \]
  \(T=4096\) 时为 **81920 B，80 KiB**，比当前增加 **32768 B，32 KiB**。
- 新增：序言、前瞻有效性判断、槽代次和排空审计；队列内部同步资源可能增加。
- 不新增：GM workspace、Cast、padding 数学计算、额外 GM 请求、额外 launch。
- 优化覆盖：本核 \(K_c\ge2\) 的输入搬入/计算窗口；首 tile 没有可隐藏的前序计算，最后 tile不再预取。
- 未优化：必要输入输出字节、输出单槽约束及 D2H。

a 没有设备下游消费，因此本方案只预测可能改善 Maximum 本身的执行，不预测 D2H 缓存收益。

### 最有竞争力替代：一次性输入的缓存策略试验

按 `action.align_cache_policy`，仅对 x1、x2 设置 `CACHE_MODE_DISABLE`，**y 保持原默认策略**。

其完整变化为：

- 逻辑 GM 字节、所有调用数、算术、tile、队列和 48 KiB 数据区均不变；
- 每个活动核初始化阶段增加两次 hint 设置；
- 不申请额外 UB，不删除事件；
- 因输入 \(q=1\)，不存在可以依赖的 \((q-1)W\) 输入复用收益；预测仅为可能减少一次性填充/替换成本；
- 也可能无收益或回退，实际 HBM 流量和等待未知。

a 的输出没有设备复用，扩大到“输出也 bypass”看似值得研究，但给定 cache 配方展示的是输入读取设置，**不足以证明当前 SDK、输出写方向的具体支持与效果**。本轮不把它当成就绪实现，更不把“一次 D2H”解释为可省输出写入。

本轮优先流水的理由是：源码直接暴露了单输入槽的依赖限制，而 cache 改动是否有利完全取决于未提供的管理和替换成本。这个排序仍可能被实际核数、UB 或编译后调度改变，不是瓶颈定论。

## 三、子例 b：输出立即被设备 kernel 完整顺序读取

### 当前路径和新增依赖

Maximum 本身仍是上述相同路径。其后多了：

```text
Maximum 的完整 GM 输出
  → 合法的跨 kernel 执行依赖
  → 消费 kernel 顺序读取全部 y
```

后继读取 y 的有效请求是另一个 \(W=4\) MiB。因此只统计已知的数据边，生产者加这一项消费读共 **16 MiB**；消费者其他输入、计算及输出未提供，不能补造。

“立即消费”不等于已经命中 L2，也不意味着两个 kernel 的 UB 连续存在。

### 主方案与 a 相同，但评价范围不同

仍采用输入双槽、输出单槽：

- Maximum 的字节、算术、调用数和 **80 KiB** 数据区与 a 相同。
- 后继完整读取的 4 MiB 不减少。
- y 继续完整写 GM；保留原跨 kernel 依赖，不在 tile 粒度提前发布结果。
- y 的缓存策略不变，不增加生产者到消费者的特殊缓存协议。
- 除 Maximum 自身时间外，未来还应比较完整“生产→消费”序列，避免生产者变快但下游回退被遗漏。

因此，**a/b 的本轮 kernel 资源和逻辑工作变化相同**；不同的是 b 存在不能忽略的近邻设备复用窗口。

### 最有竞争力替代：输入 DISABLE、输出保持 NORMAL/默认

两个输入仍各只读一次，所以输入缓存试验与 a 一样适用，新增成本也仍是每核两次设置、零额外 UB。

但 b 的风险和潜在收益不同：

- 一次性输入的缓存填充可能干扰 y 或其他待复用数据；禁用输入缓存可能改善这种竞争，但当前没有证据确认。
- y 的后继读取可能利用缓存，故不能“整个算子统一 bypass”。
- 若某输出策略破坏了原本可命中的 y，单次消费最多有 \(W\) 有效读 payload 从缓存服务转为更下层服务的风险；实际放大、写策略与事务行为未知。
- 输出保持默认也不保证驻留或命中。

这正是 cache-hint 正文对选择的实际影响：**必须按对象和整个执行序列分析，不能把“Maximum 内只写一次”当成 y 无复用。**

融合是 b 的潜在更大机会，但消费者只有“完整顺序读”这一条信息。缺少其数学、owner、其他消费者、scratch、数值和可见性合同，不能实例化为可实施的 `fuse_kernel_chain`。若以后证明可以完全片上交接且无需保留 y，理论上可考虑省去这条边的 \(2W=8\) MiB 写读及一次 launch；现在不计为本轮节省。

## 四、共同机会比较与未选方向

### 1. 放大连续搬运是另一个实质性竞争方案

同 owner 内把两个相邻 tile 合成最大 8192 元素：

\[
K'_c=\lceil L_c/8192\rceil
\]

若三路均扩大，基础数据区为：

\[
3\operatorname{AlignUp}(8192\times4,32)=98304\text{ B，96 KiB}
\]

变化：

- 搬运调用从 \(3K\) 降为 \(3K'\)，有效 GM 字节不变；
- 若保持现有最大 4096 的 Max 调用域，可对合并后的 UB 区分两段计算，避免未经核验地扩大 Max 单次 count；此时计算调用不必同比减少；
- 增加输入输出存活范围和首包等待，少数核原本只有一个 tile 时没有合并空间；
- 不改变核数和 owner，不跨核合并输出。

本轮未选它，不是认为 16 KiB 必然已经高效，而是当前没有 setup 主导证据，且这一方案比选定的 80 KiB 流水需要更大的数据区。后继若显示发射/循环显著而预取收益小，应重新比较。

### 2. 明确不适用或暂缓的机会

- **输入驻留**：当前每个原输入元素只搬入一次，`reuse_input_tiles` 没有删读对象。
- **减少内存流量**：当前 Maximum 没有可证明冗余的输入读或内部 GM 中转；不能仅因 12 MiB 流量就登记可删流量。
- **广播、标量向量化、Cast 合并**：不是当前实际分支。
- **尾块向量化**：已有有效 count 的 Max 与 DataCopyPad 尾路径，未见独立 Scalar 慢尾。
- **尾分配重排**：用户已给定均匀互斥连续块，无集中昂贵尾任务依据。
- **缩同步范围**：当前未见热循环全流水/全核屏障；必要队列完成边不能按调用数量删除。
- **字段外提**：`tileElements` 在循环中重复出现，具备源码线索；但编译器可能已外提，且不改变主要数据通路，本轮不夹带。
- **bank padding**：没有当前实际 UB 地址和指令映射，不能照搬示例固定地址或增加 32B。

## 六、统一 C2：新共同计划，不沿用不充分的 KEEP

### 1. P 路由及计划身份

手工路由采用：

```text
planning.root
  → elementwise
  → planning.elementwise.continuous
```

采用其连续 owner、有效长度、物理槽字节账和尾块原则；**不采用模板 q/r 公式去替换当前分区**。

新计划建议身份为 `p_same_input_lookahead_r1`，相对 `p_same` 记 **P_CHANGE**：

- 原 `p_same` 只证明单输入槽、单输出槽和 48 KiB 数据区；
- 它没有授权本次双输入槽的容量和生命周期；
- 原计划也不能充当 broadcast/int64 的完整 fallback 计划。

这是“保留算法和 owner、改变核内资源及调度计划”，不是重新分核带来的收益。

### 2. 所有权、布局与 workspace

- 原每核区间 \([O_c,O_c+L_c)\) 不变。
- 三路 GM 均按原连续 FP32 下标映射。
- UB：x1 两独立槽、x2 两独立槽、y 一独立槽；不做物理 alias，不增加 bank padding。
- workspace：
  \[
  W_{\rm workspace}=0
  \]
- 不增加跨核通信，不改变 a 的 D2H 或 b 的跨 kernel 完成依赖。

### 3. 容量和队列约束

\[
A(T)=\operatorname{AlignUp}(4T,32)
\]

\[
U_{\rm alloc}=5A(T)+U_{\rm API}+U_{\rm framework/other}
\le U_{\rm available}
\]

T=4096 的五块用户数据区为 81920 B。不能把实际独立分配量按“通常只有部分有效”缩减，也不能把来源标称 UB 当当前可用容量。

每条队列仍可为 `TQue<...,1>`；输入 `InitBuffer` 的 num 改为 2，输出 num 保持 1。最大未 DeQue 项数必须始终不超过 1，**不是连续 EnQue 两次后再统一消费**。

### 4. 同步生命周期

| 对象 | 必须保护的完成边 |
|---|---|
| 当前输入槽 | MTE2 写完 → Max 读取 |
| 输入槽回卷 | Max 最后读完 → 下一代 MTE2 覆写 |
| 输出槽 | Max 写完 → MTE3 读取 |
| 输出槽复用 | MTE3 最后读完 → 下一次 Max 写入 |
| 退出 | 已提交输出完成、队列租约归还、框架生命周期闭合 |

选择队列管理，不同时引入手写 TBuf 事件管理同一槽。输出单槽意味着不能宣称已建立完整三段双缓冲；V 与 MTE3 对同一 y 槽仍有必要的复用串行关系。

### 5. 分派与 fallback

- 在现有同形 FP32 路径内部，只有本核有两个及以上有效 tile 才有前瞻机会。
- 可在初始化资源前按本核 `length_` 判断：零/单 tile 走原单槽路径，多 tile 走新路径；这是结构条件，不是捏造性能阈值。
- 保留原 `maximum_kernel` 的 dtype/sameShape 分派和原类作为 fallback，不新增跑分 Key。
- broadcast、int64 和其他 dtype 不改。C2 应另行**提取**其当前分派与资源契约；提取不算优化，也不等于证明这些未测域正确。

## 七、C3 准确实施步骤与正文实际影响

### 1. 实际方法选择

本轮主方法：

- `implementation.pipeline-sync.pipeline`
- 配套：`implementation.tiling-tail.valid-length`
- 配套：`implementation.precision-boundaries.bounds`
- 失败退路：`implementation.pipeline-sync.fallback`

缓存替代比较实际使用了 `implementation.memory-transfer.cache-hint`，但**不执行该缓存变换**。连续合并比较使用了 `implementation.memory-transfer.coalesce`。

### 2. 后继应完成的源码步骤

1. 保留原 `KernelMaximumSame<T>`，新增或参数化一个仅用于同形 float 的流水实现，避免改变 BF16/INT8 分支资源。
2. 初始化前算出 \(L_c,K_c\)。零任务不发 DMA；单 tile 使用原路径。
3. 多 tile 路径一次性分配 x1/x2 各两槽、y 一槽，单槽最大 16384 B。
4. 序言只搬入 tile 0，各输入 EnQue 一项。
5. 稳态按下面顺序执行：

```text
DeQue 当前 a、b                         # 消费输入队列项
若 next < Kc：
    为 next 分配另一个输入槽
    计算 next 的有效 count 后搬入并 EnQue # 每队列最多仍只有一项待 DeQue

分配当前 out
Max(out, 当前 a, 当前 b, 当前有效 count)
EnQue out；按队列协议归还当前 a、b
DeQue out；只写当前有效字节；归还 out
```

这里各阶段名称是调度说明，不是新增 SDK helper。下一 tile DMA 必须在本 tile Max 前发出，并写独立槽；否则仅增加物理槽没有兑现本方案。

6. 每个 next 地址先判有效再形成；继续使用无 mode 的 DataCopyPad，`blockLen=4*valid`，不向上扩展 GM 范围。
7. 最后一轮不再预取，确保所有已 EnQue 项都被 DeQue/归还，退出前由目标 SDK 合法协议闭合待完成搬出。
8. 真实接到 `DispatchMaximum<float>` 的 sameShape 分支；其他分支保留原实现。记录分析父本与候选实现的不同身份。
9. 构建前审查槽回卷、别名、有效 count、队列资源及完整容量；若需要手工事件、自定义地址或更多输出槽，返回 C2，不自行扩大方案。

### 3. 正文怎样改变了本方案

- **流水正文**使我没有把“num=2”当作优化完成：明确增加前瞻发射、当前槽 DeQue 和最后消费者闭环。
- **队列深度正文**使我保留 depth=1，并禁止序言连续塞入两个未 DeQue 输入。
- **continuous 正文**使我保留现 owner，把核内 tile 与跨核任务粒度分开，不借流水改变核数。
- **valid-length/bounds 正文**使尾块仍以有效 count 和有效字节执行，不加整 tile 清零，也不扩大 GM 尾部。
- **cache-hint 正文**使 a/b 都没有统一 bypass，尤其 b 的 y 明确保留近邻设备复用机会。
- **Compare/Select、数值边界正文**使本轮保持原 Max，不为换 API 添加 predicate、补齐或 8 KiB Select scratch。
