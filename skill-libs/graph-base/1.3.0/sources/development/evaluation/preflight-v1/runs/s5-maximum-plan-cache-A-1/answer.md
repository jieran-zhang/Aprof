## 结论与交接状态

本轮选择一个**缓存策略假设试验**，不叠加流水、放大 tile 或更换计算 API：

- **a：两个输入设置 `CACHE_MODE_DISABLE`，输出保持默认 `NORMAL`。**
- **b：同样只禁用两个输入的 L2 cache，输出保持 `NORMAL`。**

两例选择相同实现，但理由不完全相同：a 没有后继设备读取输出；b 有明确的输出复用窗口，保留输出缓存策略更重要。**a 不顺带禁用输出**，是因为提供的具体 cache-hint 配方直接展示的是输入读取路径，尚不足以确认当前 SDK 下输出写方向的具体效果与适用限制；不能由“一次性输出”直接补造这一能力证明。

最有竞争力的替代是：**保持 4096 元素 tile，为两个输入各配置两个物理槽，输出仍为一个槽，建立下一 tile 的预取窗口。**它有明确结构依据，不因缺少 overlap 实测而被否决；但相较所选方案，会增加每核 32768B 显式 UB，并需要新的生命周期计划，收益还依赖实际每核 tile 数。

这是纸面选择与 C2/C3 实施说明，**没有执行 router、生成 hash、修改源码、编译或运行**。状态为：

- 选择：有依据的条件化假设试验；
- 工程实施、正确性、性能：均未验证；
- 不声称当前缓存策略错误、流水完全串行或带宽饱和。

## 一、共同代码理解：当前真正执行什么

### 1. 实际路径与数学语义

按题目给定实际入口，当前执行原始 `KernelMaximumSame<float>`。若经过所示统一分派，则对应：

`maximum_kernel:178 → DispatchMaximum<float>:165–166 → KernelMaximumSame<float>`。

每个有效元素计算：

\[
y_i=\operatorname{Max}_{\text{当前AscendC API}}(x1_i,x2_i)
\]

输入、计算和输出均为 FP32，没有 Cast、广播、归约或跨核合并。有限非 NaN 域内保留原 `AscendC::Max` 即可避免引入新的数值实现差异；仍不能把它未经证明改成三元选择，尤其不能忽略相等值和正负零的具体行为。

每核起点与长度来自源码 12–17 行：

\[
B_c=c\cdot blockLength,\qquad
L_c=\min(blockLength,\max(N-B_c,0))
\]

题目已经给出这些连续块互斥、均匀且尾部完整处理。因此本轮不重新分核、不改变输出所有权。

### 2. 数据通路与依赖

每 tile 的实际顺序为：

1. 分配 a/b 输入 tensor；
2. 两次 `DataCopyPad`：GM→UB；
3. 输入 `EnQue/DeQue`；
4. 分配输出 tensor，执行一次 `Max(out,a,b,count)`；
5. 输出入队，输入释放；
6. 输出出队，一次 `DataCopyPad`：UB→GM；
7. 输出释放。

对应 `maximum_kernel.asc:31–66`。

910C/dav-2201 下，VECIN、VECOUT 都是 UB，通路为：

`GM —MTE2→ UB —Vector Max→ UB —MTE3→ GM`。

队列协议需要保护四类边：

- MTE2 写输入完成 → Vector 读输入；
- Vector 最后读输入完成 → 下一次 MTE2 覆写该输入槽；
- Vector 写输出完成 → MTE3 读输出；
- MTE3 最后读输出完成 → 下一次 Vector 覆写输出槽。

已有队列不等于已经有效重叠，也不能据源码顺序断言硬件完全串行。

### 3. 可静态计算的工作量

令 \(T=4096\)，\(s=4\) 字节，实际核数为 \(C\)，总 tile 数为：

\[
K=\sum_{c=0}^{C-1}\left\lceil \frac{L_c}{T}\right\rceil
\]

不能只因 \(N/T=256\)，就把总 tile 数固定写成 256：核边界若不与 tile 边界重合，各核可能各有短尾。非空连续分区下：

\[
256\le K\le256+C-1
\]

当前逻辑请求量：

| 工作 | 数量 |
|---|---:|
| x1 有效读取 | 4MiB |
| x2 有效读取 | 4MiB |
| y 有效写入 | 4MiB |
| Maximum kernel 合计有效 GM 请求 | 12MiB |
| MTE2 API 调用 | \(2K\) |
| MTE3 API 调用 | \(K\) |
| Max API 调用 | \(K\) |
| 有效元素最大值计算 | 1048576 次 |

这些是**逻辑请求及源码 API 次数**，不是 HBM 实际字节或底层指令数。

每个满 tile 的单路有效搬运为 16384B。不能套用其他设备的 256B/4KB 经验阈值，把它认定为“小包”。

当前显式 UB 数据分配：

\[
U_0=3\,AlignUp(4T,32)=49152\text{B}
\]

FP32 分支不分配 22–27 行的转换临时区。框架及编译器预留没有实值证据，不能把 49152B 当成完整可用容量证明。

还有一个边界：未给出输入指针的别名关系。两个逻辑输入各读取一次，不自动证明其物理地址集合互不相交。因此 **8MiB 是逻辑输入读取量，不一定是两者并集的唯一字节数**。该问题影响 cache 试验价值，不是本次仅改 hint 的新增地址安全风险。

## 二、子例 a：输出只 D2H 一次

### 当前路径与关键事实

Maximum 内核路径如上，之后输出用于一次 D2H，不再被设备 kernel 读取。

- 两个输入没有跨调用复用；
- 输出不能删除，D2H 仍需要完整结果；
- 没有 kernel 内部中间 GM 往返；
- 未提供缓存管理周期、按对象命中率或 HBM 字节；
- D2H 是否受当前 L2 状态影响、影响多少，材料不足，不能推定。

### 主方案 a：只禁用输入缓存

**绑定实例**

- 实例名：`A_cache_a`
- 注册 Action：`action.align_cache_policy`，使用输入提供的 D v0006 正文；
- target：当前 FP32 sameShape 实例的 `x1_`、`x2_`；
- stage：`Init` 中 GlobalTensor 绑定后，第一次 CopyIn 前；
- workload：N=1048576、T=4096、输入单次消费、输出仅 D2H；
- parent：题目所给原始源码；
- template/source hash：本轮未计算，正式登记时必须补齐，不伪造。

拟变化是在源码 15–17 行绑定后，对两个输入显式设置 DISABLE；y 保持 NORMAL。

**全部工作变化**

- 保留：12MiB 有效 GM 请求、\(3K\) 次搬运、\(K\) 次 Max、原队列操作及尾部；
- 减少：**没有可保证减少的逻辑读取或计算**；
- 改变：8MiB 逻辑输入读取请求的缓存策略；
- 新增：每核初始化时两次 hint 设置；实际生成指令和管理代价待编译确认；
- UB/workspace 增量：0；
- 不增加 padding、转换、初始化扫描或同步。

预测是：一次性流式输入绕过 cache，可能减少填充/替换开销；也可能无收益，或因输入地址重叠、其他未描述复用而退化。

**为什么本轮值得先试**

这不是因为字段修改容易等价，而是它直接作用于当前每次调用的全部输入读取路径，且不以增大工作集、缩小 tile 或重排生产消费为代价。当前已经是连续批量搬运及向量 Max，输入驻留和逐元素向量化都没有可消除工作；缓存策略因此是有来源支持的剩余候选之一。

### 最强替代 a：双输入槽软件流水

实例可登记为 `action.software_pipeline_stages`，对象为当前 CopyIn/Max/CopyOut 循环，而不是将“增加槽数”本身当优化结果。

候选保持 \(T=4096\)，两个输入各两槽、输出一槽：

\[
U_{\rm pipe}=(2+2+1)AlignUp(4T,32)=81920\text{B}
\]

相较原版增加 32768B/核；workspace 仍为 0。

完整变化为：

- 序言只搬入 tile 0；
- 第 t 轮出队当前 a/b 后，在另一组输入物理槽提交 t+1 的搬入；
- 再计算当前 Max、搬出当前输出；
- 末轮不再预取，退出时完成队列排空；
- 不新增有效 GM 字节或 Max 运算；
- 原搬运及队列操作的总次数原则上不变，增加首末判断、预取状态和框架资源管理；
- 输出单槽仍受 MTE3→V 复用边限制，**不是三阶段完全解耦流水**。

适用收益窗口只存在于 \(m_c=\lceil L_c/T\rceil\ge2\) 的核，潜在下一 tile 窗口数为：

\[
\sum_c\max(m_c-1,0)
\]

实际 C 未给出；若每核只有一 tile，不应强行增加输入槽。若搬运已经充分重叠或共享通路限制吞吐，多槽也可能无益。

本轮暂不选它，原因是新增资源、生命周期和实际循环长度都更敏感；不是把“没有 overlap profile”当作否决理由。

## 三、子例 b：输出立即被设备顺序读一次

### 当前路径与关键事实

Maximum 的计算、分区、UB 和请求量与 a 完全相同。不同之处是随后有一个设备 kernel 完整顺序读取 y：

\[
B_{\text{后继读取y}}=4N=4\text{MiB}
\]

因此只计这条已知连接边，链上包含 Maximum 的 12MiB 请求及后继对 y 的 4MiB 读取。后继 kernel 的其他输入、输出和计算未知，不能写出完整链的总流量。

“完整顺序读取”也不证明它可以与 Maximum 融合：其函数、核角色、owner、布局及其他消费者均未提供。

### 主方案 b：输入 DISABLE，输出 NORMAL

**绑定实例**

- 实例名：`A_cache_b`
- Action：`action.align_cache_policy`；
- target、stage、parent 与 a 相同；
- workload 绑定改为“y 随即被设备完整顺序读取一次”；
- hash 状态同样为未计算，不能冒充正式注册完成。

工作变化与 a 一样：只改变两输入 hint，不减少逻辑请求，不增加 UB/workspace，不改变同步。

**与 a 不同的成本判断**

b 中保留 y 的 NORMAL 有明确的复用依据。若最大可复用的 y 写入工作集都仍在 cache，后继读取可能获得收益；是否实际留存没有证据。相反，若对 y 也设置 bypass，可能损失这次复用。

从理想命中到完全 miss/bypass 的简化模型看，该读取边的 HBM 读量可能相差至多约 **4MiB**；这是风险量级模型，不是当前实际差值。禁用输入 cache 还可能减少它们对输出工作集的替换干扰，但同样只是预测。

所以两个子例采用同一输入策略，却不能写成相同的端到端收益假设。

### 最强替代 b：同一双输入槽流水

其 kernel 内部工作变化、81920B 显式 UB 和潜在窗口公式与 a 相同，仍保持 y NORMAL。

新增区别是评价范围：必须同时观察 Maximum 和后继 kernel，而不能只因 Maximum 更快就宣布链路改善。流水改变输出产生时间及访问相位，可能改变后继启动时的 cache 状态；不能假定两个阶段耗时独立可加。

另有一个可能更大的机会是跨 kernel 融合。若未来证明合法，删除 y 中间写读的理论量可以达到 \(2N\cdot4=8\)MiB，并可能少一次 launch；但当前缺消费者函数及执行契约，**不能实例化为可实施融合方案，也不能用 `keep_intermediate_onchip` 越过 kernel 边界**。

## 四、其余主要机会为何未并入

| 机会 | 当前判断及成本 |
|---|---|
| 更大 tile，例如 8192、仍三单槽 | \(U=98304\)B；tile 数变为 \(\sum_c\lceil L_c/8192\rceil\)，可减少搬运/API/控制次数，但必要字节不变，首包及尾部改变；需核验更大 Max count 和容量。不将它与缓存方案无依赖地叠加。 |
| 输入驻留 | 当前每个逻辑输入每元素只消费一次，\(R-1=0\)，无删读依据；不能把两输入同 shape 当重复原值。 |
| 连续访问重排 | 当前已连续，两个相邻 tile 地址相差 T 个元素；没有跨轴非连续机制依据。 |
| 合并写回 | 满 tile 已为16KiB；可以扩大汇总窗口，但增加输出存活量，逻辑输出字节不变，缺少明显碎片结构。 |
| Scalar 向量化、Cast 合并 | 当前 FP32 数据运算已经是 Max，无 Cast。通用 fallback 中的 Scalar 循环不属于这两个实际 workload。 |
| 元数据外提 | 32–34 行多次读 `tileElements` 是源码事实；但仅每 tile 规模，编译器可能已外提。相较输入策略和流水，本轮优先级较低，未夹带缓存字段修改。 |
| 删同步或 bank padding | 没有热循环全流水/全核屏障可直接收窄；没有实际 UB 地址和目标映射证据，不能随意加32B padding。 |
| 减少必要 GM 流量 | Maximum 单独的两个输入读和输出写均有消费者，没有已证明冗余区间；不能以可能带宽高登记可删流量。 |

以上判断分别受提供的 cache、pipeline、input-reuse、continuous-transfer、Scalar、bandwidth 与 bank 正文影响，并非仅按 Action 名称排除。

## 五、统一 C2 计划

### 1. 原计划与本轮计划的关系

不能把原 `p_same` 直接宣布为覆盖本轮所有对象的 **P_KEEP**：

- 它覆盖 sameShape FP32 的原三单槽计划；
- 未声明 cache 策略的许可自由度；
- 未覆盖 broadcast/int64 等 fallback；
- 更不能授权双输入槽或手工事件的新生命周期。

建议建立后继计划身份，暂称 **`p_same_cache_r1`**：

- 对当前分区、布局和三单槽的内容是**提取并保留已有计划**，不计为并行优化；
- 真正新增的自由度仅是目标输入的 NORMAL/DISABLE 策略；
- 同时把 fallback 的保留范围单独记录，不能拼接成虚假的全域 KEEP。

### 2. 共同合同

| 项目 | 本轮冻结内容 |
|---|---|
| 算法 | 原 FP32 `AscendC::Max`，不改表达式、Cast 或特殊值模式 |
| 分区/owner | 原每核连续区间、唯一写者；C 与 blockLength 不变 |
| 布局 | 原连续 FP32 GM；独立 VECIN a/b 与 VECOUT y |
| tile | 4096 元素，保留原有效短尾 |
| UB | \(3AlignUp(4T,32)=49152\)B 显式数据区；框架/编译器预留另计 |
| workspace | 0，无新 owner |
| 同步 | 原三队列协议，不删、不新增手工 event，不改变跨核拓扑 |
| cache | 目标两输入 DISABLE；y 保持 NORMAL；不采用 PERSISTENT |
| dispatch | 不按 a/b、case ID 或消费时间建立新 Key；两个子例可使用同一候选 |
| 禁止自由度 | 改核数、改 tile、增加槽、共享物理区、改变融合边界或消费者，均返回 C2 |

**容量结论应分开写：**本方案 UB 增量确定为 0，因此不增加原计划的容量需求；但输入未提供实际可用 UB 和完整预留，不能将绝对 `capacity=true` 伪写成已核验。正式实施前需确认原分配在实际 SDK/配置下合法。该缺项不妨碍纸面比较。

### 3. fallback 的真实范围

保留原 `DispatchMaximum` 及原策略版本，不把输入 bypass 扩散到其他 dtype、broadcast 或 int64。

尤其要记录：half 非 sameShape 分支无条件进入“LastAxisBroadcast”类，而该类固定把 x2 当作长度 row 的末轴向量。**仅由这份源码，无法证明它支持任意合法 half 广播。**本轮不修复或扩大该域，但也不能把“保留原分支”说成“通用广播正确性已证明”。

正式 C2 应补充既有接口支持域与 fallback 验证身份。当前 sameShape FP32 优化可以独立说明；全算子正式交接不能由 `p_same` 替代这些缺项。

## 六、C3 精确实施说明及正文的实际影响

以下是未来实施步骤，不是已经完成的 patch。

### 所选方案的步骤

1. 冻结原父源码及本轮计划身份，补实际 hash、SDK、构建目标和可用资源证据。
2. 在隔离候选中，仅为当前 **FP32 sameShape** 路径增加输入 hint 设置，位置在 `SetGlobalBuffer` 后、第一次 DataCopyPad 前：
   ```cpp
   x1_.SetL2CacheHint(AscendC::CacheMode::CACHE_MODE_DISABLE);
   x2_.SetL2CacheHint(AscendC::CacheMode::CACHE_MODE_DISABLE);
   ```
3. 保持 y 的 NORMAL。不要根据 a/b 名称增加运行时分支；也不向 tiling ABI 增加未经 Host 提供的“下一消费者”字段。
4. 通过局部策略模板/专用实例或等价隔离方式，保证其他 dtype 与 broadcast/int64 仍连接原实现。不顺便改通用 fallback。
5. 保持 19–21 行物理槽数、31–66 行计算/搬运/队列顺序、有效 count 和字节长度不变。
6. 审查两个 GlobalTensor 的所有视图及别名，确认没有遗漏另一套 hint 配置；hint 不作为可见性或同步保证。
7. 实施前核验实际 SDK 支持上述 A3/dav-2201 API。之后才进行代码审查、构建、完整 oracle 与实际分支核验；本轮不执行这些动作。

### P/O 正文如何改变了方案

- **P：`planning.elementwise.continuous`**  
  采用其所有权、有效 count、真实槽数及字节预算原则；不照搬其 q/r 公式改掉已经合法的原分区，也不把 tile 放大当必要字节减少。
- **O：`implementation.memory-transfer.cache-hint`**  
  实际采用“逐对象判复用、一次性输入可比较 DISABLE、输出不能因本 kernel 无复用而统一 bypass”；因此 b 的 y 明确保留 NORMAL，a 也不无证据扩大到写方向。
- **O：`implementation.tiling-tail.valid-length`、`precision-boundaries.bounds`**  
  保持尾部 `count*4` 有效字节，不把 UB 对齐量写成 GM 长度；不新增整 tile 清零。
- **竞争方案：`implementation.pipeline-sync.pipeline`**  
  其正文要求物理槽、未 DeQue 数和最后消费者闭合，所以替代方案是“两个输入双物理槽＋具体预取次序”，不是只把模板 depth 改成2。
- **竞争方案：`input-tile-residency`**  
  其 \(R=1\) 无删读依据，直接阻止把本轮包装为输入驻留。
- **`compare-select-tail` 与数值边界正文**  
  提醒 Max 不能仅按名字换成条件选择；既然本轮不改计算，就不增加 predicate、256B 比较补齐或8KiB Select 临时区。

这些是人工依据给定正文形成的路由判断；没有声称机器 router 已命中或严格契约已通过。

## 七、可复用后继摘要与待验证项

### 当前状态

- 原始实现保留，候选未修改、未构建、未测量。
- 两子例选择输入 cache bypass；三单槽、4096 tile、owner、workspace 和计算均不变。
- 原 `p_same` 仅作 sameShape FP32 的计划基础，不作全 fallback 或双槽生命周期证明。
- 性能状态：`not_measured`；正式接纳：未评价。

### 本轮路线

| 路线 | 覆盖与静态预测 | 新增代价及限制 |
|---|---|---|
| 选定：输入 DISABLE | a/b 当前 FP32 sameShape；改变8MiB逻辑输入请求的策略，无逻辑删读 | 两次/核初始化设置；真实 cache/HBM/耗时未知 |
| 未实施：双输入槽流水 | 多 tile 核可预取下一 tile | +32768B/核；需新计划、队列资源及首尾闭合 |
| 未实施：放大 tile | 减少 tile/API 次数 | 更多 UB、更大 count、尾部与首包改变 |
| 暂缓：b 的链融合 | 潜在减少中间物化及 launch | 缺消费者数学与执行合同，不能授权 |

### 必须区分的后续检查

**实施合法性补项：**

- 实际 SDK/目标编译下 SetL2CacheHint 的支持与真实接线；
- 原三槽加框架预留的完整容量；
- fallback 的声明支持域和验证身份；
- 正式计划、模板和实现 hash。

**检验性能预测，而非统一实施门禁：**

- 两输入是否物理重叠，是否存在未描述的近邻复用；
- cache hint 是否实际进入生成物；
- 按对象的 L2/HBM、MTE2 等待和 Task 时间；
- a 同时观察 D2H 完整序列，不假定其代价与缓存无关；
- b 同时观察 Maximum 与后继消费 kernel，避免把成本转移误认成优化；
- 取得真实 C、\(m_c\) 后重新比较流水窗口与缓存方案：若大量核仅一 tile，削弱双槽价值；若有长稳态等待且81920B容量合法，流水仍是有竞争力的后继。

没有硬件结果前，不能把本轮策略称为赢家，也不把尚未测量当成机制反证。
