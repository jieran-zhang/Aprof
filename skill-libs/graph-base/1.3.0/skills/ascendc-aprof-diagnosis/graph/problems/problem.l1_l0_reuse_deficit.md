# L1/L0 复用不足

## 对象、阶段与适用域

- MatMul中可跨多个对侧tile复用的A/B矩阵块
- host M/N/K与驻留侧选择
- kernel GM→L1→L0→Cube

旧scope=all保留作检索范围，机制成立仍须核对目标架构、dtype、shape和API支持。

## 机制链

- A/B块在多个对侧tile期间地址和值不变
- 该块仍在内循环反复搬入L1或L0，未建立相应驻留
- MTE1/MTE2搬运及Cube等待增加

## 预测、支持检查与反证

- 合法驻留一侧后该层重复搬运减少，流式侧仍按需更新；这是prediction
- 把GM→L1与L1→L0分层核算，不拿GM读减少代替MTE1证据
- 检查高阶Matmul内部已实现的cache或驻留能力
- 只复用一次或K每轮变化时不能归因于未驻留
- 驻留挤掉关键ping-pong导致等待增长时应比较折中

## 具体替代解释

- problem.insufficient_input_reuse：层级不同：L1/L0低复用可在GM流量正常时出现；检查：分别比较各层计数与地址重复
- problem.pipeline_serialization：装载次数合理但顺序串行应改流水而非驻留；检查：固定加载次数观察事件和重叠

## 候选动作与成本

action.retain_matrix_tiles：选择合法的A或B驻留层级，保留流式侧同步和释放边界。

原硬前提：symptom.source.l1_l0_reuse_deficit=true；constraint.l1_l0_budget=true；constraint.semantic_equivalence=true；constraint.capacity=true。

- 驻留容量挤压双缓冲
- 更长存活期和布局限制可能增加尾处理复杂度

## 限制与缺口

- arch22文档的L0 cache/NBuffer33是具体适用形态，不能作为所有Matmul API能力
- API已内部管理时需查看实际配置而非复制手排方案
- 本轮无同任务profile、无case_support、无收益或发生频率声明；源码形态只支持待核验候选。
