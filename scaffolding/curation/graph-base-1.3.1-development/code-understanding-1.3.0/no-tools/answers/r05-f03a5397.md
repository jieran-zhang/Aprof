# 代码理解说明

以下区分**源码事实**、**平台/API语义**与**静态推导**；没有设备编译、运行或性能证据。`source/DELTA.json:2–42`表明仅测试标识符、文件名更名，未改变常量或API语义。两个入口独立执行。

## 入口 V：逐元素指数变换

### 算法、数值与分派
`vector/op_host/nacre.asc:38–60`读取参数、查询Vector核数，生成并复制`NacrePlan`后启动核函数。输入输出均为连续一维BF16，共25019元素，各50038字节，无归约或元素间依赖。

`nacre_plan.h:18–29`将正底数折入系数：
\[
g=0.5\ln2,\quad b=-\ln2,\quad y_i=\exp(gx_i+b)
\]
实数意义即 \(2^{0.5x_i-1}\)。实际路径是BF16转FP32，依次执行FP32 `Muls→Adds→Exp`，再以`CAST_RINT`转BF16；不是直接用BF16计算，也不是无限精度幂函数（`nacre_stage.asc:45–63`）。输入BF16值可精确扩展为FP32，但系数、逐步算术、Exp及回写均有浮点语义；极端值和特殊值结果不能由实数公式替代。一般参数下，`base<=0`使用自然指数分支，而非计算非正底数的幂。

本次`storageTag=2`，实际进入`StageNacre<bfloat16_t>`（同文件85–93）；不存在Cube计算。

### 工作划分、循环与尾块
计划计算为：
- `useful=ceil(25019/4096)=7`；
- 查询核数为3，故`laneCount=3`；
- `laneExtent=ceil(25019/3)=8340`，窗口4096元素。

由`Init/Process`（9–33）推导：

| blockIdx | GM起点，元素/字节 | 有效长度 | 三次循环的count |
|---|---:|---:|---|
| 0 | 0 / 0 | 8340 | 4096、4096、148 |
| 1 | 8340 / 16680 | 8340 | 4096、4096、148 |
| 2 | 16680 / 33360 | 8339 | 4096、4096、147 |

循环局部偏移为0、4096、8192元素。共9次窗口处理，6个整窗、3个尾窗。每个整窗搬8192字节，尾窗分别296、296、294字节；核间区间不重叠且完整覆盖输入输出。

### 存储、同步及910C行为
`Init:16–23`为每核分配单槽输入/输出队列，各8192字节，以及两个FP32临时区，各16384字节；显式数据缓冲合计49152字节，即48 KiB，不含实现内部开销。

每轮是`CopyIn→Compute→CopyOut`：
- `DataCopyPad`按`count*sizeof(T)`字节搬GM→UB；
- Vector流水执行转换及逐元素运算；
- UB→GM仅写有效字节（37–73）。

按AscendC队列契约，EnQue/DeQue及释放管理跨流水依赖和槽位复用；源码没有手写HardEvent。队列深度均为1，未见双缓冲或显式多窗口流水调度，不能仅凭函数调用次序量化实际重叠程度。910C上主要涉及MTE2、Vector、MTE3及UB，不涉及矩阵流水。

核起点不都32字节对齐；源码使用支持扩展长度/非整块搬运的`DataCopyPad`接口，未给GM额外分配尾部空间。UB内部可能存在对齐处理，但不改变有效count；不能据此把GM尾块算成4096元素访问。可见host逻辑不使用`NPU_ARCH`分支，不能拿它替代device架构宏。

## 入口 C：Matmul后接LeakyReLU

### 算法与实际任务
`cube/mica.asc:197–215`固定：
- A：half `[512,128]`，131072字节；
- B：half `[128,128]`，32768字节；
- C：half `[512,128]`，131072字节；
- 单核尺寸与基本tile均为`256×128×128`；
- `numBlocks=(512/256)*(128/128)=2`。

`mica_entry`声明`__mix__(1,2)`，因此源码表达的混合执行契约为2个AIC、4个AIV（188–194），不是只有两个Vector任务。

数学目标是 \(C=\operatorname{LeakyReLU}(AB)\)，负支斜率0.001。实际数值路径更具体：
1. half输入经`Mmad`产生float L0C结果，初始化累加器；
2. `Fixpipe`先转half写GM；
3. AIV读取该half结果，用half表示的0.001执行half LeakyReLU，再写回。

因此激活发生在中间结果已转half之后，并非对未舍入FP32结果激活后仅转一次half（115–127、155–176）。Cube内部累加细节、Fixpipe默认舍入及特殊值细则，不能仅凭参数表完整确定。

### 分工、地址和数据路径
`Init:33–44`使AIC \(p=0,1\)分别处理A/C的256行，偏移均为`p*32768`个half，即`p*65536`字节；B不偏移，两个AIC各加载完整B。

这里没有M/N/K分块遍历：每AIC只执行一次完整tile的搬运、一次`Mmad`和一次`Fixpipe`。K=baseK=128，不存在跨轮K累加；所有维度整除，无矩阵尾块。`singleCoreK/N`等模板参数没有形成通用多tile循环。

每AIC显式片上分配（52–61）：
- L1：A 64 KiB、B 32 KiB；
- L0A：64 KiB；L0B：32 KiB；
- L0C：float结果128 KiB。

GM连续ND经`Nd2NzParams`转NZ存入L1，源行距A为K=128、B为N=128个half（65–68）。随后L1→L0，经矩阵流水计算，再由FIX完成L0C→GM、NZ→ND及FP32→half转换；Fixpipe关闭ReLU。

AIV \(v=0…3\)通过`v/2`定位所属AIC输出，再由`v%2`选择128行半块（134–158）。全局起点为0、16384、32768、49152个half，即0、32768、65536、98304字节。每AIV使用32 KiB UB；搬运参数为128行、每行256字节、GM行间跳过0字节，因此本次半块连续。四个AIV原位更新互不重叠的区域，Cube与Vector之间通过GM传递结果，不是直接传到UB。

### 依赖链
源码显式建立：
`MTE2→MTE1`（72–73）、`MTE1→M`（110–111）、`M→FIX`（119–120）。FIX写回后以`CrossCoreSetFlag<0x2,PIPE_FIX>(0)`通知对应AIV；AIV等待后才读GM（129、136）。AIV内部再以`MTE2→V→MTE3`事件保护读取、激活与写回（162–176）。入口末尾有`PIPE_ALL`屏障，host同步流后才复制结果（194、244–247）。

这些是流水依赖及关联核同步，不应解释为全部核之间的一次全局计算屏障。

## C的2201实际路径与3510静态对照

条件差异仅位于`mica.asc:75–107`的L1→L0装载：

| 项目 | 实际2201 | 静态3510 |
|---|---|---|
| A目标布局 | NZ→ZZ | NZ→NZ |
| A API | `LoadData2DParams` | `LoadData2DParamsV2` |
| A调用结构 | 16次，每次8个16×16块，源stride=16 | 一次二维调用：step=(16,8)，src/dst stride=(16,16) |
| B目标布局 | NZ→ZN，转置标志true | 同为NZ→ZN，转置标志true |
| B调用结构 | 8次，每次8块，源stride=8 | 一次V2调用：step=(8,8)，src/dst stride=(8,8) |

2201中A、B各循环的源起点均每次增加256个half，即512字节；目标起点均增加2048个half，即4096字节（79–90）。这是NZ物理块寻址，不是直接按原ND行偏移。A共装载128个512字节块，B共64块。

两条件下，其余源码相同：混合核声明、任务划分、GM/L1格式转换、缓冲大小、`Mmad`参数、`FixpipeParamsV220`、激活和同步调用均不变。**相同API调用不等于相同底层指令或性能**：不同装载方式满足各自L0布局契约；3510的API可用性、混合核映射、FIX及跨核同步支持，仍需相应平台编译和运行验证。尤其不能因类型名含“V220”就自行确认或否定3510兼容性。

上述实现只对本次常量可确认完整覆盖；改变尺寸未必仍正确分核或处理尾块。C的文件读取/ACL调用返回值多未检查，成功执行还依赖输入文件和运行环境。没有profiling，不能判定带宽、流水利用率、核间等待时间或瓶颈，也不能把3510条件视为已运行结果。
