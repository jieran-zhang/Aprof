# 矩阵乘代码理解说明

以下行号默认指 `source/baseline/mmad.asc`；variant 除 L209 外行号、代码相同，差异见 `source/VARIANT.patch:L3–9`。结论分为源码事实、平台/API语义及静态推断，不代表运行测量。

## 1. 输入输出与数值语义

输入 A 为连续 `[8192,8192]` half；B 文件为连续 `[N,K]` half，是逻辑 `[K,N]` 矩阵的转置存储。目标为：

\[
C[m,n]=\operatorname{half}\left(\sum_{k=0}^{8191}A[m,k]B_{\rm file}[n,k]\right).
\]

C 为连续 `[M,N]` half，无 bias、激活或旧 C 累加。`Init` 将三个 GM 指针解释为 half（L36–40）；host 用 `sizeof(int16_t)` 计算文件大小只是按两字节分配，并非整数计算。A/B/C 各占 128 MiB。

每次 `Mmad` 计算 `128×64` 与逻辑 `64×256` 的乘积，累加到 float L0C；K 首轮 `cmatrixInitVal=true`，后续累加，共128轮。最后 Fixpipe 用 `F322F16` 转换输出（`Compute` L501–520、`CopyOut` L525–541）。这是 half 输入、float 累加、half 输出的计算路径，不应视为实数精确求和；Cube 内部归约次序、特殊值及舍入细节不能仅由本源码确定。

host 读取两文件、H2D、单次 launch、流同步、D2H 并写文件（L597–631），没有结果校验。`ReadFile` 只拒绝空文件、过大文件等，不要求文件恰好填满缓冲区；返回值和 ACL 错误未检查（`data_utils.h:L25–61`）。

## 2. 实际分派、循环与尾块

本题 host `NPU_ARCH=2201` 选择：
- `baseM/baseK/baseN=128/64/256`；
- `singleCoreM/K/N=2048/8192/1536`；
- `stepKa/Kb=8/4`，launch 24 个 Cube block。

device `__NPU_ARCH__=2201` 决定 LoadData API 分支，不能与 host 宏混用。`SCENARIO_NUM=1` 只走 `Process()`；`ProcessL2Cache()` 不执行（L562–572），因此没有该函数的外层分批调度。

`InitComputeParams`（L273–306）将 block \(q\) 映射为：
- \(i=q\bmod4\)，M 起点 `i*2048`；
- \(j=\lfloor q/4\rfloor\)，N 起点 `j*1536`。

q=0…19 各负责 `2048×1536`；q=20…23 各负责 `2048×512`。每个 block 都独立完成全部 K，无 split-K 或跨核归约。

循环次序为 **N tile → M tile → K tile**（L170–192）：
- M 循环16次；
- 前20个 block 的 N 循环6次，后4个为2次；
- 每个输出 tile 的 K 循环128次。

全矩阵共 `64×32=2048` 个 `128×256` 输出 tile。末组 block 的512列仍是两个完整 baseN tile；M/N 的 `tail` 和对齐尾长均为0，循环不会进入零长度尾块分支。K 同样无尾块。

对核内 tile `(u,v)`，令 `m0=i*2048+u*128`、`n0=j*1536+v*256`。GM half 元素偏移为：
- A：`m0*8192 + chunkA*64`；
- B：`n0*8192 + chunkB*64`；
- C：`m0*8192+n0`，输出行距8192元素。

字节偏移须乘2。`chunkA/B` 实际以 **baseK块数**计数，而非大包序号，每次分别增加8/4（L178–189、238–254）。

## 3. 数据路径与物理存储

`Process` 的 LocalTensor 构造（L52–72）指定的是各本地存储空间内的字节偏移；张量长度、下标则以元素计。

| buffer | 所在空间 | Ping/Pong 起点 | 每份有效大小 |
|---|---|---|---|
| A1 | 共享 L1 地址空间 | 0 / 128 KiB | 128 KiB |
| B1 | 同一 L1 | 256 / 384 KiB | 128 KiB |
| A2 | 独立 L0A | 0 / 32 KiB | 16 KiB |
| B2 | 独立 L0B | 0 / 32 KiB | 32 KiB |
| C | L0C | 0 | 128 KiB，float |

因此 L1 恰覆盖512 KiB；L0A 两份之间有空隙。A2/B2 同为偏移0不表示物理别名，它们属于不同存储体。

平台/API层面，执行路径为：

**GM → MTE2 的 ND-to-NZ 搬运 → L1 → MTE1 LoadData → L0A/B → Cube Mmad → L0C → Fixpipe → GM。**

`DataCopyInA/B`（L343–388）分别搬入 `128×512`、`256×256` 的大包，GM 行距8192元素，转换为 NZ 分块布局，不是连续 memcpy。

2201 上：
- A 每轮用 `LoadData3DParamsV2` 取 `128×64`（L399–411）。
- B 已转置存储，走 L459–469：每轮4次 LoadData2D，每次搬16个 `16×16` half块，`ifTranspose=false`。源、目的子段步长均4096 half，即8 KiB，总计32 KiB。

每个输出 tile 搬16个 A 大包、32个 B 大包。大包内分别复用8/4个K切片；输出 tile 切换后搬运进度归零，源码没有跨输出 tile 保留输入的策略。跨核/跨 tile 的 GM 重复读取可能受 L2 缓存影响，但命中率未知。

## 4. 一个 tile 的前10轮与事件关系

选 block0、`u=v=0`，输出 `C[0:128,0:256]`。第t轮使用 K 区间 `[64t,64t+64)`；A/B 每一行的 GM 起点均为 `row*8192+64t` half。

下表为读取的 **L1切片起点** 和写入的 **L0起点**，单位 KiB。A切片长16 KiB，B切片长32 KiB；L0A/B地址分别解释。

| t | A1起点 | B1起点 | A2/B2起点 |
|---:|---:|---:|---:|
| 0 | 0 | 256 | 0 |
| 1 | 16 | 288 | 32 |
| 2 | 32 | 320 | 0 |
| 3 | 48 | 352 | 32 |
| 4 | 64 | 384 | 0 |
| 5 | 80 | 416 | 32 |
| 6 | 96 | 448 | 0 |
| 7 | 112 | 480 | 32 |
| 8 | 128 | 256 | 0 |
| 9 | 144 | 288 | 32 |

这些是 NZ 分块数据的起点，不代表 GM 行主序布局。C 始终累加到 L0C 起点0。

按源码发起顺序（L178–255）：
1. 循环前预装 A Ping 的 t=0…7、B Ping 的 t=0…3。
2. t=0 的 Compute 发起后，先预取 B Pong 的 t=4…7，再预取 A Pong 的 t=8…15。
3. t=3 消费完 B Ping，随后复用它装 t=8…11。
4. t=7 消费完 B Pong 和 A Ping，随后分别装 B t=12…15、A t=16…23。

这些是流水提交及依赖关系，不意味着各引擎完成时间等于源码调用时间。

**baseline 的事件协议：**
- `MTE1_MTE2`：ID0/1对应 A1 Ping/Pong，ID2/3对应 B1 Ping/Pong；预置“可写”，MTE2 覆盖前等待；大包最后一次 LoadData 后由 MTE1 释放。
- `MTE2_MTE1`：同样ID对应“搬入完成”；只在大包首切片等待。后续切片依赖同流水有序执行。
- `MTE1_M`：每轮 LoadData 后 Set、Cube侧 Wait，保证本轮 L0 输入就绪。
- `M_MTE1`：ID0/1对应两份 L0；预置允许首次装载，每轮 Mmad 后 Set，下次复用前 Wait（L159–165、209、506–519）。

由此，对同一 L0份建立：
`Load(t) → Mmad(t)完成 → Load(t+2)`。
双缓冲允许另一份搬运与计算重叠，但不保证实际达到某个重叠比例。

Mmad 的 UnitFlag 为前127轮2、末轮3，Fixpipe为3；按平台API语义，承担 Cube/Fixpipe 间的 L0C交接同步，而非显式 `M_FIX` 事件。末尾还有事件回收等待和 `PIPE_ALL` barrier（L265–270、572）。

## 5. 两版本的保证差别与证据边界

variant **仅删除每轮 L209 的 `WaitFlag<M_MTE1>`**。布局、选择、计算参数、所有 SetFlag 和末尾 Wait 均未变。

因此正向 `Load(t)→Mmad(t)`、L1大包的读写保护仍存在，但无法再由该协议证明 `Mmad(t)完成→Load(t+2)`。最早在 t=2 就复用 t=0 的 L0 Ping；此时不需要新的 L1大包等待，不能用 L1事件补足这条反向依赖。MTE1_M 的 Wait约束消费者 Cube，不会反向阻止 MTE1继续覆盖。

这是明确的 **L0覆盖先于旧操作数消费完成的潜在风险**，不是静态证明“必定输出错误”。初始及每轮 `M_MTE1` Set仍保留，形成未逐轮配对的事件使用；不能把事件当无限计数器，也不能凭材料确定重复置位会合并、阻塞或产生何种设备表现。末尾等待/barrier不能修复已经发生的覆盖。

910C 上 Cube、MTE1、MTE2、Fixpipe 是可异步推进的流水，C++调用先后本身不等于跨流水完成顺序。静态材料支持依赖缺失的判断，但不足以断言具体竞态是否触发、是否挂起、误差大小或性能变化。当前尺寸无越界尾包；对其他K长度、大包不整除或额外block的适用性也不能由本次整除 workload 外推。
