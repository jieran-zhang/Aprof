# 代码理解说明

## 范围与证据

两个入口相互独立。`source/DELTA.json:2–42` 声明仅测试标识符、文件名更名，数值常量和 API 未改；应按现有调用解释，而非据旧名称猜算法。以下区分**源码事实、workload 推导、平台契约及未确认项**。实际 device 条件为 **2201**；3510 仅作静态对照，不代表编译或运行成功。源码没有使用 host `NPU_ARCH` 选择这些 device 分支。

## 入口 V：逐元素指数变换

### 算法、分派与数值语义

输入、输出都是连续 ND 的 `[25019]` bfloat16，各 **50038B**。host 解析参数、查询 Vector 核数并生成计划，将输入与计划复制到 GM，按 `laneCount` 启动；同步 stream 后回传输出（`source/vector/op_host/nacre.asc:38–63`）。

`MakeNacrePlan` 将底数换成自然指数的系数：
\[
g=0.5\ln2,\quad b=-\ln2,\qquad y_i\approx 2^{0.5x_i-1}.
\]
实际执行为 bfloat16→float，再依次 `Muls`、`Adds`、`Exp`，最后以 `CAST_RINT` 转回 bfloat16，不是直接在 bfloat16 上求幂，也不保证与理想公式逐位相同。host 系数为 float，乘、加分开发射；`Exp` 精度、异常值及溢出细节不能由调用文本完全确定。若 `base<=0`，源码改用自然指数而非该底数的幂（`nacre_plan.h:18–29`；`nacre_stage.asc:45–63`）。

实际 `storageTag=2`，入口走 `StageNacre<bfloat16_t>`；另有 float、half 路径，但不在本 workload 中执行（`nacre_stage.asc:85–93`）。

### 工作划分与尾块

由 `nacre_plan.h:22–25`：
- `useful=ceil(25019/4096)=7`，查询值为 3，因此启动 **3 个 block**。
- `laneExtent=ceil(25019/3)=8340`，`windowElements=4096`。

按 `StageNacre::Init/Process`（`nacre_stage.asc:9–33`）推导：

| block | 全局元素区间（半开） | GM 起始字节偏移 | 三轮有效元素数 |
|---|---|---:|---|
| 0 | `[0,8340)` | 0 | 4096、4096、148 |
| 1 | `[8340,16680)` | 16680 | 4096、4096、148 |
| 2 | `[16680,25019)` | 33360 | 4096、4096、147 |

每核循环偏移为 0、4096、8192，单位是元素；合计九轮。各区间不重叠且覆盖全部输出，无归约或核间同步。3 是本次查询和计划决定的启动量，不是 910C 的固定物理核数。

### 存储、搬运与依赖

每核输入、输出队列各有**一个 8192B 槽位**，另有两份各 16384B 的 float TBuf；显式 UB 数据区共 **49152B**。队列深度和物理槽数均为 1，没有源码可见的双缓冲。VECIN、VECOUT、VECCALC 在 A3 上均映射 UB，不是三层存储（`nacre_stage.asc:16–23,76–82`；资料 H03/H07/H08）。

数据路径为：
`GM --MTE2--> UB输入 --V/Cast及指数计算--> UB输出 --MTE3--> GM`。
`DataCopyExtParams.blockLen` 为字节：完整轮 8192B，尾轮 296B、296B、294B。A3 普通 `DataCopyPad` 的 local 块按 32B 补齐，因此三个尾轮各需 320B local 空间，现有 buffer 足够；只计算有效 count、只写出有效字节，dummy 不参与运算。`isPad=false` 不承诺补零；非对齐 GM 起点也不能按普通对齐整块拷贝解释（`nacre_stage.asc:37–42,69–73`；H05/H06）。

队列 EnQue/DeQue 表达搬入就绪、计算就绪，FreeTensor/再分配参与槽位复用管理；不能因没有手写 flag 就断言缺少同步。V 多条指令间及 TBuf 复用依赖还涉及 API/编译器同步契约，未见生成代码，不能还原精确事件时间线或证明搬运计算已重叠。

## 入口 C：half GEMM 后接 half LeakyReLU

### 算法与实际分工

`source/cube/mica.asc:199–215` 固定：
`M=512,K=128,N=128`，单核及基础 tile 均为 `256×128×128`。输入 A `[512,128]`、B `[128,128]`，输出 `[512,128]`，均为 half、GM ND；分配大小分别是 **131072B、32768B、131072B**。

算法是完整 K 轴矩阵乘，再激活：
\[
S_{mn}=\sum_{k=0}^{127}A_{mk}B_{kn},\quad
H=\mathrm{half}(S),\quad
C=\operatorname{LeakyReLU}_{\mathrm{half}(0.001)}(H).
\]
Mmad 使用 float L0C；Fixpipe 先转 half，之后 AIV 才做 half 激活。因此不是对 float 累加结果先激活再统一转 half。具体舍入、异常值传播及逐位参考一致性仍未验证（`:115–127,165–166`）。

host 启动 `numBlocks=2`；`__mix__(1,2)` 表达每组 1 AIC 配 2 AIV，即本次 **2 AIC、4 AIV**（`:188,215,242–244`）。按源码核号映射（`:36–44,150`）：

- AIC 0/1 分别产生 C 的行 `[0,256)`、`[256,512)`；A、C 起点分别偏移 0/32768 个 half，即 0/65536B。两核各读完整 B。
- AIV 0～3 分别处理 128 行，最终 GM 起点为 0、16384、32768、49152 个 half，即 0、32768、65536、98304B。`blockIdx/2` 找所属 AIC，`blockIdx%2` 选择其上下半块。

每 AIC **一次 Mmad**，初始化 L0C 并完成 K=128 归约；每 AIV **一次 ApplyGate**。没有 M/N tile 遍历、K 分段累加或尾块循环。LoadData 小循环只是布局搬运，不是多次 GEMM。

### 2201 上的数据流、资源和同步

每 AIC 的显式分配（`:52–61`）：
- 同一 L1 allocator：A 65536B、B 32768B，合计 98304B；
- L0A 65536B、L0B 32768B；
- L0C float 131072B。

每 AIV 分配 16384 个 half，即 **32768B UB**（`:133–138`）。这些是分存储层的用户数据区，不能合并成 UB 占用，也不是编译产物总资源证明；L0C 数据区达到资料所述 128KiB 标称容量。

A3/2201 路径为：

`GM ND → MTE2/L1 NZ → MTE1/L0A ZZ及L0B ZN → M/Mmad/L0C NZ(float) → FIX/GM ND(half) → MTE2/UB → V激活 → MTE3/原GM区域`

ND→NZ 使用原矩阵行跨度 K/N（`:65–68`）。half 分形为 16×16、512B：
- A：16 次 LoadData，每次 8 个分形，源 stride=16；第 i 次源偏移 `256i` 个 half，目的偏移 `2048i` 个 half。
- B：8 次，每次 8 个分形，源 stride=8；源偏移 `256i`、目的偏移 `2048i` 个 half，`ifTranspose=true` 形成 ZN，**不改变数学 B 为 `[K,N]`**（`:75–91`；H09）。

显式依赖链为 `MTE2_MTE1 → MTE1_M → M_FIX`，分别保护 L1、L0A/B、L0C 的生产消费；Fixpipe 同时做 NZ→ND、float→half，且自身 ReLU 关闭。随后 AIC 在 `PIPE_FIX` 上发布跨核 flag，两个对应 AIV 等待后才读 GM 中间结果（`:70–73,108–136`）。这是 AIC/AIV 经 GM 交接，不是共享 UB 或片上直通。

AIV 每次搬 128 行，每行 256B，GM 行间间隔为 0；UB stride=0 的单位为 32B，GM stride 的单位为字节。行长已对齐，无实际补齐需求。`MTE2_V` 保证激活输入就绪，`V_MTE3` 保证写回读取计算结果（`:146–176`；H05/H06）。入口最终核内 `PIPE_ALL` 屏障、host stream 同步分别覆盖核内收尾与主机回传顺序（`:194,244–246`）。

## 2201 与 3510：相同文本不等于相同硬件契约

| 项目 | 可确认的静态差异或相同点 |
|---|---|
| LoadData | 2201 选上述 16/8 次 `LoadData2DParams`；3510 选各一次 V2：A 参数 `{0,0,16,8,16,16,false,0}`，B `{0,0,8,8,8,8,true,0}`。 |
| L0 输入布局 | 源码注释明确：A 在 2201 为 ZZ、3510 为 NZ；B 均意图形成 ZN（`:75–106`）。 |
| 算法与公共代码 | shape、launch、偏移、分配、Mmad、Fixpipe、跨核 flag、GM 中转、激活代码文本相同，没有 3510 专属直通分支。 |
| 硬件/API 保证 | 资料 H01/H11 表明 3510 属另一架构及底层实现，不能把 A3 的流水、核号配对、同步模式、资源与重载支持直接移植过去。 |

因此能确认 3510 **预处理选中的源码及其意图**，不能确认该混合核声明、V220 Fixpipe、flag 模式和所有 API 在该目标上的合法性、完整执行语义或结果正确性，更不能声称已有性能对照。

当前固定 shape 恰好整除，单核范围等于一个基础 tile，覆盖关系成立；模板名称并不证明支持任意 shape、多 N 块或尾块。两个入口均无设备编译、正确性验证或 profiling 证据；流水等待时长、实际重叠率、cache/HBM 流量及吞吐仍属未测项，不据静态代码裁定瓶颈。
