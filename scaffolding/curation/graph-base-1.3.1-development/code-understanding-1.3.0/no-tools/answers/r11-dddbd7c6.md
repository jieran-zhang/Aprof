# 代码理解说明

以下区分**源码事实**、**平台/API语义**与**静态推断**；没有编译、运行或性能测量结果。`source/DELTA.json:2–42`仅记录测试标识符和头文件更名，未改变常量或API，不能据名称推导另一套算法。

## 一、入口 V：逐元素指数变换

### 算法与数值语义

`source/vector/op_host/nacre.asc:38–60`解析参数、查询Vector核数、构造计划，将输入和计划复制到GM，再按`laneCount`启动`nacre_entry`。输入输出均为25019个连续BF16元素，各50038字节；无归约或元素间依赖。

`op_kernel/nacre_plan.h:18–29`将底数折入系数：
\[
gain=0.5\ln2,\quad bias=-\ln2,\qquad
y_i\approx\exp(x_i\,gain+bias)=2^{0.5x_i-1}.
\]
这是实数层面的等价式，不代表逐位等价。实际路径为BF16输入转FP32，依次执行FP32 `Muls→Adds→Exp`，最后以`CAST_RINT`转回BF16（`nacre_stage.asc:45–64`）；中间不是源码显式融合的乘加。输入已有BF16量化，系数也是host端float；指数近似、舍入和溢出等影响实际结果，特殊值细节不能仅凭本文件确定。

### 分派、循环与尾块

计划计算`useful=ceil(25019/4096)=7`，查询核数为3，故：
- `laneCount=3`；
- `laneExtent=ceil(25019/3)=8340`元素；
- `windowElements=4096`元素。

`StageNacre::Init/Process`（`nacre_stage.asc:9–33`）按块号切分：

| 块号 | GM起点，元素／字节 | 有效元素 | 三轮count |
|---|---:|---:|---|
| 0 | 0／0 | 8340 | 4096、4096、148 |
| 1 | 8340／16680 | 8340 | 4096、4096、148 |
| 2 | 16680／33360 | 8339 | 4096、4096、147 |

每核循环局部`off=0,4096,8192`。两个整窗各搬8192字节，尾窗分别296、296、294字节，覆盖恰好25019元素，无核间重叠。GM索引以元素计，`DataCopyExtParams.blockLen`以字节计；核起点和尾长并不全为32字节对齐，源码使用`DataCopyPad`而非要求整块对齐的普通搬运（37–42、69–73行）。未请求显式左右填充，计算count也仅覆盖有效元素。

### 存储、依赖与910C执行

`nacre_entry:85–93`运行时按标签选择模板，本题进入`StageNacre<bfloat16_t>`。每核UB申请输入、输出队列各8192字节，FP32临时区各16384字节，总计49152字节，即48 KiB，不含实现元数据（16–23行）。

在910C上，此路径主要使用MTE2搬GM→UB、Vector进行转换和算术、MTE3搬UB→GM，不使用Cube矩阵乘。队列入队/出队及释放承担搬运—计算—复用的依赖管理；源码没有显式硬事件，也没有手工双缓冲。每轮按`CopyIn→Compute→CopyOut`发起，队列深度为1，不能仅凭存在队列便断言形成了跨窗重叠流水。实际异步重叠和指令展开需编译或测量确认。host等待stream后才读回输出（host文件61–63行）。

## 二、入口 C：矩阵乘后原地LeakyReLU

### 算法与任务划分

`source/cube/mica.asc:200–215`固定：
- A为`[512,128]`、B为`[128,128]`连续ND half；
- C为`[512,128]` half；
- 单核与基础tile均为`256×128×128`；
- `numBlocks=(512/256)×(128/128)=2`。

`mica_entry`声明`__mix__(1,2)`（185–194行）。按此混合执行契约，每组1个AIC配2个AIV，本题为2个Cube任务、4个Vector任务；不是把启动参数2直接当作全部物理核数。

每个AIC计算256行的完整矩阵乘，FP32结果放L0C，Fixpipe先转为half写入GM；两个AIV再读取各128行，在half上执行LeakyReLU并原地写回：
\[
S=AB,\quad H=\mathrm{half}(S),\quad
C_{ij}=\mathrm{LeakyReLU}_{half}(H_{ij},\mathrm{half}(0.001)).
\]
因此激活之前已发生一次FP32→FP16转换，不等价于始终在FP32中激活后再转换。`Mmad`的具体内部累加次序、精度模式和特殊值行为不能仅由输出张量类型完全确定。

`Init:33–45`中，AIC编号q的A、C基址均偏移`q×32768`个half，即`q×65536`字节；B基址不变。AIV编号v先映射到`v/2`对应的Cube块，再由`v%2`选择半块（143–158行）。四个AIV最终负责C起始行0、128、256、384，各16384元素／32768字节，互不重叠。

当前没有外层M/N tile遍历，也没有K分段循环：每AIC只做一次完整`Mmad`，K=128全部纳入。模板参数并不意味着实现了任意shape的通用分块；本题常量恰好整除且单核块等于基础tile，无尾块。

### 搬运、存储与依赖

AIC侧（50–68行）每核分配：
- L1：A 64 KiB、B 32 KiB，共96 KiB；
- L0A 64 KiB、L0B 32 KiB；
- L0C：32768个float，共128 KiB。

MTE2将A、B从ND转NZ搬入L1。两核读取不同A行，但各自读取完整B；逻辑B仍是`[K,N]`，后续转置参数服务于硬件布局，不是将数学表达式改成`ABᵀ`。

依赖链由明确事件建立：
1. `MTE2_MTE1`：L1数据就绪后才能LoadData；
2. `MTE1_M`：L0A/L0B就绪后才能Mmad；
3. `M_FIX`：L0C计算完成后才能Fixpipe；
4. `CrossCoreSetFlag<0x2,PIPE_FIX>(0)`与AIV等待配对，令AIV在对应结果写回后读取。

定位分别为70–73、108–129、131–138行。这是经GM中转的Cube/Vector协作，不是直接共享L0C或UB。

每AIV申请32 KiB UB。`ApplyGate`搬128行，每行256字节，GM和UB行间额外间隔均为0；`srcStride=(N-baseN)×2=0`（143–176行）。之后用`MTE2_V`和`V_MTE3`保证读入→激活→写回顺序。入口末尾有`PIPE_ALL`屏障，host再同步stream；前者不应解释为任意核之间的全局屏障。

## 三、C的2201实际路径与3510静态对照

两种条件下，源码的shape、混合启动声明、核地址映射、分配大小、ND→NZ搬运、Mmad参数、Fixpipe调用、跨核通知及AIV激活均相同；唯一显式架构分支是L1→L0加载（75–107行）。

| 项目 | 实际2201 | 静态3510条件 |
|---|---|---|
| A加载API及布局 | `LoadData2DParams`，NZ→ZZ | `LoadData2DParamsV2`，NZ→NZ |
| B加载API及布局 | `LoadData2DParams`，NZ→ZN | `LoadData2DParamsV2`，NZ→ZN |
| 源码调用数／每AIC | A循环16次，B循环8次 | A、B各1次 |

2201中，A每次加载repeat=8、srcStride=16；B每次repeat=8、srcStride=8且转置。两者第i次的L1源起点都是`i×256`个half，即`i×512`字节；L0目的起点均为`i×2048`个half，即`i×4096`字节。512字节对应一个16×16 half基础块，参数中的repeat/stride是块级单位，而不是普通ND行跨度。

3510的V2参数分别为：
- A：`{0,0,16,8,16,16,false,0}`；
- B：`{0,0,8,8,8,8,true,0}`。

它们用二维步数描述整块装载；API调用更少不等于底层搬运指令更少或耗时更短。尤其A的L0布局契约明确不同，不能认为两分支产生相同字节排列，或通过修改宏就在910C上模拟另一架构。

## 四、可确认范围

实际设备宏2201选择上述循环加载路径；host核数查询与device架构宏是不同信息，本题也没有可据以混用的host架构分支。3510仅能作源码静态对照：相同的API名称、`__mix__`声明、`FixpipeParamsV220`结构体并不能证明它们在该目标上的全部支持条件、布局解释和同步契约已通过验证，更不能证明数值或性能相同。

静态上可确认两入口的数据覆盖、显式分工和依赖；无法确认实际带宽、缓存命中、流水重叠、占用率或瓶颈。C的文件输入和ACL调用未像V那样完整检查返回值，输入内容及成功执行还依赖外部文件和运行环境，不能据样例代码宣称已验证正确性。
