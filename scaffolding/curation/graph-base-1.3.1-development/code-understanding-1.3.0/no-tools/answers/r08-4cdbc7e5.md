# 代码理解说明

以下行号除特别注明外，均指 `source/baseline/mmad.asc`；variant 同名符号、行号对应一致。

## 1. 输入输出与数值语义

**源码事实：**A、B、C 的设备指针均解释为 `half*`（L36–40）。本次矩阵维度均为8192；A按 `[M,K]` 行连续存储，题面规定B文件按 `[N,K]` 行连续存储。因此目标为：
\[
C[m,n]=\sum_{k=0}^{8191}A[m,k]B_{\rm file}[n,k].
\]
B是逻辑 `[K,N]` 的转置存储，不是再对文件执行一次全局转置。

每次Cube计算形状为 `128×256×64`，在float类型L0C上累加。每个输出tile的第一个K块设置 `cmatrixInitVal=true`，后续继续累加，最后Fixpipe做 `F322F16` 写回（`Compute`、`CopyOut`，L501–541）。无bias、激活或跨核归约，也不读取原C。目标语义是FP16输入、FP32累加、FP16输出；不能据此保证与任意CPU求和顺序逐位一致，特殊值和转换舍入细节未由材料完整规定。

host读取两份输入、H2D、启动一次kernel、同步stream、D2H并写文件（L597–631）。每个完整矩阵占128 MiB。`int16_t`只用于计算文件字节数，并非整数矩阵乘。host没有正确性比较，也未检查ACL或读文件返回值；`data_utils.h::ReadFile` L47–59允许小于目标容量的非空文件，故完整有效输入仍是运行前提。

## 2. 实际分核与循环

**实际分派：**host `NPU_ARCH=2201`选择 `baseM=128, stepKa=8, singleCoreN=1536, numBlocks=24`；其余为 `baseK=64, baseN=256, singleCoreM=2048, singleCoreK=8192, stepKb=4`（L577–590）。device `__NPU_ARCH__=2201`独立决定LoadData分支。`SCENARIO_NUM=1`只调用 `Process()`；`ProcessL2Cache()`不执行，3510分支也不参与（L562–572）。

令block编号为 \(b\)，则：
- M分区索引 \(i=b\bmod4\)，N分区索引 \(j=\lfloor b/4\rfloor\)；
- 输出区域起点为 `(2048i,1536j)`；
- A、B、C的GM基址偏移分别为  
  `i*2048*8192`、`j*1536*8192`、`i*2048*8192+j*1536`，单位均为half元素，字节地址再乘2（`InitComputeParams`，L273–306）。

20个block的区域为2048×1536；最后4个block（j=5）为2048×512。内部顺序是 **N块→M块→K块**：M循环16次，N循环分别6或2次，K循环128次（L170–192）。每block计算96或32个输出tile，全局共2048个tile，覆盖完整8192×8192且输出不重叠。

这里的512列是**分核区域不足1536**，但仍包含两个完整256列tile。实际 `tailM=tailN=0`，尾块分支不进入；K也整除64、512和256，没有部分K包。一般化代码虽有M/N尾块逻辑，却没有通用K尾包裁剪，不能推广为任意尺寸安全。

## 3. 数据路径与物理存储

**平台/API知识：**910C的Cube核可通过独立搬运、矩阵计算及FIX流水执行这些操作；源代码调用顺序不代表不同流水已经依次完成。这里无Vector计算或UB路径。

路径为：

`GM → MTE2做ND→NZ → L1 → MTE1做LoadData → L0A/L0B → Cube Mmad → L0C → FIX转换并写GM`

`DataCopyInA/B`（L343–388）每次分别搬128×512、256×256个half，各128 KiB，源行距8192元素；`kChunkIdx`实际以64宽K块计数，A每次加8、B每次加4，并非包编号。

`Process` L52–72给出的核内地址如下。区间单位为KiB，均左闭右开；它们是相应存储体内偏移，不是设备绝对地址：

|存储体/缓冲|Ping|Pong|
|---|---:|---:|
|共享L1中的A1|[0,128)|[128,256)|
|共享L1中的B1|[256,384)|[384,512)|
|独立L0A中的A2|[0,16)|[32,48)|
|独立L0B中的B2|[0,32)|[32,64)|

A2、B2虽同为0/32 KiB基址，但属于不同物理存储体，不互相别名。C固定在L0C偏移0，占128 KiB。

2201上，A每个K片用一次 `LoadData3DParamsV2`，从A1包内 `offset*8192` 个half处读取（L395–411）。转置存储B走L458–469：每片执行4次LoadData2D，每次重复16个16×16块，不做转置；源、目的子偏移均为 `i*4096` 个half。每片共搬A 16 KiB、B 32 KiB。

双缓冲复用的是存储槽；不同输出tile会重置GM搬入进度，源码没有让A/B在多个输出tile间直接保留复用。相同数据是否命中L2由硬件缓存行为决定，不能由源码命名推定。

## 4. 一个tile的前10个K迭代

选择block 0、`mBlockIdx=nBlockIdx=0`，输出为 `C[0:128,0:256]`。迭代k处理全局K区间 `[64k,64k+64)`。两版本的**地址选择和指令提交结构相同**，差异在执行约束。

下表A1/B1数值是该片在L1内的**绝对起始偏移，单位KiB**；L0列同时表示A2和B2在各自存储体内的基址。所有迭代累加同一L0C。

|k|A1选择/片起点|B1选择/片起点|L0选择/基址|
|---:|---|---|---|
|0|Ping / 0|Ping / 256|Ping / 0|
|1|Ping / 16|Ping / 288|Pong / 32|
|2|Ping / 32|Ping / 320|Ping / 0|
|3|Ping / 48|Ping / 352|Pong / 32|
|4|Ping / 64|Pong / 384|Ping / 0|
|5|Ping / 80|Pong / 416|Pong / 32|
|6|Ping / 96|Pong / 448|Ping / 0|
|7|Ping / 112|Pong / 480|Pong / 32|
|8|Pong / 128|Ping / 256|Ping / 0|
|9|Pong / 144|Ping / 288|Pong / 32|

包的搬入/覆盖顺序（L178–255）：
- 循环前：A Ping装K `[0,512)`，B Ping装 `[0,256)`。
- k=0的Compute提交后：先向B Pong预取 `[256,512)`，再向A Pong预取 `[512,1024)`。
- k=3：B Ping消费完，覆盖为 `[512,768)`，供k=8–11使用。
- k=7：B Pong消费完，覆盖为 `[768,1024)`；A Ping消费完，覆盖为 `[1024,1536)`。
- k=8、9分别读取A Pong的前两片及已重装B Ping的前两片。以上“之后”表示提交位置，不表示Compute已完成。

## 5. 事件依赖与版本差别

**按HardEvent的跨流水同步语义，baseline形成如下关系：**

1. `MTE1_MTE2`：L1可覆盖通知。A Ping/Pong用ID0/1，B用ID2/3；初始化预置，搬入前等待，每包最后一片LoadData之后释放。它保护的是MTE1读取L1，不必等待Cube完成。
2. `MTE2_MTE1`：包搬完才允许读取。仅包首片等待：上述10轮中A在k=0/8等待ID0/1，B在k=0/4/8等待ID2/3/2；同包后续片依靠MTE1流水顺序。
3. `MTE1_M`：每轮LoadData后Set/Wait，使Mmad读取对应L0之前，搬运已完成（L506–507）。
4. `M_MTE1`：baseline每轮加载前等待当前L0槽释放，Mmad后发释放事件（L209、519）。首次消费预置事件；从k=2起，建立  
   `Mmad(k−2)读完该槽 → LoadData(k)覆盖该槽`。
5. Mmad的 `unitFlag`为中间2、末轮3，Fixpipe为3，使用平台M/FIX结果交接机制；这不等同于L0A/B覆盖保护。末尾事件回收及 `PIPE_ALL`（L265–270、572）用于收尾，不能代替中途依赖。

**唯一差异**是variant删除第4项中的循环内Wait（`source/VARIANT.patch` L3–8）。交替地址、正向等待、反向Set和末尾Wait均保留。

因此variant仍能证明“本轮搬完再计算”，却缺少源码显式建立的“前轮读完再覆盖”：最早k=2的MTE1写Ping可能与k=0的Cube读Ping重叠，后续每两轮同理。保留的正向同步方向相反，L1事件也不保护L0；末尾等待或全流水屏障无法追溯修复该竞争。

此外，variant反复Set同一 `M_MTE1` 事件却不逐轮消费，破坏baseline成对使用的结构；不能把硬事件假定为可无限计数的信号量。但仅凭材料不能确定重复Set的具体运行表现，也不能断言必然死锁、必然错值或必然加速。实际是否触发覆盖、编译器是否补入依赖、指令时延和缓存命中均无编译产物或测量支持。**可静态确认的是显式依赖保证被削弱，而不是某个已经观测到的运行结果。**
