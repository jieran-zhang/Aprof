# `data_copy_pad.asc` 代码理解

以下行号均指 `source/current/data_copy_pad.asc`，另行注明者除外。区间统一采用**相对各缓冲区基址的字节偏移、左闭右开**。

## 1. 输入输出与整体语义

**源码事实：**`scenarioNum=2`（L20）；host 实例化参数为 `srcRows=5、srcCols=13、dstCols=16、dstTotalLength=120`（L220–223）。入口选择 `KernelDataCopyPad<float,...>`（L194–201），因此每元素4字节。这些参数分别控制搬运行数、每行有效元素数、UB内填充长度和UB分配量，并非统一的物理矩阵形状。

本 workload：

- 输入GM：5行，每行20个float，行距80B，共400B；值为 `100*r+c`。
- 输出GM：5行，每行18个float，行距72B，共360B；先全部初始化为字节 `0xA5`（L241–259）。
- UB：分配120个float，即480B，先全部清零（`Process`，L60–64）。

**由API语义推导的最终变换：**

\[
z[r,c]=x[r,c]=100r+c,\quad 0\le r<5,\ 0\le c<13
\]

输出每行的 `c=13…17` **不写回**，其每个字节仍为 `0xA5`，即每个float存储槽保留位模式 `0xA5A5A5A5`，不是零填充。输出有效部分依次为 `0…12、100…112、200…212、300…312、400…412`。

这是**跨行有间隔的复制，经UB补齐，再只写回有效列**；没有加法、归约、类型转换或浮点计算。输入有效float位模式由搬运保留。UB中确实有零填充，但这些零未进入输出。

`VARIANT.patch` 明确改动了步长、UB清零及写回方式，不能沿用 upstream 的“整个连续UB写回”解释。

## 2. 地址、填充和写回范围

### API单位与步长

**平台/API知识：**此处普通 `DataCopyPad` 使用Normal布局。`DataCopyExtParams` 的 `blockLen` 单位为B；GM侧stride是相邻块之间跳过的字节数，UB侧stride单位为32B数据块，且是块后的间隔，不是起点间距。padding计数单位为元素。

**搬入**（`CopyIn`，L95–105）：
```cpp
copyParams{5, 52, 28, 1, 0}
padParams{isPad=true, leftPadding=0, rightPadding=3, paddingValue=0}
```

- GM每行读取13个float，即52B；跳过28B，下一行起点增加80B。
- UB每行52B数据，右补3个float即12B，组成64B对齐块；再跳过 `1×32B`，下一行起点增加96B。
- 此例显式padding已经恰好达到32B整数倍，不需额外的对齐填充。
- `paddingValue=0` 是明确赋值（L103）；不依靠注释中“isPad=true即为零”的简化表述判断数值。

**写回**（`Process`，L68–69）：
```cpp
copyParams{5, 52, 1, 20, 0}
```

- UB侧每行读取52B，按32B补齐所占源块为64B，再加32B源间隔，因此起点仍增加96B。
- GM侧每行只写52B，跳过20B，因此输出行距72B。UB中的12B padding和32B间隔均不写入GM。

### 各行实际区间

| 行r | 输入GM读取 | UB有效数据 | UB右侧零填充 | 输出GM写入 |
|---|---|---|---|---|
| 0 | [0,52) | [0,52) | [52,64) | [0,52) |
| 1 | [80,132) | [96,148) | [148,160) | [72,124) |
| 2 | [160,212) | [192,244) | [244,256) | [144,196) |
| 3 | [240,292) | [288,340) | [340,352) | [216,268) |
| 4 | [320,372) | [384,436) | [436,448) | [288,340) |

其余区域：

- 输入每行 `[80r+52,80r+80)` 的28B，即列13–19，未作为有效数据搬入；最后一行也是如此。
- UB行间32B间隔为 `[64,96)、[160,192)、[256,288)、[352,384)`；末尾 `[448,480)` 同样只保留预清零值。不能把这些stride间隔称为 `rightPadding`。
- 输出未写区域依次为 `[52,72)、[124,144)、[196,216)、[268,288)、[340,360)`，全部保留 `0xA5`。

因此，逻辑GM有效读取260B、写入260B；UB初始化480B，搬入形成5个64B数据加padding块。最大输入读取终点372B，UB搬入终点448B，输出写入终点340B，均在本次分配内；这些数字不等于硬件总线实际传输量。

## 3. 分派、任务、同步与依赖

**源码事实：**

- `numBlocks=1`，以 `<<<numBlocks,0,stream>>>` 启动（L225、264）。无动态tiling结构、workspace参数，也没有按核编号切分地址。
- 一个 `__vector__` kernel任务执行整批5行。`if constexpr` 在编译期选择float路径，非运行时逐行分派。
- 当前路径没有源码层行循环、分块主循环或双缓冲；两次搬运各通过 `blockCount=5` 表达5块重复搬运。
- L107–186的3510专用Compact/loop-mode代码，在本题device宏2201下被预处理排除。场景4/5的循环常量不参与本次执行。
- 没有“最后一行不足”的任务尾块；5行规格完全相同。每行52B不是32B整数倍，其尾部由上述padding和搬运长度规则处理。

依赖链为：

1. **V写UB零 → MTE2写UB数据和padding**：`Duplicate` 后的 `V_MTE2` Set/Wait（L62–65），保证向量清零先完成，避免迟到的清零覆盖搬入结果；未被搬入覆盖的间隔继续为零。
2. **MTE2生产UB数据 → MTE3读取UB写GM**：`MTE2_MTE3` Set/Wait（L66–69）保证搬入结束后才读UB。结合前一步，建立完整顺序。
3. 入口末尾 `PipeBarrier<PIPE_ALL>()`（L212）完成核内全流水同步；它不是跨核或host同步。
4. host的 `aclrtSynchronizeStream`（L266）等待kernel完成，然后D2H并输出360B文件（L268–269）。前面的同步式memset/H2D调用提供启动前数据准备；以上均以API调用成功为前提。

只有一个UB张量，输入和输出GM为独立分配（L254–257）；无队列、核间通信、原子操作或输出读改写。

## 4. 910C执行行为与确认边界

**平台知识对应：**目标2201上，该实现使用向量执行路径及UB，不使用Cube矩阵计算。`Duplicate` 由V流水写本地UB，GM→UB搬运由MTE2承担，UB→GM由MTE3承担；事件连接不同流水，不能仅凭C++语句顺序假定异步流水已完成。32B对齐约束体现在UB布局，而GM端允许本例52B长度与非32B对齐行起点。

**静态可确认：**源码只启动一个block，没有显式多核并行；整个工作集很小，且上述事件将三个阶段按依赖串接。没有源码级的跨批次搬运/计算重叠。

**不能由材料确认：**具体编译指令数、`Duplicate` 的repeat/mask展开、DMA事务粒度、缓存命中、物理AI Vector Core映射、带宽与耗时均需编译或测量；不能据此宣布某流水是性能瓶颈。

上述结果依赖给定400B输入内容、运行时成功及API契约。host未检查ACL和文件操作返回值；`ReadFile` 还会通过引用修改 `inputByteSize`（`data_utils.h` L25、59），因此短文件或读取失败不属于已证明正确的输入边界。当前没有实测结果，但不影响对本 workload 的逻辑布局、依赖与输出保留区间作上述静态判断。
