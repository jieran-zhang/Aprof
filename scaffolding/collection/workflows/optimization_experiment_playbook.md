# 优化实验、过程记录与经验提炼手册

版本：2026-09-11。适用于外部协调器组织的 AProf 算子优化实验。

本手册规定如何组织实验、把实际过程保存为可还原的记忆，以及从证据中提炼条件经验。优化 agent 继续使用原有 AProf skills 和 workflow；graph、runtime gate 和正式 episode 的语义保持不变。实验的目标是解决算子的性能问题，数据质量来自有反馈的实验和准确的记录，不以候选数、成功率或 lesson 数为目标。

**下一轮 A/A 与 A/B 的主指标改为原生 msprof 的完整调用 task 耗时总和，默认只采时间；探索 A/A 容限由 ±0.5% 调整为 ±2%。** 同一原生进程/context/stream 内配对、独立进程重复的设计继续保留。校准用于说明各 case 的测量分辨能力，不再把“全 case 达到严格等效”作为开始优化的总开关。优化 agent 仍按原 AProf workflow 工作；外部协调器负责返回有质量标记的反馈、捕获轨迹和提炼经验。

本手册第 2、3、6、8 节是**后续探索的组织规范**，优先于旧文档中与之冲突的 event 主指标、±0.5% 探索门槛及质量不足即全任务停止规则。[共享 context 配对协议](shared_context_paired_protocol.md)保留为历史协议和设计参考，不改写旧结果；现有 msprof 入口及实测范围见[方法说明](msprof_kernel_time_study.md)。本次只更新本文件，没有修改脚本、schema、skills、graph、gate、历史数据或 checkpoint，也不启动设备。

## 1. 开始前确定边界

新探索使用独立 run，任务清单在启动 manifest 中明确：剩余 Level1 的 train 为 `exp、masked_scale、foreach_addcdiv_scalar、mish、sigmoid`；`foreach_norm` 的已有源码可作为方法对照，新增优化须另列任务。本手册更新不自动启动任何算子。旧批次剩余 21 个冻结候选属于另一条补测队列，不自动接续。`gelu` 的 validation 与 train 分 store、分数据视图，`swi_glu` 继续封存。实验结论属于已知 workload，不能写成未见样本泛化。

每算子默认最多 **3 轮“单次修改—执行—反馈—下一步”迭代**，不预先写完三个候选。源码修改后的失败也要反馈，不以补满三个成功候选为目标；提前停止应说明预算、安全/正确性问题或已无可区分的优化问题，不能仅因为某 case 的 A/A 不够精细。每次产生新优化源码并进入执行都占一轮，包括源码修复；同源码重测只增加 observation，不增加源码轮次。六次测量进程启动不是六轮源码优化。

预算上限仍为 6 个源码候选、6 次候选构建、6 个候选计时组、3 个候选**机制 profile** 组，承接消耗从 checkpoint 读取。六候选是既有账本的总上限，不授权本批超过三轮。搜索和最终全量比较各占一个计时组：最多三个候选参加搜索，停止搜索并冻结清单后，再对选定候选做全量比较。上限不是用满配额的要求；失败修复计新源码尝试并消耗构建额度，同源码重测只增加 observation 和计时成本。只采 task time 的 msprof A/B 归入计时组；多 counter/流水线机制诊断归入 profile 组，不能因工具都叫 profiler 就重复计费或把候选计时藏进免费诊断。baseline、A/A 和方法控制另列固定计划及实际成本。

| 开始前冻结的内容 | 记录要求 |
|---|---|
| 任务与精度契约 | 上游任务 commit、20 个 case 的 shape/dtype/layout/属性、输入生成与 oracle、阈值、特殊值覆盖；本地与上游差异单列 |
| 源码与工具 | 原始 baseline、直接父本、依赖 commit、实际工作树快照及 diff、构建参数、harness patch；优化 patch 单独保存 |
| 知识入口 | 原有 workflow、角色 skill、相关诊断/优化 reference、适用 playbook、graph/schema/runtime 路径 |
| 实验规则 | case 集合、预算及已消耗量、测量协议与分析版本、顺序种子、控制实验、失败/停止规则 |
| 环境 | 主机、物理 chip 与逻辑设备映射、SoC、CANN/驱动、CPU affinity、设备健康、占用与锁；未知值附原因 |
| 决策边界 | 哪些历史结果只作先验、哪些问题尚未解决、何时冻结候选、何时暂停 |

启动 manifest 应足够让 fresh agent 从任务和源码开始工作。默认只加载相关知识分支和一个适用 playbook，按需读取精确 reference；不要把整个仓库和历史 CSV 清单灌入初始上下文。技能路径与内容 hash 由协调器固定，实际阅读及使用另行记录。

## 2. 分工与一次实验的闭环

| 角色 | 职责 | 交付 |
|---|---|---|
| 协调器 | 队列、预算、设备互斥、反馈、冻结和 checkpoint | 任务 manifest、执行安排、状态与选择依据 |
| 优化 agent | 按原 AProf workflow 诊断、修改和验证；根据反馈决定下一步 | 实际分析、源码修改、正常工作记录 |
| 外部记录器 | 捕获已发生的读取、判断、执行、失败和决策；绑定来源 | 事件流、实验记忆、证据索引 |
| 独立分析 agent | 从记录和原始证据提炼问题—干预经验，检查反例与边界 | lesson、缺失证据和待验证问题 |

每个算子使用隔离上下文，例如 `fork_turns="none"`，只传 manifest。分析 agent 不替优化 agent 补写当时的想法；优化 agent 不负责填写训练 JSONL，也不因产出更多 lesson 得到更多实验预算。

总流程如下；其中性能质量判断分支决定**能说多强的结论**，不替代是否继续源码探索的判断：

```text
固定起点（任务、skill、baseline、输入和工具）
  → baseline 20/20 correctness + msprof A/A 逐 case 校准
  → agent 按原 AProf skill 收集机制 profile 并诊断
  → 一个优化候选 → 静态/构建/20-case correctness/runtime
  → msprof A/B（父本与原始 baseline 独立比较）
  → 带 case 条件、质量和不确定性的反馈 → 下一轮（默认最多 3 轮）
  → 冻结候选 → 完整 20-case 评估 → 发布 trace/lesson → checkpoint
```

记录器从第一步持续工作，每轮封存观察和判断更新；最终发布不代替及时记录。

一次完整循环按以下顺序推进：

1. **当前基线验证和诊断。** 重新构建、验证 20/20 correctness，核对 prepared 路径输出，再用只采 task time 的 msprof 做 A/A，并按原 workflow 采集 baseline 机制 profile。历史记录只能作有来源的先验。A/A 精度不足时标记受影响 case，仍进入诊断和候选探索；源码、精度或采样身份错误按第 3 节停止相应执行。
2. **选择一个修改。** 优化 agent 根据当前症状提出一个可区分的干预。记录其实际给出的理由、预期和备选；未说明的内容记为缺失。不得预先要求列满候选清单。
3. **封存尝试身份。** 登记原始 baseline、`source_parent`、源码快照、精确 patch、构建参数和 `decision_basis`。源码修复产生新候选；同一源码的重测只增加 observation/session。
4. **分阶段执行。** 静态检查、构建、全量正确性、runtime、搜索 case 的 msprof 时间比较，按需要追加独立机制 profile。每个阶段保留 argv、cwd、主机/设备、起止时间、退出状态和日志。执行或完整性失败关闭该次执行并跳过依赖阶段；A/A 不等效、区间较宽、无收益或回退是需反馈的观察，不等于执行失败，不覆盖旧输出。
5. **返回足以改变决策的反馈。** 给出具体 case/属性分组、每个进程的 task 时间倍率及区间、normal/swapped 和顺序差异、A/A 分辨能力、预测 counter 与实际变化。明确哪些只是观测、哪些有局部收益证据、哪些待精测；suite speedup 和 gate verdict 不能代替这些信息。
6. **让反馈决定后续。** 下一次可修正解释、探测作用边界、处理剩余瓶颈，或沿已验证父本改进。记录哪条 observation 改变了判断，以及选择继续、回退或停止的理由。
7. **关闭 observation 后再进入下一候选。** 记录器封存证据并更新实验记忆；分析 agent 可提出回溯解释，但不会把它变成事先预测。

下一实验优先解决影响选择的不确定性，例如“是 p 分支受益还是公共路径改变”“任务粒度在哪个范围已经饱和”“guard 开销与 vector 工作量能否区分”。只有一个失败点时，先定位该点；不要堆入多个相互抵消的改动，使结果无法解释。关联的必要配套修改可以作为一个干预，但应明确无法分别归因。

profile 额度优先用于区分候选机制、解释反例和异常，而不按 suite 提速排名分配。采集前保存实际提出的 counter 预测，采集后分别列出符合、相反和缺失；旧 profile 只在来源与条件相容的范围内作先验。没有当时预测的，可以做回溯分析，但不能声称进行了事前机制检验。

### 父本、比较与预算

`source_parent` 是实际编辑的源码；`decision_basis` 是影响此次选择的已发生观察。二者独立，不能由“上一个 candidate ID”猜测父子关系。

父本作为**源码探索起点**，必须具备可验证的源码身份、当前构建、20-case correctness、prepared 路径正确性和 runtime 通过记录；不要求其 A/A 全部等效、已有加速或满足 3% 生产准入。性能尚不确定的父本可以继续改进，但应明确标为“正确性已验证、性能未确认”，保留原始 baseline，不能把它推广为已确认的最优实现。这样允许记录真实的迭代轨迹，同时不把不稳定数据变成收益正例。

`source_parent` 与其**性能结论资格**分别记录。沿父本继续时，分别进行“子候选 vs 直接父本”和“子候选 vs 原始 baseline”的独立 msprof 采样；父本就是 baseline 时合并为一次比较。某比较不确定不自动废弃另一个比较；不得拼接样本或用历史倍率相乘、相除推算总收益。跨协议历史结果只作先验，不能作为当前比较样本。

**预算中的一个计时组定义为：一个候选、一个阶段、一个事先冻结的 case 集合和完整测量计划。** 它包含最多两个比较，每个比较包含第 3 节规定的独立进程重复。搜索与冻结后的全量评估分别消耗组额度；同一源码的额外重测也消耗新组。组启动即计费，失败不退款；预启动恢复仍保留原组及恢复记录。每次安排搜索前须预留选定候选的全量组额度，不把 6 个计时组理解为可以无限重测 6 个候选。

构建一旦启动即计数；即使只重建相同源码也记录消耗。profile 组预先固定候选、case、比较来源和捕获窗口；不能看到结果后追加 case 到已关闭的组。不同的实际命令、比较、case、进程启动、完整算子调用和墙钟时间另设成本账本。

现有 `shared_context_campaign.py` 已有多 observation、启动计费和 checkpoint 能力；`cannbench_msprof_timing.py` / `run_msprof_timing_study.py` 是独立的方法采集入口。**本手册没有把它们自动接成新的优化 campaign。** 新的评价分级、A/A 复用和轨迹绑定须由后续外部 adapter 显式实现；旧 `trace_v2_campaign.py` 与旧 event 协议的自动停止行为不能直接用来执行本规范。

### 搜索与最终揭示

搜索默认只反馈 `[1,8,14,20]` 的性能。每个候选可在测量前声明至多两个额外诊断 case，并解释要检查的分支或边界；声明后不可随结果改变。正确性始终覆盖全部 20 个 case。候选诊断 case 在第一次计时前写入其计划，不修改旧 checkpoint 绕过限制。初始 A/A 可以覆盖全部 20 case，但搜索期间只向优化 agent 返回 sentinel 和已声明诊断 case 的数值；其余校准结果由协调器保存，待最终阶段揭示。

停止搜索后冻结候选源码、父本、参数、身份、清单及全量比较计划，再揭示全部 20-case 性能。该批次不再追加候选。事后分组标为探索性分析；需要验证的新问题留给下一独立批次。不得把完整结果已经可见的候选重新称为 sentinel 盲搜。

## 3. msprof 时间比较、逐 case 校准与继续规则

### 3.1 主指标与两类 profile

已有 2026-09-11 方法试验支持“ACL event 区间会包含设备可见的 host 提交间隙”，不能简化为“event 测的是 CPU 启动函数耗时”，也未证明所有剩余波动都由 host 引起。exp case1 的同源码延迟干预中，给 A 每次提交前 sleep 200 μs 后，event 为 262.751/8.684 μs，task 为 6.464/6.427 μs；两个反向干预各只有一次进程，不能证明 task 时间对提交节奏完全不敏感。详见2026-09-11 方法报告（外部历史记录：`../.aprof/runs/msprof-kernel-time-20260911/REPORT.md`）。

| 指标/采集 | 本手册用途与边界 |
|---|---|
| `operator_task_sum_us = sum(Task Duration(us)) / repeat` | **A/A、A/B 主指标**。每样本内所有完整调用、所有串行 kernel 的 task 耗时求和，再除以完整调用次数；包含设备 task 调度、执行和结束响应，排除 task 间间隙，不是端到端延迟或纯 busy time |
| 原生 `msprof --task-time=l1 --ai-core=off` | 默认轻量计时模式；显式设置 request 的 `profiler_mode=task_time_l1_ai_core_off`，不能依赖工具的兼容默认值 |
| `aiv_time` / `core_us` | 辅助平均核时间，非最慢核完成延迟；只采 task 时缺失为 null。需要它时另设 PMU-on 诊断组，不与主计时样本混合 |
| 原 AProf 机制 profile | agent 继续按原 skill 使用适用的 `msprof op` / `msopprof` 或多 counter 流程诊断瓶颈。它解释机制，不以这批不同配置的 duration 替代主 A/B 样本 |
| ACL event、`task_span_us`、`inter_task_gap_us` | 可选诊断信息，分别展示窗口、跨度和间隙。event 不再作为探索停止门槛，也不与 task 指标混成一个训练标签 |

`foreach_norm` 必须包含所有列表成员的 partial/finalize；分块 TensorList 必须包括全部 chunk/tail。优化前后 kernel 数可以不同，按各自真实源码的完整调用序列核对，不能只比较同名的一个 kernel。当前解析器仅接受经过 launch 核验的 `AI_VECTOR_CORE` target task；其他 task 类型需要先适配和方法验证，不能只因串行就直接使用。当前主指标只适用于已核验的串行、无重叠 target task；多 stream/重叠时不能直接求和宣称延迟收益，应另立方法。优化减少 host 调度或 kernel 间空隙但 task sum 未变时，保留这个指标盲区，不写成优化必然无效。

### 3.2 一批测量怎样组织

新的研究协议标识建议为 `msprof_task_time_exploration_v1`，度量、阈值和统计版本在执行前冻结。它是本手册的拟用协议名，**不是现有 CLI/schema 已接纳的新模式**；现有工具的 `msprof_kernel_time_study_v1` 原始标识及 producer hash 同时保留。

| 参数 | 探索默认值 |
|---|---|
| 原生执行 | 一个 process、显式 context、同一 stream、同线程串行调用两个独立角色；输入准备/分配/H2D 在计时外；host delay=0 |
| 每个比较 | 6 次独立 native 启动，每次覆盖该比较全部声明 case；同进程做 A/B 配对 |
| 每 case/config | 两角色分别 warmup=10；30 对、15 AB/15 BA；每角色样本 repeat=10 次完整调用 |
| 资源/顺序 | normal、swapped 分别输出；六进程均衡加载顺序和起始 AB/BA，显式列出分配，避免两个因素完全混杂；记录配置执行顺序 |
| 采集模式 | task time l1、ai-core off；设备、CPU affinity、输入、binary/harness 和 profiler 配置冻结 |
| 独立诊断 | counter profile 单独计划；默认 warmup=10、repeat=5 的完整调用捕获，按实际 launch 数核对，不挪作主时间数据 |

repeat=10 是为限制 profiler 数据量而选择的独立协议参数；旧 event 的 repeat=100 结果保持原样。原生正常退出、目标 task 名/身份/顺序/数量、设备/stream、正且有限的时间与逐 CSV 行来源均须可核验。预热按每角色实际完整调用序列排除：固定 K 个 kernel 时跳过 10K，K 随 case/角色改变时分别计算。解析不能以“头十行”代替十次完整调用，辅助 PMU 缺失不能填零，缺预热 PMU 不能被误当作正式 task 的零时长。

候选先做全部 20-case correctness；计时路径还需校验每个 case/config/role 最后一次正式调用的输出，明确没有逐次校验所有中间调用。每个比较有 6×30×2=360 个角色样本/config/case、3,600 次正式完整调用/config/case；normal+swapped 加倍。warmup、A/A 控制、两个比较、离线导出和失败成本另外统计，不把 repeat 内的调用算作独立统计重复。

### 3.3 逐 case 校准与复用

“逐 case”指一批 A/A 进程共同覆盖声明 case，然后分别统计；不是每个 case 单独启动六个进程。

1. **固定 baseline A/A。** 两角色使用相同 baseline 源码，输入与 oracle 相同，角色符号和资源身份独立可核验。批次开始用六次启动覆盖 20 case，得到 normal/swapped 的逐 case 倍率、95% CI、CV、AB/BA 差异和已覆盖的资源/加载控制。
2. **建立校准卡。** 每 case 保存 shape/dtype/属性、源码/资源路径、模式/设备、六个倍率、控制区间、质量状态与缺失项。每个字段区分“等效”“观察到偏差”“精度不足”“未覆盖”，而不是只有 pass/fail。
3. **同 epoch 复用。** 后续候选引用该卡，不为每个候选机械重跑旧 before/reverse/after 三套完整 A/A。默认在批次结束另做固定六次同基线 A/A，检查校准作用范围内的漂移；开始与结束分别报告，不能挑较好一组或拼在一起缩窄区间。结束控制异常时，给相关候选追加质量观察与限制，保留当时决策，不覆盖原结果。
4. **失效与新控制。** 设备/CANN、profiler 模式、runner/harness、输入或 affinity 改变时建新 epoch。父本/候选改变了分配、workspace、chunk/launch 或角色加载路径时，原 baseline A/A 不能证明新路径无偏；预声明相关父本 A/A 或同源码角色控制，计入固定成本。控制未覆盖时可继续探索，结论标为条件性观察。

起始与结束各六进程是后续批次默认控制计划，不是对 2026-09-11 已有 study 的重述。中途新增控制须解决明确的新混杂或资源变化，在执行前冻结 case、次数和停止规则；稳定性失败不触发“再跑六次直到通过”。已知大波动 case 仍保留原数据，可暂不承担小收益判别任务；不能将剩余子集包装成全 20-case 合格。

### 3.4 放宽探索精度，区分四种结果

**探索 A/A 容限采用 log 对称的 ±2%：主倍率 95% CI 应落在 `[1/1.02, 1.02]`。** 不是只要求点估计接近 1，也不是只要求区间跨 1；因此下界约为 0.980392，不写成另一种阈值 0.98。CV 仍按单进程、单 case/config、单角色计算并要求 ≤5%；不同 shape 的延迟不拼接算 CV。normal/swapped 分别判断，已估计的顺序、缓冲区、加载效应也以 log 差及其区间对照预声明容限。均衡顺序不等于完成独立的加载因素控制，缺失控制保留为“未覆盖”，不能判作通过。

| 结果类别 | 判断与处理 | 对下一轮的影响 |
|---|---|---|
| 执行/证据无效 | baseline 或候选精度/runtime 失败；target task 缺失、重复、错绑、重叠、单位错误、非有限值、native 未正常退出等 | 停止受影响执行，保留失败；候选错误不阻断其他安全候选。共享 runner/解析身份不可信时暂停全部相关采集，先修复；不输出该观察的有效时间样本 |
| 有限分辨能力的可用测量 | 所声明控制完整，两个配置的 A/A/因素区间达到 ±2%，各 case/config/角色 CV≤5%，A/B 采样完整 | 正常反馈和继续；只说明该作用范围的粗粒度分辨能力，不自动保证任意小收益真实 |
| 完整但需谨慎解释 | A/A 精度不足/已见偏差、CV>5%、某控制未覆盖，或 A/B 跨进程/配置不一致；原始采样本身完整 | **继续记录、诊断和源码迭代**，标明受影响 case；倍率/CI 是有质量限制的观测，不能加入合格性能数组或宣称确认收益，也不把整个任务关闭 |
| 小变化、无收益或回退 | 完整结果没有达到预期，含区间跨 1、局部正负相抵等 | 是正常实验结果；反馈用于修正假设、沿正确父本继续或有理由停止，不自动重测，不因没有“成功样本”删记录 |

1%–3% 附近的变化默认标记“待精测”；即使 CI 很窄，也不能忽略相近量级的角色/资源效应。需要确认时，在新计划中预声明 ±1% 或 ±0.5% 的精细控制及预算，不回头换阈值挑结果。大幅收益可以优先验证：当适用控制满足粗粒度要求、A/B 区间与两个配置/各进程结果共同支持同一方向时，可给出**限定条件的时间收益证据**；若控制仍不确定，则保留“观察到大倍率、归因和精度未确认”，仍可继续优化。

A/A 不是 A/B 误差的严格上界，不用 A/A 均值去扣除、相除修正 A/B，也不能用“收益超过 A/A 偏差”这一条规则确认收益。单 case 不合格不抹掉其他 case 的有效证据；完整 suite 结果仍须列齐全部 case 和各自状态。缺 case 时不给完整 suite 数值；原样本完整但含质量不足 case 时，可给清楚标注的描述性 suite，不给“全量合格”标签。另报子集时同时列出原集合、覆盖数与选择理由，事后选出的子集标为探索性。

这次已有六 case 的 PMU-off 数据中，仅对 normal/swapped 均值 CI 回顾性套用 ±2% 时为 5/6 落带，原 ±0.5% 为 2/6；这只说明新阈值的探索动机，不是完整因素控制通过。exp case1 的缓冲区影响仍需保留，case9 仍有明显区间/顺序问题，不能继续放宽到“它也通过”。新阈值仅用于未来冻结的计划；历史 study 的 `aa_within_half_percent` 与旧 verdict 不重判。

### 3.5 进程级统计与反馈

令 `T[r,c,k,j,A/B]` 为一个角色样本的 `operator_task_sum_us`，r 是进程，c 是 case，k 是 normal/swapped，j 是配对：

```text
case_log[r,c,k] = mean_j(log(T[r,c,k,j,A] / T[r,c,k,j,B]))
suite_log[r,k]  = mean_c(case_log[r,c,k])
L[k]           = mean_r(suite_log[r,k])
speedup[k]     = exp(L[k])
95% CI[k]      = exp(L[k] ± t(0.975,5) * std_r(suite_log[r,k], ddof=1) / sqrt(6))
```

逐 case 用 `case_log` 替代 `suite_log`。case、进程等权，normal/swapped 分别报告；AB/BA 顺序分层及可识别的加载/缓冲区效应独立展示，不能用总均值遮住反转。六进程是主区间的重复单位，不展平 180 对或数千 kernel。新 PID 本身不证明统计独立，六点 t 区间保留近似独立/分布假设，并展示执行时间顺序、全部六点与异质性。缺进程不冒充六进程完整评估；必要的描述性摘要写明实际 n，不能沿用 df=5。

`S>1` 表示 task 时间加速，候选延迟变化为 `1/S-1`；区间 `[l,u]` 对应变化区间 `[1/u-1,1/l-1]`。区间跨 1 不证明持平，低 CV 不证明无偏，几何平均倍率不等于总墙钟时间减少比例。全部 case 各自 95% 区间也不是同时覆盖保证。

每轮反馈使用以下人读模板；它不是新增 JSON Schema：

```text
观察/源码尝试/直接父本/原始 baseline/协议、metric、case 集合：
此前判断及来源：未记录的预测明确缺失，不补写为事前认识。
测量：task_us、repeat、profiler mode、A/A 校准卡及复用范围。
质量：逐 case 的 CV、A/A/顺序/资源状态、六个倍率、缺失和异常。
结果：normal/swapped 的 case、分组和 suite 倍率/CI；哪些仅观测、哪些待精测。
机制：源码变化、独立 counter profile、支持/相反/缺失证据。
判断更新：哪个解释得到支持或削弱；有无与改动无关的混杂。
下一步：继续/沿父本改进/回退/有理由停止，引用实际观察和剩余轮次预算。
机器状态：correctness/runtime/原始 gate 各自保存；新研究评价正式准入 not_evaluated。
```

旧生产规则 LCB≥1.03、最大 case 回退≤3% 保留原义，**不作为本轮能否继续收集轨迹的门槛**。小回退、无效和不确定结果均可产生经验。新 task 指标不填入旧 event gate，不伪造 v1 episode 或 propensity；需要正式选优时另行评估适用范围和准入接口。

## 4. 捕获可还原的实验记忆

两份主要视图仍为 `optimization_traces.jsonl` 与 `lessons.jsonl`。事件流、原始样本、profile、源码、日志、索引和 CAS 是支撑归档，不是需要反复塞入正文的第三份训练摘要。train 与 validation 分目录、分索引作用域保存。

当前结构以 [memory schema](../contracts/optimization-memory-v2.schema.json)、[lesson schema](../contracts/conditional-lesson-v2.schema.json)和 [v2 工具说明](optimization_trace_collection_v2.md)为准。以下是字段填写规则，不允许绕过已有 schema 随意增加结构字段；新测量报告的专用结构应另行版本化，由 adapter 绑定。

| 实验记忆中的位置 | 保留在正文的内容 |
|---|---|
| `identity`、`sources`、`context_ref` | 稳定尝试 ID、operator/split、原始 baseline、真实父本、候选/patch 和共享上下文引用 |
| `knowledge` | 实际读取与判断用途，相关少量条目；完整目录引用一次 |
| `diagnosis` | 当时具体症状、数值、来源性质、可能解释、相反证据和缺失证据 |
| `intervention` | 精确位置、关键前后代码或公式、参数、实际理由与预期；完整 diff 外置 |
| `evaluations` | 同一源码的不同 observation/session；task metric、原始单位、repeat、profiler mode、比较对象、A/A 校准卡、阶段与证据质量分别记录，保留逐 case/config 的倍率/CI及报告 |
| `timeline`、`next_decision` | 观察发生的先后、认识如何变化、实际选择及其依据 |
| `machine_results` | 原始 verdict、失败阶段、准入与源码选择；提前返回的默认数值不可当实测 |
| `provenance` | producer/提取版本、来源和回溯属性；共享依赖闭包不重复展开 |

过程捕获应区分四种行为：**实际阅读知识、明确用于判断、解析测量数据、仅校验 hash**。读过不代表用于某次决策，CSV 不是 skill 阅读条目；只有读取事实时不要推断“已消化”。

关键事件在发生时写入 worker 独立流，由协调器校验顺序、hash 链和去重后汇总。捕获命令与输出来源，不要求保存或补造模型私有推理；保存可审查的假设、理由摘要和实际工作产物即可。时间戳区分事件发生与事后提取，不能从文件修改时间编造精确执行顺序。未知发生时间在允许 nullable 字段的版本化原始报告中用 null 和原因；现有 v2 `timeline[].timestamp` 必须为字符串，导入事件使用真实已知的采集/导入时间，并在 summary 明示“原事件发生时间未知”，不把它当作原实验时间。

历史导入统一标记 `retrospective`、来源记录和提取版本。新观察产生的回溯解释也标记回溯，不能移到旧候选的“事前预期”。同一源码补测合并到同一尝试；六次进程、A/A 控制或阈值敏感性分析不增加源码尝试；已构建失败、精度失败、无收益、NOOP、回退、停止及执行中断全部保留。跨协议补测有新 observation 和协议 ID，不修改旧 observation 的判定。

### 去重与可读性

workload、环境、依赖和知识目录各保存一次。统一证据索引将短 ID 解析为内容 hash、文件、split 与具体位置，例如 CSV 的完整表头/行/列、JSON pointer、源码行及源码版本。正文仅列支撑该事实所需的引用；完整 artifact 清单、原始数组和依赖闭包外置。

“外置”不能变成只剩引用：`case 9，BF16，[363,367,373]，两阶段中位数约 166/179 μs` 是应可直接读到的事实；全部采样点才放到报告。源码锚点必须绑定相应源码快照，不能只链接到以后会变化的工作树行号。

稳定 ID、修订号、内容 hash 与前一修订引用用于追溯。记录和证据先封存，两个当前 JSONL 作为同一不可变 revision 发布，再原子切换 `current.json`；旧修订留在 CAS。中断后的 staging 不当作完成版本。只复制两个 JSONL 不等于得到可搬运数据集，交付还须包含其索引与引用闭包。

JSON 数值禁止 NaN/Infinity；任务中的特殊值使用显式标签。缺失使用 null 并说明缺的是未执行、失败、历史未记录还是不适用。引用能解析不等于结论成立；读取校验也不能隐式调用 gate、登记 artifact 或写入历史 SQLite。

## 5. 提炼具有条件和反例的 lesson

一条 lesson 围绕一个**性能问题—干预**，可以引用多个真实候选及不同观察。不要把同算子的不同机制拼成一条，也不要把同一实验拆成很多“独立验证”。组合优化的总收益和单项增量分别归属，禁止重复归因。

| 字段 | 内容要求 |
|---|---|
| `diagnosis.symptoms` | 具体症状、数值/单位、case 范围、源码锚点；标明实测、源码事实、启发式或推断 |
| `intervention` | 算法/调度机制、公式或关键代码、参数、作用位置、必要配套修改 |
| `effective_conditions` | 实际 shape/dtype/属性、工作粒度或代码分支，以及该条件下的实测结果和不确定性 |
| `ineffective_conditions` | 未表现预期收益的范围；“观测无收益”与“未测/尚无法判断”分别说明 |
| `counterexamples` | 具体条件、反驳的命题、结果和不确定性；小回退也纳入，不以 3% 作过滤器 |
| `claims` | 每个可分别判断的命题，状态 `supported/refuted/inconclusive`，证据及适用范围 |
| `limitations`、`next_questions` | 混杂、历史证据边界、未覆盖范围，以及能进一步区分解释的实验 |
| `graph_links` | 实际节点和关联依据；没有对应节点时为空，不制造 route、edge 或 propensity |

条件、症状和反例采用内嵌对象，关键细节直接可读。不要用 suite speedup 充当 `effective_conditions`，不要把完整引用清单当作 `diagnosis.symptoms`。

命题的正负与命题的真假是两回事。例如“某未特化分支在这些条件下变慢”可为 supported；它反驳的是“所有分支都提速”。“预期 scalar time 降低”与“观察到 stall 降低”是不同命题，需要分别判定。采样无效时仍可确认源码改了什么，但不能确认由该改动造成多少收益。A/A 精度不足时，“观测到某倍率”与“源码修改导致真实收益”分别建命题：前者可作为带质量限制的实测事实，后者仍可为 inconclusive；无收益和小回退也不因未达到正式准入而消失。

对于 msprof 观察，症状与条件对象内嵌 `metric=operator_task_sum_us`、case/shape/dtype/属性、profiler mode、repeat、倍率/CI 和校准状态；这些名称是填写内容约定，放在现有允许的 fact `attributes` 或引用的版本化报告中，不冒充已增加的 schema 顶层字段。每个“有效”条件说明是局部时间证据还是待精测的观察；未测、精度不足、观测无收益分别标注，不能把未测 case 当作无效负例。

方法 lesson 也要把具体适用条件和反例放进 `effective_conditions / ineffective_conditions / counterexamples`，不能只在 `symptoms` 里放一个布尔标记。例如“只采 task、case9 的进程内 CV 很低，但六进程 A/A 区间仍宽”反驳“低 CV 足以证明无偏”，不反驳该算子的任何优化方案。通用方法经验复用一次，关联各 case 的具体观察；不要把方法失败计成算子优化尝试。

### 示例：p=1 恒等运算移除应保留什么

| 10 | float16；1 × `[2049,513]`；1 | 2.498145；`[2.493337,2.502975]` | 非整齐维度也执行该分支；不是任意尾块均已覆盖 |
| 16 | bfloat16；4 × `[255,8193]`；1 | 2.892671；`[2.886560,2.898821]` | 此四成员列表条件下受益 |
| 20 | float32；4 × `[2,3,17,1024,101]`；2.5 | 0.986902；`[0.986532,0.987279]` | 回退 1.3272%；反驳“所有分支都受益”，不反驳限定于 p1 的命题 |

这一例可支持“已测 p1 分支移除恒等运算有局部收益”，并提供“所有分支都会获益”的反例。这里的普遍收益命题是事后的适用范围检验，未声称优化 agent 当时作过该预测。它不证明其他 dtype/shape、非有限输入或未见 workload，也不证明非 p1 回退的唯一机制。它仍须在新 msprof 协议下独立验证，不能直接迁移旧置信区间。

### 独立阅读验收

分析 agent 仅拿到新记录和所引证据，应能准确回答：原先哪里慢、为何怀疑该机制、具体改了哪里、什么条件受益、什么条件不受益、哪些结果不确定、下一实验能区分什么。若它还需反查数千项无差别清单才能找到这些答案，或只能复述一行“gate 未通过”，则记录尚不合格。

## 6. 把实操经验用于执行

**本机一个时刻只有一个活跃硬件任务。** 用主机级串行锁，并兼容旧设备锁；监测不遵守锁的外部进程。计时 native 存活期间不并行编译、其他 profile、导出或大规模共享盘 hash，CPU 分析安排在窗口之间。当前 msprof 自身采集所需的工作照常记录；不能把“避免额外 profiler”误读成不用主采集器。原生正常退出且 PID 已结束之后，才可调整离线导出进程的 CPU affinity，保存前后设置与证据；不能只看到文件出现就宣布计时结束。健康和进程清理只在实际启动授权下执行，本次文档工作不触碰设备。

| 已遇到的问题 | 后续做法 |
|---|---|
| event 受 host 提交间隙影响 | 主目标改为核验过完整调用的 task sum；event/span/gap 分列。sleep 对照支持这种影响，不能据此把所有剩余波动归为 host 原因 |
| 只采 task 仍有跨进程/资源差异 | 保留各 case/config 的六点、CI、CV 和顺序差异；关闭 PMU 没有消除 exp case9 的问题，不宣布工具天然稳定 |
| 严格 A/A 阈值让整个任务停止 | 采用预声明 ±2% 探索容限；不足时降低相应性能命题强度，继续正确性合格的源码实验，不丢失失败、反例和迭代决策 |
| 只有某些 case 校准充分 | 校准卡绑定 case、源码/资源、模式、harness、设备和 epoch；不推广为全任务资格，不将坏 case 删除后宣称全量合格 |
| msprof 抓到预热或漏掉 TensorList/partial/finalize | 由 journal 对齐真实完整调用序列和 CSV 行；时间采集是 warmup=10、每角色样本 repeat=10，独立机制 profile 可用 warmup=10/repeat=5，分别记账 |
| 单 kernel/profile duration 被当成完整延迟 | 只有无重叠、串行、全 launch 核验后才汇总 task 时间；优化可改变 launch 数，按各自源码聚合。task sum 排除了间隙，不能冒充 event 或端到端 |
| profiler 收尾失败或辅助 PMU 缺失 | native 没有正常结束不能因为输出校验通过就放行。缺 PMU 不填零；解析器修复只读重分析另存，不覆写原失败或顺手重跑硬件 |
| CSV 长表头与大绝对时间戳 | 完整解析表头及行/列，保留单位；用足够精度处理时间戳并检查顺序，不靠短 grep 或低精度浮点丢失微秒信息 |
| 重复扫描与共享盘开销 | 按内容去重，采集结束后批量导出/核验；artifact 清单外置，记录 CPU/IO 成本，不用导出墙钟作为算子时间 |
| 输入与 oracle 身份混淆 | 分开记录 native 输入、golden、输出和末次校验范围；身份绑定内容，不靠文件名 |
| 只读验证误写归档或调用 gate | 纯读取验证；衍生报告另存，修复发布新 revision，原 evidence、SQLite、verdict 保持冻结 |

客观预启动编排/环境故障每阶段最多一次显式恢复，保留原命令、错误和未启动事实；执行中失败保存部分产物，不能自动补一个“好进程”。仅解析/导出问题优先对已封存 raw 数据另存离线分析，不重采硬件；源数据缺失不由解析修复补造。稳定性、方向或收益未达到预期，不属于可自动恢复的基础设施故障。

改变测量方法需要关闭当前 observation、保留协议和样本，另立固定计划；因新候选源代码错误而修复仍计新源码尝试。某 case 的精度限制只限制该 case 的结论；若 runner 绑定、输出正确性或采样完整性失去可信来源，才暂停相关硬件链路。其他任务是否受影响按真实共享依赖判断，不把“一个 case 不够稳定”扩大成六个算子的总阻断。

## 7. 发布、验收与停止

交付内容包括两份 JSONL、对应 schema、证据索引、上下文/知识/环境 manifest、源码和 patch、逐进程逐 case 原样本、profile、失败日志与报告。报告按“性能问题—干预—证据—适用条件—结果/限制”组织，单独保存方法问题与剩余方向。

发布前核对：

1. 尝试、修订和补测数量正确；重复导入不增加尝试；时间线没有把事后解释改为事前预测。
2. baseline/parent/candidate、patch/binary/harness、比较样本、case/protocol/单位和输出校验范围相互一致。
3. 关键症状、条件、代码差异、负例和不确定性在正文可读；知识判断不由 gate 自动覆盖。
4. 新 task 协议按进程聚合、normal/swapped 分列；缺失或异常 case 未悄悄删除；不同模式/协议未混样，A/A ±2% 是事前探索规则，旧 ±0.5% verdict 未重写。
5. graph 关联有依据。新 msprof 研究观察无论是否关联 graph 知识节点，均固定 `graph_policy_eligible=false`、`episode_ref=null`、正式准入 `not_evaluated`；未来图内正式比较另须绑定真实父本和 Context，不能借用上一候选的 Context。
6. 只读验证无写入副作用；两个视图原子发布且旧修订仍可恢复；正式 v1 outcome/hash/replay 不变。

批次达到三轮、预算用尽、优化 agent 有证据地决定停止、用户要求暂停，或遇到无法继续的执行阻断时保存 checkpoint；单 case 的 A/A 不等效不自动触发整批停止。checkpoint 包含当前 revision、完整候选清单、每阶段状态、已用/剩余轮次和预算、逐 case 校准卡/复用范围、未决解释、下一动作及依据、失败恢复次数、输入和产物位置。确认本轮进程已退出、释放锁和设备，状态设为等待明确开始。以后从已封存 checkpoint 读取，不能从零重置预算，也不自动扩大到旧队列。

## 8. 当前能力与后续落地顺序

这次仅维护实验方案。现有研究工具已经完成过方法试验，不再把共享 native runner 或 msprof 解析链路描述为“从零待实现”；但文档中的探索规则也不等于代码已完成接入。

| 入口 | 当前已有能力 | 本手册的新约定仍需什么 |
|---|---|---|
| `cannbench_msprof_timing.py` | 独立 native runner、显式 task-only 模式、完整 launch/CSV 绑定、oracle、逐 case/config 的进程级 CI、角色 CV 和每进程顺序效应 | 当前 `aa_within_half_percent` **仍硬编码 ±0.5%**；±2% 评价、校准卡/失效管理、完整因素区间及 suite 统计尚需外部分析适配。保留原布尔值，不能只改名字当新规则 |
| `run_msprof_timing_study.py` | 串行执行冻结的有限 schedule，不覆盖输出、不自动重试 | 反馈式三轮候选协调、最终额度预留、A/A 复用及结束控制需要 campaign adapter；不能把有限方法试验脚本当成已完成的优化循环 |
| `shared_context_campaign.py` / `shared_context_archive.py` | 账本、多 observation、独立 v2 归档基础 | 绑定新 task 报告、将执行状态与证据质量分开、取消旧 event 资格不足导致的总停止；不修改原历史账本 |
| v2 JSONL / CAS 与旧 gate | 版本化记忆/lesson、证据与只读验证；旧 gate/replay 语义保留 | 新方法报告独立版本化并绑定 `evaluations`；未接正式接口前不写 v1 episode，不填旧 event 数组 |

当前 summarizer 会拒绝不同 source/build、case 集、设备/CPU、PMU、host-delay 等条件混合，但它不会替协调器完成全部加载/起始顺序设计；`load_order/first_order` 需要明确的 cohort、可识别设计及分层报告。normal/swapped 的均值 CI 达标，不等于所有加载/顺序/资源控制已经通过。

后续在收到明确执行命令之后，按以下顺序落实：

1. 冻结任务清单、剩余预算、新研究协议/分析版本与恢复策略；保留已有失败 run 和旧队列。依据[msprof 方法说明](msprof_kernel_time_study.md)显式选择 task-only，原 AProf workflow 只负责正常优化。
2. 实现并核对上表的外部适配：测试“采样无效应停止”和“A/A 精度不足应继续但限制结论”两条分支，同时核对多 kernel、配置隔离、父本、预算、CSV、单位和输出契约。此处是后续工程验收，本次不运行测试或硬件。
3. 执行初始逐 case A/A，保存卡片后进入 baseline 机制诊断与第一候选；对需谨慎解释的 case 按第 3 节返回完整观察，不再等待所有 case 达到 ±0.5%。底层正确性/来源不可信时仍暂停修复。
4. 每轮一个修改，构建/精度/runtime 后做 msprof A/B，把条件结果和不确定性交回同一优化 agent，最多三轮；保持分析 agent 和外部记录器独立，不给优化 agent 设置 lesson 数量目标。
5. 冻结候选与全量比较清单，执行完整 20-case 性能及预声明的结束 A/A；更新质量限制、发布两份 JSONL、核验来源，保存 checkpoint 并释放设备。揭示后不在该批追加候选，不自动接续旧 21 候选。

历史命令见[最初 campaign](level1_trace_campaign.md)、[串行续采](level1_serial_continuation.md)和[旧 event 配对协议](shared_context_paired_protocol.md)。其中各自记录的独立角色进程、repeat=100、±0.5% 强资格、绝对漂移硬阈值及自动停止策略均保留其历史作用域；本手册没有将这些旧 CLI 自动升级成新 msprof 探索入口。
